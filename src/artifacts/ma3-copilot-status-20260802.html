오퍼레이터 관점 기능 제안

“연출을 만드는 것”은 파이프라인이 이미 해냅니다. 이제 부족한 것은 공연 당일 오퍼레이터의 시간 흐름 — 셋업 → 리허설 → 본 공연 → 철수 — 을 따라가는 기능입니다. 기존 자산(OSC 왕복·툴 13종·대시보드)을 재활용할 수 있는 순서로 정리했습니다.

Tier 1 — 즉시 착수 가능 (기존 자산 재조합)

프리쇼 체크리스트 자동화 제안서 P2-6

공연 30분 전 오퍼레이터가 손으로 확인하는 것들 — OSC 연결, 시퀀스/실행기 존재, 프리셋 무결성, DMX 출력 — 을 한 번에 검사.

기존 ping/state 왕복 + get_rig_context 10경로 조회를 묶어 “공연 준비 OK / 항목별 결함” 신호등 리포트로. 과거 반복된 함정(소켓 스테일, osc_slot Send행, 응답포트 9005 드리프트)을 자동 진단 항목으로 승격하면 실전 가치가 큼.

쇼파일 스냅샷 & 안전 되돌리기

AI가 콘솔 메모리를 만드는 앱의 최대 불안은 “잘못 만들면?”. 오퍼레이터가 안심하고 시키려면 되돌리기가 필요.

배치 작업 전 SaveShow 스냅샷을 자동으로 남기고, 감사 로그와 짝지어 “이 지시 이전으로 복원” 제공. 콘솔 쇼파일 정리 세션(34건 삭제) 경험이 그대로 재료가 됨.

라이브 큐 진행 모니터 (대시보드 확장)

본 공연 중 오퍼레이터의 시선은 “지금 어느 큐, 다음 큐는 뭐, 페이드 얼마나 남았나”에 고정됨.

DASHUI 좌측 상태 풀에 현재 시퀀스/큐 번호·다음 큐 미리보기·최근 실행 이력을 폴링 표시. state 채널 확장만으로 가능.

Tier 2 — 중기 (한 SPEC 규모)

자동 페이퍼워크 생성 제안서 P2-4

패치시트·큐시트·매직시트는 만들기 귀찮지만 대관·협업에 필수인 문서.

get_rig_context가 이미 리그 전체를 회수하므로, 이를 인쇄용 HTML/PDF(패치시트·큐시트·프리셋 목록)로 렌더링. 콘솔 쓰기 없음 → 위험 0.

볼런티어 런북 모드 제안서 P2-5

교회·소극장에선 비전문 오퍼레이터가 콘솔을 잡는 날이 많음. “이 버튼만 누르세요” 수준의 안내가 필요.

SONGCUE 큐리스트를 기반으로 곡 순서·큐별 실행 버튼·주의사항만 남긴 극단순 UI 프리셋. DASHUI에 모드 스위치로.

페이지·실행기 레이아웃 자동 구성

버스킹의 실제 마찰은 “페이더 어디에 뭘 놓을까”. 실행기 주소 체계(실번호=i+100)는 이미 실측·검증 완료.

BUSKWIZ 산출물을 받아 장르·곡 구성에 맞춰 페이지별 실행기 배치를 제안·자동 할당하고 라벨까지 부여. “버스킹 준비”의 마지막 조각.

Tier 3 — 장기 (검증 난도 높음)

타임코드/음악 동기 연출

SONGCUE가 만든 큐리스트를 타임코드 트리거(TrigType 설정은 이미 라이브 검증됨)로 자동 배선 — 재생만 누르면 곡 전체가 무인 진행.

음성 명령 버스킹

본 공연 중 손은 페이더에 있음. “다음 곡”, “파랗게” 같은 짧은 음성을 기존 자연어 파이프라인에 그대로 흘리는 입력 채널 추가.

공연 후 자동 회고 리포트

감사 로그 + 실행 이력으로 “이번 공연에서 실제 쓴 큐/안 쓴 큐, 수동 개입 지점”을 정리 — 다음 공연의 쇼파일 다이어트 재료.

실행 로드맵 — 세션 단위 순차 진행 + 병렬 판정

아래 순서는 기능마다 실제로 건드릴 코드 표면을 저장소에서 확인해 잡은 것입니다. 공유 병목은 딱 하나 — 신규 툴 등록이 전부 지나는 server/orchestrator/tools.py — 이고, 나머지 표면은 기능별로 분리돼 있습니다.

병렬 레인 (선택 — 워크트리 분리 세션)

D 페이퍼워크는 조회 전용·신규 디렉터리라 어느 시점에든 별도 워크트리 세션으로 병행 가능합니다. S1~S3 어디와 붙여도 파일 충돌이 없습니다. 형제 SPEC을 같은 base에서 병행할 때의 함정(머지 순서에 따라 BASE..HEAD 게이트가 깨짐)은 FXLIB·OVERLAP 머지에서 이미 학습됨 — 먼저 머지된 쪽 이후 리베이스 후 게이트 재실행이 규칙입니다.

또한 각 세션 내부에서는 plan-phase 리서치(코드 표면 조사·기존 자산 인벤토리)를 read-only 서브에이전트 병렬 fan-out으로 돌려 세션 시간을 줄일 수 있습니다 — 쓰기 작업은 항상 1개 에이전트 순차.

요약 — 순차 축은 S0→S1(A)→S2(B)→S3(C)→S4(E)→S5(F), 병렬 축은 D(페이퍼워크)를 아무 때나 워크트리로. 첫 착수는 위험이 가장 낮고 기존 OSC 노하우를 그대로 제품화하는 S1 프리쇼 체크리스트를 권장합니다.

OMP 실행 패키지 — Orca 오케스트레이션으로 돌리기

이 저장소는 이미 Orca 오케스트레이션으로 병렬 웨이브를 성공시킨 이력이 있습니다(SCENE-001: 코디네이터 1 + 워커 3, 쓰기 집합 교집합 ∅, 워커는 커밋·전체테스트·SPEC 문서 쓰기 금지 — 검증과 커밋은 코디네이터). 같은 계약을 그대로 재사용합니다. 아래 명령을 코디네이터 터미널(현 세션)에서 순서대로 실행하면 OMP 패널에 Run·Task·워커가 나타납니다.

0단계 — Run 생성 + 태스크 DAG 등록

orca orchestration run-create --objective "MA3 코파일럿 오퍼레이터 로드맵 — 웨이브1(A 프리쇼·D 페이퍼워크 병렬) → 웨이브2(B 스냅샷·C 라이브모니터) → E 런북 → F 레이아웃. 워커는 커밋·전체테스트·SPEC문서쓰기 금지; 검증·머지·커밋은 코디네이터." --json

orca orchestration task-create --spec "T-A 프리쇼 체크리스트: 워크트리 preshow-check에서 /moai plan→run. 쓰기 집합: server/preshow/(신규)·server/tests/. tools.py 등록은 스텁 커밋으로 분리해 코디네이터에 보고. 완료=AC 정의+pytest 신규 green 증거를 worker_done으로." --json
orca orchestration task-create --spec "T-D 자동 페이퍼워크: 워크트리 paperwork에서 /moai plan→run. 쓰기 집합: server/paperwork/(신규)만 — 조회 전용, 콘솔 쓰기 금지. 완료=패치시트·큐시트 HTML 산출 + 테스트 green 증거를 worker_done으로." --json
orca orchestration task-create --spec "T-B 쇼파일 스냅샷·복원: server/safety/backup.py 확장 + gate·audit 연동. T-A 머지 후 리베이스 기점에서 시작." --deps '[""]' --json
orca orchestration task-create --spec "T-C 라이브 큐 모니터: server/web/dash.py·panel.py + ui/src. T-A 머지 후 시작." --deps '[""]' --json
orca orchestration task-create --spec "T-E 볼런티어 런북 모드: ui/src 중심 — T-C 완료·머지 후에만 시작(ui/src 충돌)." --deps '[""]' --json
orca orchestration task-create --spec "T-F 실행기 레이아웃 자동 구성: orchestrator·rulebook + BUSKWIZ 산출물 소비. 최후순." --deps '["",""]' --json

1단계 — 웨이브 1 워커 기동 (검증된 병렬쌍 A ∥ D)

orca orchestration worker-start --task <T-A id> --worktree new-child --name preshow-check --agent claude --setup run --json
orca orchestration worker-start --task <T-D id> --worktree new-child --name paperwork --agent claude --setup run --json

# 코디네이터 대기 루프 (폴링 금지 — 이벤트 대기)
orca orchestration check --wait --types worker_done,escalation,question --timeout-ms 1800000 --json

2단계 — 머지 규율 (FXLIB·OVERLAP에서 학습된 규칙)

worker_done 수신 시 코디네이터가 ① 워커 워크트리에서 검증 배치(테스트·게이트) 직접 실행 → ② main 머지 → ③ 아직 열려 있는 형제 워커에게 리베이스 + 게이트 재실행 지시(같은 base 형제 SPEC의 BASE..HEAD 게이트는 머지 순서에 반드시 깨짐) → ④ 다음 웨이브 태스크 dispatch. 판단이 갈리는 지점(예: tools.py 등록 순서)은 gate-create로 결정 게이트를 세워 사용자 승인 후 진행.
