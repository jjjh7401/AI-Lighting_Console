## 0. 한눈에

감독이 런북 모드에서 곡을 **역할 6개 × 마디** 격자로 보고, 칸을 고치고, 승인 한 번으로 콘솔에 보내는 기능이다. 보낸 결과는 콘솔에 **역할별 시퀀스 6개 + 트랙 6개짜리 타임코드 1개**로 만들어지고, 타임코드를 재생하면 마디에 맞춰 각 역할이 따로 움직인다.

새 송신 장치는 **완전히 새로 짜지 않는다.** 앱에는 이미 곡 큐용 타임코드를 만드는 코드(`server/looks/songcue.py`, 트랙 1개)와 승인 게이트가 있다. 새 장치는 그 부품(빈 번호 판독·이름 규칙·승인 경로)을 그대로 쓰고, **트랙을 여러 개로 늘리고 트랙마다 박자 이벤트를 심는 부분만** 새로 만든다. 그 명령 꼴은 t520 이 실기에서 이미 돌려 본 것이다.

## 1. 무엇을 만드나 — 감독이 쓰는 흐름

| 단계 | 감독이 하는 일 | 앱이 하는 일 |
|---|---|---|
| 1. 보기 | 런북 모드에서 곡을 연다 | 격자 표시 — 행은 4마디, 열은 SCENE · BACK PULSE · SIDE CHASE · MOVER-U · MOVER-D · ACCENT. 처음엔 0~25마디 |
| 2. 고치기 | 칸을 눌러 바꾼다(예: 「11~13마디 MOVER-U 를 틸트 웨이브로」) | 화면은 **문장만** 만들고 서버가 검사·적용한다. 틀린 값은 이유 하나를 대며 거절. 되돌리기 20단계 |
| 3. 승인 | 승인 카드에서 명령 묶음 전체를 한 번 본다 | 구간(묶음) 단위로 명령 파일 하나 — 칸마다 따로 묻지 않는다 |

## 4. 새 송신 장치 — 어떻게 만드나 [제안]

### 4-1. 위치와 경계

- 새 모듈 하나(가칭 `server/looks/beat_grid_emit.py`)를 `songcue.py` **옆에** 둔다.
- 연출 경로 `server/director/emit.py` 와 그 재생 계약(`manual_go`·`trig_time`)은 **손대지 않는다**. 기존 큐시트 재생은 그대로 돈다.
- 곡 큐 경로에서 가져다 쓰는 것: 빈 번호 판독(`timecode_slot_verdict`, 시퀀스 빈 번호 고르기), ASCII 이름 정리(`_ascii_label`), 승인 게이트 경로.
- 입력은 서버에 저장된 격자 하나뿐이다. 화면이 명령을 직접 만들지 않는다.

### 4-2. 입력 → 출력

**입력(격자)**: 곡 BPM(112.35)·다운비트 위상, 그리고 역할마다 「몇 마디 몇 박에 → 무엇으로」 바뀌는 칸 목록. 칸 하나는 고정값(밝기·색·위치) 또는 반복 동작(펄스·체이스·움직임 — 모양·주기 박 수·축·위상) 중 하나다.

**출력(명령 묶음, 승인 파일 한 개)** — 묶음 순서는 t520 이 실기에서 돌린 것과 같다:

| 묶음 | 내용 | 실기 근거 |
|---|---|---|
| ① 역할 시퀀스 6개 | 역할마다: 큐마다 `Group N ; Attribute … At …`(선택 **한 줄**) → 반복 동작이면 `Step 2` 값 + 속도·주기 → `Store Sequence S Cue k '<라벨>' CueFade f` → `ClearAll`. 끝에 `Set Sequence S Property 'Name' '<곡명> - <버전> <역할>'` | [잰 것] t520 승인 파일 587줄, `Store Sequence` 22 · 이름 줄 |
| ② 타임코드 뼈대 | `Store Timecode T` · 이름 · `Duration` · `Store Timecode T.1` · 역할마다 `Assign Sequence S At Timecode T.1.i` | [잰 것] t520 트랙 2개, t516 트랙 2개 |
| ③ 트랙 이벤트 | 트랙마다 `Store Type 'CmdSubTrack' Timecode T.1.i.1` → 그 안에 바뀌는 시각마다 `Store Property 'Time' t 'AbsTime' t 'Token' 'Go+'` | [잰 것] t520 트랙당 이벤트 7·15개, 계획 시각 뒤 첫 표본(≤0.7초) 안에 큐 진행 |
| ④ 재생(별도 승인) | `Top Timecode T` → `Go Timecode T`, 음원은 앞 여유 3초 뒤 시작 | [잰 것] Top 이 0.00 으로 되감음, 음원 띄운 시각 TC 3.002초 |

시각 계산: 마디·박 → 초 = 앞 여유 3초 + 음악 지도(`reports/loveattack-music-map-20261006.md`)의 그 마디 실제 시각. 박 수 × 60/BPM 만으로 세면 다운비트 위상만큼 어긋난다(18마디: 41.45초 대 실제 40.9초 — t520 이벤트도 40.9초). 반복 동작의 주기도 박 수로만 적고, 실제 속도는 스피드 마스터 15(112) 에 묶는다.

### 4-3. 반드시 지킬 줄 꼴 (실기에서 확인된 것만)

| 지킬 것 | 이유(잰 것) |
|---|---|
| **큐 하나에 선택 하나** | 큐 하나에 선택 다섯 + `Step 2` 를 넣었더니 무빙 Pan/Tilt 만 남았다(t520 §20 — 첫 시연 「팬만 나온다」의 원인). 역할마다 시퀀스를 나누는 이유가 이것이다 |
| 선택은 `Group N ; …` 한 줄 | 서브픽스처 디머까지 열린다. `Fixture a + b.1` 목록은 `Illegal object` 로 거절 |
| Spiider 는 `Attribute 'Dimmer2' At 100` 을 같이 | 기본값 0 이라 안 켜진다(감독 손 시험) |
| BACK 은 Pan 180 / Tilt 80 | 감독 결정(t519). 계산상 객석 위 공중 — 덜 보일 수 있음 |
| 되감기는 `Top Timecode` | `Off Timecode` 는 되감지 않는다 |
| 색은 W 0 + 채도 높은 RGB, `ColorMacro` 쓰지 않음 | 첫 시연 색이 거의 흰빛(채도 0.15~0.45). `ColorMacro At 0` 은 Failed |
| 번호는 빈 칸만, 덮어쓰기·삭제·쇼 저장 없음 | 기존 규칙. 빈 번호는 쓰기 직전에 다시 읽는다 |

### 4-4. 승인과 대조

1. 격자 → 명령 묶음 생성(서버).
2. 가짜 콘솔 리허설 → 대조 PASS 확인.
3. 승인 카드: 묶음(구간) 단위로 한 번.
4. 송신 → 감사 로그의 실제 보낸 줄을 재구성 → 승인 파일과 sha256 동일 + 설명 안 되는 줄 0건이어야 성공. 비교 로직은 `approval_vs_sent.py` 를 바이트 그대로 앱 모듈로 옮긴다(새로 발명하지 않는다).

### 4-5. 방식 비교

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 새 모듈 + 곡 큐 부품 재사용 (권장)** | 위 4-1~4-4 | 기존 큐시트·연출 재생이 안 흔들린다. 실기로 돌려 본 명령 꼴 그대로 | 모듈 하나가 늘어난다 |
| B. `emit.py` 에 타임코드 방식 추가 | 연출 경로 재생 계약을 넓힘 | 장치가 하나 | 기존 연출 재생 경로를 다시 검증해야 한다 |
| C. `songcue.py` 를 직접 확장 | 곡 큐 경로에 트랙·이벤트 추가 | 코드가 가장 적다 | 기존 곡 큐 생성(LDRENDER 결과)과 섞여, 옛 연출과 리듬 연출을 나란히 비교하기 어려워진다 |

**M1 ①(트랙 3개 이상)이 실패하면**: 트랙을 둘로 줄이고 나머지 역할 시퀀스는 SCENE 큐의 명령으로 함께 출발시키는 방법이 후보다. 다만 큐 명령 방식은 실기에서 잰 적이 없다.

## 6. 안 잰 것과 남은 위험

- 타임코드 트랙 3개 이상, 그룹 한 선택 페이저 저장, 다른 속성 겹침, 서클·발리후 — 모두 M1 이 잰다. 그 전에는 해당 송신을 열지 않는다.
- 곡 큐 경로의 부품을 그대로 쓸 수 있는지는 코드만 읽었다. 함수 경계(인자·반환)가 격자에 맞는지는 M4 설계 때 확인한다.
- 스피드 마스터 BPM 을 곡과 함께 싣는 방법(G9)은 모른다 — 감독이 콘솔에서 직접 맞춘다.
- 음원과 타임코드 동기는 t520 의 재생 스크립트(앱 밖)로만 맞춰 봤다. 앱 안에서 음원을 같이 트는 것은 이 SPEC 범위가 아니다.
- 전곡(26~82마디)을 한 묶음으로 보낼 때의 명령 줄 수·쓰기 시간은 안 쟀다(0~25마디가 587줄).
