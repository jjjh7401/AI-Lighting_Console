# SPEC-COPILOT-MVP-001 — 설계 (design)

> Tier L 설계 산출물 (plan-audit MVP-M6 반영). 근거: `/DESIGN.md` §3(시스템 아키텍처), §4(Claude 연계), §5(안전 설계). 본 문서는 컴포넌트 아키텍처와 **안전 관문(chokepoint) 설계**를 다루며, 구현 세부(함수 시그니처 등)는 run-phase에 위임한다.

### A.1 LLM 프로바이더 추상화 계층 (2026-07-15 amendment — REQ-MVP-038~041)

- **인터페이스 분리**: 프로바이더 중립 인터페이스가 ① 도구 호출(도구 스키마 등록·호출 파싱), ② 시스템 프롬프트 구성(룰북 고정 프리픽스 + 가변 컨텍스트 배치), ③ 응답 파싱(텍스트/도구 호출/오류)을 추상화한다. 상위 계층(안전 게이트·UI·브리지)은 활성 프로바이더를 알지 못한다.
- **어댑터 2종**: Anthropic 어댑터(`claude-opus-4-8`, prompt caching — cache_control 프리픽스), Gemini 어댑터(설정 핀 모델, context caching). 도구 스키마는 중립 정의에서 프로바이더별 형식으로 어댑터가 변환한다.
- **전환 메커니즘**: 설정 파일의 프로바이더 키 1개로 전환 — 코드 변경 없음 (AC-MVP-026의 코드 diff 0건 검증 대상).
- **캐싱 정책**: 프로바이더별 캐싱 능력에 따름(REQ-MVP-041) — 미지원/최소 토큰 임계 미달 시 비캐시 경로로 동작하고 성능·비용 저하를 수용한다. 왕복 시간 판정(AC-MVP-003)은 활성 프로바이더의 웜캐시 가능 조건 기준.
- **기본 프로바이더 선정**: REQ-MVP-040 술어 — 적격 = 프로바이더별 오류율 <5%(AC-002) **AND** 왕복 중앙값 <10초(AC-003) 동시 통과; 적격 중 비용 우선(측정 코퍼스 1회 실행 실측 청구액, 무료 등급 0 계상); 운영 중 AC-003 지속 미충족 시 다른 적격 프로바이더로 폴백(설정 전환 + 감사 로그).

## B. 안전 관문(single chokepoint) 설계 — REQ-MVP-029

**불변식**: 콘솔로 향하는 모든 명령은 안전 게이트를 통과한다. 게이트 이외의 어떤 모듈도 OSC 송신 표면에 도달할 수 없다.

설계 수단:
1. **송신 표면 캡슐화**: OSC 송신 함수는 bridge 내부 비공개 표면으로 두고, 게이트 모듈만이 접근 가능한 단일 진입점을 노출한다. orchestrator·api·ui는 송신 표면을 직접 참조할 수 없다.
2. **아키텍처 테스트 (AC-MVP-019 ①)**: 정적 임포트 경계 검사 — "OSC 송신 모듈을 임포트하는 모듈 집합 == {안전 게이트}"를 CI에서 자동 검증.
3. **감사 로그 대조 (AC-MVP-019 ②)**: 모든 OSC 송신 이벤트와 게이트 통과 기록의 1:1 대응을 E2E에서 대조 — 게이트 미경유 송신 0건의 런타임 증거.

## C. 게이트 파이프라인 설계

```
명령 시퀀스 생성 (모델)
  → ① 문법 밸리데이터        실패 → 차단 + 자가 수정 회신 (REQ-MVP-012)
  → ② 위험 분류
      · 폐쇄 블랙리스트 (SSOT 설정 파일, 초기 6종)         (REQ-MVP-013)
      · 간접 호출(Go/Call) 전개-또는-보류                  (REQ-MVP-026)
      · 파괴적 플래그 플러그인 호출 = 블랙리스트 동급       (REQ-MVP-028)
  → ③ 인간 승인 (위험 시)     거부 → 번들 전체 미실행       (REQ-MVP-014~015)
  → 잠금 체크                 잠금 활성 → 제안 카드만; 잠금-우선 (REQ-MVP-016, 035)
  → 백업 정책 체크            위험 명령 → 직전 백업; 백업 실패 → 실행 차단 (REQ-MVP-017, 034)
  → OSC 송신 (게이트 전용 진입점) + 감사 로그 기록          (REQ-MVP-001, 018, 029)
```

번들 실행 원자성: 승인은 all-or-nothing(REQ-MVP-015), 실행은 stop-on-first-failure + 기실행분 재전송 금지 + 부분 상태 보고(REQ-MVP-033).

## D. 플러그인 경로 게이트 통합 — REQ-MVP-019, 027, 028

```
deploy_plugin(lua_source)
  → pcall 컴파일 검증          실패 → 자가 수정 루프 회귀
  → 파괴적 내용 스캔           블랙리스트 키워드 포함 Cmd() 검출 → 리뷰어에 스캔 결과 표시
  → 인간 리뷰 게이트           승인 → 배포 (+파괴적이면 플래그 등록)
배포 후 플러그인 호출
  → 명령 실행 경로로 취급 → 게이트 통과 (§C 파이프라인)
  → 파괴적 플래그 → 매회 인간 승인
```

> **잔여 위험 (plan-audit m5)**: 정적 `Cmd()` 스캔은 **최선 노력(best-effort)** 통제다 — Lua 문자열 연결·동적 조립으로 회피될 수 있다. 따라서 **인간 리뷰 게이트가 권위 있는(authoritative) 통제**로 유지되며, 스캔은 리뷰어 보조 신호로 위치한다 (REQ-MVP-027).

## E. 장애 모드 상태 설계 — REQ-MVP-030~032

| 상태 | 진입 조건 | 시스템 동작 |
|---|---|---|
| online | 하트비트/조회 정상 | 정상 실행 경로 |
| console-offline | 하트비트/조회 타임아웃 | UI 상태 표시 + 신규 실행 차단 |
| responder-degraded | responder 미응답 | 조회·회수 불능 보고 + 부수효과 명령 실행 미개시 |
| 실행 미확인 (명령 단위) | 송신 후 결과 확인 타임아웃 | "미확인" 보고 + 자동 재전송 금지 |

UDP는 무연결이므로 송신 유실과 피드백 유실은 관측상 동일 신호다 — 상태 설계는 이를 하나의 "미확인" 결과로 수렴시키고, 구분 시도 대신 재전송 금지(중복 실행 방지)를 우선한다.
