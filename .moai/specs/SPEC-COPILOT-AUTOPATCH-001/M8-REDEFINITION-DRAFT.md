## §1. 왜 재정의가 필요한가

**[round15 #5 현행화]** 아래 인용은 **구판(v0.1.4까지)** AC-AUTOPATCH-026이다. **현행(v0.1.5)은
이미 §2의 4관문 개정안으로 교체돼 있다** — `acceptance.md` AC-AUTOPATCH-026을 보라. 이전 판은
이 문장을 "현행"이라 적어, 반영이 끝난 뒤에도 읽는 사람에게 구판을 현행으로 오인시켰다.

> **When** 실기에서 대조→승인→드라이런→**실행**→검증을 왕복하면, the 시스템 **shall** 1회 통과한다.

이 문장은 **v0.1.2의 자동 실행 모델**을 전제했다. v0.1.3 amendment가 REQ-AUTOPATCH-018을
"서버가 실행한다"에서 "사람이 실행하고 서버가 검증한다"로 바꿨을 때 **AC-026은 함께 고쳐지지
않았다** — 그래서 그 판의 AC는 **서버가 하지 않기로 한 일**을 통과 조건으로 요구했다.

구체적으로 어긋났던 지점(왼쪽 열의 원문자는 **구판** 번호이며 현행 ①~⑦과 무관하다):

| 구판 AC-026 (v0.1.4) | 반자동 모델의 실제 | 현행 v0.1.5 대응 |
|---|---|---|
| "실행"이 왕복의 한 칸 | 서버는 실행하지 않는다. 사람이 콘솔에서 누른다 | G1·G2·G3·G4로 분리 |
| 시스템이 "1회 통과한다" | 통과 여부의 절반은 **사람의 조작**에 달려 있다 | 서버 책임 구간(G1·G3)만 통과 요구 |
| 구판 ③ 생성물 제거 확인 | 그대로 유효 | 현행 **④**(G4) |
| 구판 ④ 부분 성공을 통과로 적지 않는다 | 그대로 유효 | 현행 **⑤** |
| 구판 ① 종단 생성 요구 | — | **삭제 · 등가물 없음.** `acceptance.md` AC-026 아래 **고지 블록** 참조 |

**핵심**: 사람이 실행하는 단계가 들어오면 "시스템이 통과했다"와 "절차가 통과했다"가
갈라진다. 서버가 옳게 전달했는데 사람이 다른 걸 실행하면 그것은 서버의 실패가 아니고,
서버가 틀린 Lua를 냈는데 사람이 손으로 고쳐 성공시키면 그것은 서버의 성공이 아니다.
**둘을 분리해 기록하지 않으면 M8은 무엇을 증명했는지 말할 수 없는 세션이 된다.**

## §2. AC-026을 4단계 관문으로 쪼갠다 — **채택됨(v0.1.5)**

각 관문은 **책임 주체가 다르고 실패 모드가 다르다**. 하나로 묶으면 어디서 깨졌는지 알 수 없다.

```
G1 서버 전달   [서버 책임]  드라이런 → 승인 → 전달물(Lua + 절차)이 나온다
      ↓ 사람이 검토
G2 사람 실행   [사람 책임]  받은 Lua를 받은 절차대로 실행한다 — 손으로 고치지 않는다
      ↓
G3 서버 검증   [서버 책임]  재조회로 건별 확인 · 불일치 구조화 · 자동 보정 0
      ↓
G4 원복       [사람+기록]  생성물 제거 · 제거 확인 기록
```

### 채택된 AC-026 (v0.1.5 개정안 — **정본은 `acceptance.md`**)

**When** 실기에서 대조 → 승인 → 드라이런 → **사람 실행** → 검증을 왕복하면,
the 시스템 **shall** 서버 책임 구간(G1·G3)을 통과하고, 사람 실행 구간(G2)의 결과를
**있는 그대로** 기록한다.

- ① **G1** — 전달물이 나온다: 검토 가능한 `AddFixtures` Lua 전문 + 실행 절차 + 대상 표 +
  비가역 경고. 서버의 콘솔 쓰기 **0건**(세션 로그로 확인).
- ② **G2** — 사람이 **전달받은 것을 그대로** 실행한다. 손으로 수정했으면 **그 사실과 수정
  내용을 기록**한다 — 수정했다면 그 세션은 G1을 검증하지 못한 것이다.
- ③ **G3** — 승인 항목마다 관측 / 미관측 / 불일치 / 확인 불가 중 하나가 나온다.
  자동 보정·재시도 **0건**.
- ④ **G4** — 세션 전 쇼파일이 테스트용임을 사용자가 확인했고, 세션 후 생성물 제거를
  사용자가 확인했음이 `progress.md`에 기록된다.
- ⑤ **실패는 실패로 적는다.** 부분 성공을 통과로 적지 않는다. **어느 관문에서 깨졌는지**를
  명시한다 — "M8 실패"가 아니라 "G2에서 사람이 절차 3단계를 건너뛰어 실패" 형태로.
- ⑥ **[신설] G1이 통과하고 G2가 실패해도 그것은 SPEC의 유효한 결과다.** 이 빌드에서
  `AddFixtures`가 사람 실행으로도 실패할 가능성은 **열려 있다** — M0는 서버 실행 경로만
  10가지 반증했고, 사람 실행 경로는 **한 번도 시험된 적이 없다**. G2 실패는 REQ-AUTOPATCH-018을
  다시 열어야 한다는 신호다.
  **[round14 T12 축소 · round15 #5 현행화]** 초안의 "**코드 결함의 증거가 아니다**"는
  **폐기됐다** — 증거 종류를 선험적으로 배제해 ②·⑤와 충돌했기 때문이다. 서버가 틀린 모드
  핸들·FID·주소를 담은 Lua를 냈고 사람이 그대로 실행해 실패했다면 그것은 **코드 결함의 직접
  증거**다. 배제되는 것은 "전달물이 옳았는데도 실패했다"는 경우뿐이며, **그 판별은 AC-026①이
  보존한 전달물 원문과 G3 결과를 대조하는 5단계 절차**(`acceptance.md` AC-026⑥)로만 얻어진다.
  **기본 분류는 `판별 불가`이며, 절차를 밟지 않은 항목을 "코드 결함 아님"으로 적지 않는다.**
- ⑦ **[v0.1.5]** 표시 문자열 판별 실험(§4①)을 같은 세션에서 수행한다 — 현행 AC-026은
  ①~⑦ **7개 항목**이다(이 초안이 제안한 6개가 아니다).
- **[round15 #3] ①에 붙은 보존 의무**: G2 착수 **전에** `lua_source` 전문 · 사람에게 건넨 실행
  절차 전문 · 대상 표를 `progress.md` §E.2 M8 절에 **원문 그대로** 적는다. 사후 재생성본은
  보존본이 아니다. 이 보존이 없으면 ⑥의 판별이 성립하지 않아 그 세션은 `G1 미검증`이다.

㉡ 제거 불가면 M8 자체를 미완으로 둔다 · ㉢ P5(원복 절차 합의)를 세션 착수 **차단 조건**으로
승격해 "제거 불가"라는 상태가 아예 생기지 않게 한다.

**[round18 D-04 정정 · 결론] 이 셋은 미결이 아니다 — 2026-08-07 사용자가 ㉢을 택했다.**
위 열거는 **선택지와 그 전수성을 보존하기 위해** 남긴다(근거를 지우면 다음 담당자가 같은 것을
다시 묻는다). 귀결은 셋이다: ① `acceptance.md` **무개정**(AC 27 · AC-026 ①~⑦ 불변) —
㉢은 AC 본문을 고치는 안이 아니다 · ② 강제는 `plan.md` §B M8 착수 전제 **⑦**(본문 열거)에
있고 그 네 기재물은 위 결정 블록 P5 행 · `spec.md` §C P5 행과 **같은 넷**이다 ·
③ **[HARD] ㉢은 "제거 불가"를 배제하지 않는다** — 착수 게이트는 스냅샷이 **있음**만 보장하고
**로드 성공**은 보장하지 않는다. 제거 실패 시 **AC-026⑤대로 "G4에서 제거 수단 부재로 실패"**다
(정본 등기 `spec.md` §C 「사용자 결정 대기 → 결정 완료」).

**[round16 (c)] G4의 "제거 확인"이 미판독으로 끝나는 조건 둘.** 세션 후 제거를 확인하려면
`verify_patch`가 그 주소를 **미관측(`not_observed`)**으로 등급해야 하는데, 재조회가 불완전하면
그 등급이 나오지 않는다. `[코드]` 확인 결과 조건은 정확히 둘이다 —
`apply.console_read_caveat`가 `unread = inventory.missing_count + <PATCH_UNREAD로 분류된 주소 수>`
를 계산해 **`unread > 0`이면 `console_read_incomplete`**를 내고,
`tools.py`의 `read_complete = caveat is None or caveat["kind"] != CONSOLE_READ_INCOMPLETE`가
거짓이 되며, `verify_patch`가 *"재조회가 불완전해 그 주소의 상태를 단정할 수 없다 — 미관측이
아니다"*로 **`identity_unconfirmed`**를 낸다. 즉 **`inventory.missing_count > 0`**이거나
**주소 판독 실패(`unreadable_addresses`) > 0**이면 **G4의 관문이 닫히지 않는다.**
**단 열거 절단 자체(`index_domain_unknown`)는 막지 않는다** — 그 갈래는 `console_read_incomplete`가
아니라 `console_read_index_domain_unknown`(또는 미패치 갈래)을 내므로 `read_complete`는 참으로
남는다. 절단은 이 콘솔의 상시 상태이고 `childCount`가 진짜 총계라 수량 비교가 정확하기 때문이다
(§0 2d). 세션 당일 G4가 `identity_unconfirmed`로만 끝나면 **제거 확인은 미판독**이며,
그것을 "제거됨"으로 적지 마라.

## §4. 이 세션에서 함께 측정할 것 (권고)

라이브 세션은 비싸다. 종단 확인 외에 **미결로 남은 측정 2건**을 같은 세션에서 끝내기를 권고한다.

### ① 표시 문자열 판별 실험 — round11이 미결로 남긴 유일한 판단

콘솔 픽스처의 `FixtureType`은 `FixtureType 3` 형태로 오고, 코드는 그것을 라이브러리
**index**로 해석한다. 그런데 그 문법은 **표본 1종**(index 3, 표본 7건, 쇼파일 1개)에서만
관측됐고, `LibraryType.index`가 콘솔 표시 번호와 같은 도메인이라는 것은 **보인 적이 없다**.

**판별 실험**: 이름이 `FixtureType k`인 타입을 index `j ≠ k`에 놓고 그 타입의 픽스처를 읽는다.

```
기대 A (코드가 옳다)   : 표시가 `FixtureType j` -> 두 해석이 갈려 identity_unconfirmed
기대 B (코드가 틀렸다) : 표시가 `FixtureType k` 또는 이름 그대로 -> 편측 채택이 오답을 낸다
```

이 쇼파일에는 **이미 `FixtureType 2`라는 이름의 타입이 실재**한다(라이브러리 열거 3종 중
하나) — 판별 조건의 절반이 이미 갖춰져 있다. 결과에 따라:
- 기대 A → 현행 유지, `ASSUMPTION`으로 승격해 근거를 명시.
- 기대 B → **편측 채택을 제거**하고 타입 해석을 모드와 같은 양면 대조로 바꾼다.

### ② L2 — 패치 편집 세션 활성 상태에서의 실행 (선택)

§0의 마지막 미시험 항목. 긍정이면 REQ-AUTOPATCH-018을 v0.1.2 자동 실행 형태로 **복원 가능**
하다. 단 L6이 기대값을 크게 낮췄으므로 **부수적으로만** 시도한다 — 이것 때문에 G1~G4를
