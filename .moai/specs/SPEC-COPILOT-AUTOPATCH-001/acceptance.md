## §B. Given-When-Then 시나리오

**시나리오 1 — 정상 패치**: **Given** 1단계 대조가 수행되어 `missing_in_console` 3건이 나왔고 사용자가
빈 FID 범위를 주었을 때, **When** 3건을 승인하고 **전달받은 Lua를 사람이 콘솔에서 실행하면**,
**Then** 3대가 도면 주소에 도면 타입으로 생성되고 **서버의 검증 읽기가** 3건 모두를 확인한다.
(**[v0.1.3]** 승인과 생성 사이에 **사람의 실행 단계**가 들어간다 — 서버는 실행하지 않는다.)

**시나리오 2 — 드라이런**: **Given** 같은 상황에서, **When** 드라이런을 호출하면, **Then** Lua 소스와
대상 표가 나오고 **콘솔 쓰기는 0건**이다.

**시나리오 3 — FID 범위 미제공**: **Given** 사용자가 FID 범위를 주지 않았을 때, **When** 실행을
시도하면, **Then** 패치를 거부하고 무엇을 입력해야 하는지 안내한다.

**시나리오 4 — 라이브러리 부재**: **Given** 도면 타입이 콘솔 라이브러리에 없을 때, **When** 그 항목을
승인하면, **Then** 그 항목만 하드 스톱되고 GDTF 임포트 선행 필요를 사유로 보고한다.

**시나리오 5 — 주소 점유**: **Given** 도면 주소가 이미 콘솔에서 점유되어 있을 때, **When** 실행하면,
**Then** 그 항목을 제외하고 사유를 보고하며 **임의의 빈 주소로 옮기지 않는다**.

**시나리오 6 — 재실행**: **Given** 이미 패치한 승인 집합을, **When** 다시 실행하면, **Then** 중복을
만들지 않고 건너뛴 사실을 보고한다.

**시나리오 7 — 검증 불일치**: **Given** 사람이 실행한 뒤 검증 읽기에서 0건이 관측될 때,
**When** 결과를 보고하면, **Then** 성공으로 간주하지 않고 **실행 여부와 실행 절차를 재확인하도록
안내**한다. (**[v0.1.3]** "Patch 편집기를 먼저 열라"는 안내는 요구하지 않는다 — 그 원인 설명이
반증됐다. REQ-AUTOPATCH-024 · AC-AUTOPATCH-022③ 참조.)

**시나리오 8 — 미대조 리포트**: **Given** 1단계가 다중 시스템 미매핑으로 대조를 수행하지 않았을 때,
**When** 패치를 시도하면, **Then** 거부한다.

### AC-AUTOPATCH-026 — 라이브 종단 (M8) **[v0.1.5 재정의 — 사람 실행 단계 분리]**

**When** 실기에서 대조 → 승인 → 드라이런 → **사람 실행** → 검증을 왕복하면,

**있는 그대로** 기록한다.

> **왜 쪼개는가.** 이전 판은 "실행"을 왕복의 한 칸으로 두고 "시스템이 1회 통과한다"를
> 요구했다 — 그것은 **v0.1.2 자동 실행 모델의 문장**이며, v0.1.3이 REQ-AUTOPATCH-018을
> 반자동으로 조정했을 때 함께 고쳐지지 않았다. 사람이 실행하는 단계가 들어오면 **"시스템이
> 통과했다"와 "절차가 통과했다"가 갈라진다**: 서버가 옳게 전달했는데 사람이 다른 걸 실행하면
> 그것은 서버의 실패가 아니고, 서버가 틀린 Lua를 냈는데 사람이 손으로 고쳐 성공시키면
> 그것은 서버의 성공이 아니다. 관문을 나누지 않으면 M8은 **무엇을 증명했는지 말할 수 없는
> 세션**이 된다.

```
G1 서버 전달  [서버]  드라이런 → 승인 → 전달물(Lua + 절차)  → 콘솔 쓰기 0건
G2 사람 실행  [사람]  받은 것을 받은 절차대로 실행 — 손으로 고치지 않는다
G3 서버 검증  [서버]  재조회 건별 확인 · 불일치 구조화 · 자동 보정 0
G4 원복       [기록]  생성물 제거 + 제거 확인 기록
```

- 대상 요구사항: (통합)
- 검증 방법: 실기 onPC 2.4.2 라이브 세션 2. **테스트 쇼파일**에서만 수행.
- 기대 결과:
  - ① **G1** — 전달물이 나온다: 검토 가능한 `AddFixtures` Lua 전문 + 실행 절차 + 대상 표 +
       비가역 경고. **서버의 콘솔 쓰기 0건**이 세션 기록으로 확인된다.
  - ② **G2** — 사람이 **전달받은 것을 그대로** 실행한다. 손으로 수정했으면 **그 사실과 수정
       내용을 기록**한다 — 수정했다면 그 세션은 G1을 검증하지 못한 것이다.
  - ③ **G3** — 승인 항목마다 관측 / 미관측 / 불일치 / 확인 불가 중 하나가 나온다.
       자동 보정·재시도 **0건**.
  - ④ **G4** — 세션 전 쇼파일이 테스트용임을 사용자가 확인했고, 세션 후 생성물 제거를
       사용자가 확인했음이 `progress.md`에 기록된다.
  - ⑤ **실패는 실패로 적는다.** 부분 성공을 통과로 적지 않으며, **어느 관문에서 깨졌는지**를
       명시한다 — "M8 실패"가 아니라 "G2에서 절차 3단계를 건너뛰어 실패" 형태로.
  - ⑥ **G1이 통과하고 G2가 실패해도 그것은 이 SPEC의 유효한 결과다.** 이 빌드에서
       `AddFixtures`가 **사람 실행으로도** 실패할 가능성은 열려 있다 — M0는 **서버 실행 경로만**
       10가지 반증했고 사람 실행 경로는 **한 번도 시험된 적이 없다**. G2 실패는
       REQ-AUTOPATCH-018을 다시 열어야 한다는 **새 실측**이지 코드 결함의 증거가 아니다.
       (2026-08-06 사용자 승인.)
  - ⑦ **표시 문자열 판별 실험을 함께 수행한다.** 이름이 `FixtureType k`인 타입을 index `j ≠ k`에
       두고 그 픽스처를 읽어, 코드의 index 해석이 **거부되는지**(기대 A) **오답을 내는지**(기대 B)
       판정한다. round11이 미결로 남기고 round12가 재확인한 유일한 판단이며, 이 쇼파일에는
       `FixtureType 2`라는 이름의 타입이 **이미 실재**해 조건의 절반이 갖춰져 있다.
       기대 B면 타입 해석을 모드와 같은 **양면 대조**로 바꾼다.
