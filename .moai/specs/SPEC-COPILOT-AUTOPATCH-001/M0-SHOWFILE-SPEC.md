## §0. 먼저 — 이 문서의 과제 전제가 틀렸다 (정정 1건)

과제문은 *"`ASSUMPTION-71~75` 다섯 건이 미판정이고, 그것 때문에 M2·M3·M6 설계가 확정
불가능하다"*로 시작했다. **저장소는 그 반대를 적고 있다.**

| 과제 전제 | 저장소의 실제 기록 | 근거 |
|---|---|---|
| 71~75 **다섯 건 미판정** | **71~76 여섯 건 전부 판정 완료.** 프론트매터 `assumptions_open: 0` | `progress.md` 프론트매터 · `known_gaps` 첫 항목 `[CLOSED · M0 1~5차]` |
| M2·M3·M6 설계 확정 불가 | **M2·M3 확정 완료 · M6는 검증 읽기 유지.** M1~M7 **코드 마일스톤 전부 완료** | `progress.md` §E.2 M0 1차 「후속 마일스톤 확정 사항」 · §E.2 M2·M3·M6·M7 절 |
| 미판정 때문에 설계가 막혔다 | 막힌 것은 설계가 아니라 **`AddFixtures` 자체**다 — M0 최종 판정이 `NEGATIVE: AddFixtures 경로` | `progress.md` §E.2 M0 3차 「`NEGATIVE: AddFixtures 경로` — M0 최종 판정」 |

**현행 판정(재판정하지 않는다 — 인용만 한다)**:

```

GO(한정):      ASSUMPTION-72  드릴다운·모드명·핸들 해석 O / 점유폭 획득 X
INCONCLUSIVE:  ASSUMPTION-73  배열 의미론을 관측할 기회가 없었음
INCONCLUSIVE:  ASSUMPTION-74  생성 0건이라 관측 대상이 없었음
NEGATIVE:      ASSUMPTION-75  Patch 편집기 상태 감지 불가
NEGATIVE:      ASSUMPTION-76  서버 발화 플러그인이 patch 목적지를 갖지 않는다
```
`[실측]` `progress.md` §E.2 M0 3차 판정 블록 · §E.2 M0 5차 판정 블록 · `spec.md` §C ASSUMPTION-76 항.

**73·74가 INCONCLUSIVE인 이유는 측정 부족이 아니라 선행 조건 미성립이다** — 실행 경로 10가지 ·
인자 변형 8종 · 별도 생성 기법 1종에서 픽스처 생성 **0건**이라 관측 대상 자체가 없었다
`[실측]`(`progress.md` §E.2 M0 5차 계수 표). 그래서 v0.1.3 amendment가 **반자동 실행 모델**로
선회했다 — 서버는 실행하지 않고 사람이 플러그인을 실행하며 서버가 검증한다
`[문서]`(`progress.md` §E.2aa · `plan.md` §B M5).

**이 정정을 문서 맨 앞에 두는 이유.** 낡은 전제를 그대로 받아 "71~75를 재측정하는 절차"를 쓰면
이미 닫힌 것을 다시 재는 절차가 되고, 그것은 이 SPEC이 **열세 라운드** 동안 반복한 실패 유형 `[round23 갱신]`
(*"어떤 규율을 한 표면에 적용하고 형제 표면에는 적용하지 않는다"*)의 문서 버전이다.
과제문의 "이미 측정된 것을 다시 측정하는 절차를 넣지 마라"는 지시가 정확히 이 위험을 겨눴다.

**⇒ 부재는 ⑧까지 통과한 이름에만 말한다. 그 밖에는 미관측을 미관측이라 말한다.**
**§1.3의 잔여 셋과 같은 형태이므로 §5.2 단계 3의 읽기 1회(V-1·V-3)는 면제되지 않는다.**

> **[round22 R22-A·R22-C] 이 열거는 「못 찾는 경우」만 셌다 — 열한 번째는 「잘못 찾는 경우」다.**
> - **⑪ `[round22 R22-C]` 스윕이 요청 이름을 부분 포함하는 *다른 제품*에서 멈춘다.**
>   `rig.fuzzy_type_equal`이 **포함관계**로도 참을 내고 스윕 루프는 **첫 일치에서 `break`** 하므로,
>   `Robin MMX Spot 15k`(슬롯 2)가 `Robin MMX Spot`(슬롯 3, 정답)보다 먼저 오면 **정답 슬롯을
>   프로브하지 않은 채** `resolved` · `console_type='Robin MMX Spot 15k'` · `hard_stops=[]`를 낸다.
>   **①~⑩은 전부 fail-closed였다. ⑪만 fail-open이다** — 이 목록에서 성질이 다른 유일한 항목이다.
> - **⑨ 폐기 행은 「회수되지 않는다」보다 나쁘다** `[round22 R22-A]` — 스윕을 지나면 그 두 계수가
>   **0으로 리셋**되어 **폐기가 있었다는 사실 자체가 사라진다.** 위 ⑨ 문장은 *"회수되지 않고
>   계수로 남는다"*를 전제하는데 **그 전제가 스윕 경로에서 성립하지 않는다.**
>
> **⇒ 그러므로 「부재는 ⑧까지 통과한 이름에만 말한다」는 지금 불충분하다.** ⑪이 열려 있는 동안은
> **스윕이 「찾았다」고 말한 이름도 사람이 대조해야 한다.** 전문·귀속은 `progress.md` **§E.2ad**.

> **[round22 R22-A·R22-C·R22-E — HARD] 이 표의 「원래 근거는 소멸했다」와 「충족」이 뒤집혔다.**

> - **① 원래 근거가 되살아났다** `[round22 R22-A]`. 스윕 반환의 손열거 재구성이 폐기 축
>   두 필드(`unusable_row_count`·`unparsable_row_count`)를 지워 `enumeration_incomplete`가

>
> **[HARD] 세션 GO 조건 ①은 유지되고, ②는 완화 이전으로 되돌리며, ③은 미충족이다.**

## §3. 테스트 쇼파일 사양

### §3.1 셈 단위 정의 (먼저 정의한다 — 이 SPEC은 이것을 안 해서 세 라운드 연속 오보를 냈다)

**Group A = 15행 · Group B = 4행 · 표의 합 19행.** 단 **B04는 만들 수 없는 행**이므로
(§3.2 참조) **실제로 콘솔에 존재하게 되는 픽스처 대수는 Group A 15 + Group B 3 = 18**이고,
**본 실행 시점의 대수는 15**다. 세 수를 섞지 마라 — 표의 행 수 · 최종 대수 · 본 실행 시점 대수.
