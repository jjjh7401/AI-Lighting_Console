# SONGSTD-001 — 음악 파일 분석 실현 가능성 실측 (2026-08-14)

"코파일럿에 음악 파일을 넣고 분석해 조명연출"이 실제로 가능한지, SPEC 확정
전에 검증했다. 방법: 정답을 아는 합성 트랙(64s, **128 BPM**, 4/4, 구간
0/16/32/36s = quiet/mid/silence/loud, 킥=매박·스네어=후렴 2/4박)을 만들어
두 경로에 같은 문제를 풀게 함. 스크립트: /tmp/audio_feas (일회성 격리 venv —
프로젝트 의존성 미오염).

## 실측 결과

| 측정 | DSP (librosa 1.0.0) | LLM (gemini-2.5-flash, 오디오 파트) |
|---|---|---|
| BPM | **129.2 (오차 0.9%)** | **82 (오차 36%) — 실패** |
| 구간 경계 | 16/32/(35)/36s — 정답 일치 | 15.5/31.5/35.5s — 정답 일치 (±0.5s) |
| 에너지 등급 | quiet→D2, mid→D3, silence→0, loud→D5 전부 정확 | 후렴을 "mid"로 과소평가, 말미 silence 오검출 |
| 온셋(악센트 후보) | 257개 중 **100%** 비트 격자 정렬 | 미측정 (개별 히트 시각 질의는 신뢰 불가 판단) |

부수 실측:
- 64s WAV = 2.7MB 인라인 전송 성공 (Gemini 인라인 한도 20MB — 3~5분 곡도
  mp3면 여유; 초과 시 Files API). 기존 Vectorworks 업로드 경로(8MiB 캡)가
  재사용 가능한 패턴.
- 현 서버 Gemini 어댑터는 `Part.from_text` 전용(gemini_adapter.py:262-294)
  — 오디오는 같은 SDK의 `Part.from_bytes(mime_type='audio/wav')`로 전송
  가능함을 **같은 SDK·같은 키로 확인**. 배관 확장은 구조 변경 아님.
- librosa는 프로젝트 의존성에 없음(numpy도 없음) — F3 채택 시 의존성 추가
  결정 필요 (분석 전용 서브프로세스/도구로 격리하는 선택지 포함).

## 판정 — 하이브리드가 유일하게 정직한 아키텍처

1. **정량 사실(BPM·온셋·에너지 곡선·구간 경계)은 DSP가 담당.** LLM에게
   박자를 세게 하는 설계는 실측으로 기각(36% 오차는 §3 박 단위 시간 체계
   전체를 무너뜨림).
2. **의미 판단(장르·무드·컨셉 제안)은 LLM이 담당하되 카드 확인 필수** —
   표준 M3의 "분위기·컨셉은 자동화하지 않는다"가 실측으로도 지지됨
   (에너지 등급조차 과소평가함).
3. LLM의 구간 경계 청취력(±0.5s)은 DSP 경계 검출의 **교차 검증**용으로
   가치 있음 — 단독 근거로는 쓰지 않는다.

## SPEC 반영 사항

- F3(오디오 분석)은 실현 가능 — 단 "LLM이 음악을 분석"이 아니라
  **"DSP가 측정, LLM이 제안, 사람이 확정"** 3역 구조로 명세할 것.
- 분석 파이프라인: 업로드(기존 8MiB 패턴) → DSP(BPM/온셋/RMS→D 후보/경계)
  → [선택] LLM 교차 검증·무드 제안 → 질문 카드(구간표+D+장르 확인) →
  표준 엔진.
- 의존성 결정 필요: librosa+numpy를 서버에 넣을지, 분석기를 별도
  도구(tools/)로 격리할지 — 서버 기동 무게와 콘솔 안전 경계 고려.
