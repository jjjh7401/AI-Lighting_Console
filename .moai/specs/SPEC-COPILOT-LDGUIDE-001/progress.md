## §6-E. run M0가 찾은 §A.2 오측 — 감사 3회가 놓친 것

### §6-E.1 오측과 기전

```
초판 기재 :  17종 등장 / 16종 부재
실제      :  16종 등장 / 17종 부재      ← 서로 바뀌어 있었다
```

기전은 **단어 경계 없는 alternation grep**이다. 등록명 `preshow_check`가 가이드의
유령 이름 `run_preshow_check` **안에 부분 문자열로** 걸려 등장으로 계수됐다.

내가 직접 재측정한 값:

```
grep -c '\bpreshow_check\b' docs/user-guide.html   → 0    단독으로는 없다
grep -c 'run_preshow_check' docs/user-guide.html   → 1    유령 이름
grep -c 'preshow_check'     docs/user-guide.html   → 1    ← 유령 안에 매치된 오탐
```

### §6-E.2 왜 감사 3회가 못 잡았나

**감사도 같은 깨진 명령을 봤기 때문이다.** 1회차 감사는 §A.2에 대해 "개수 차이만으로
결함을 단정하지 말라"는 **추론 규율**은 지적했지만, **개수 자체가 틀렸다는 것**은 보지
못했다. 검사 대상과 검사 도구가 같은 결함(부분 문자열 매칭)을 공유하면 감사는 원리적으로
그것을 볼 수 없다.

이것이 §6-C.5가 말한 패턴의 **네 번째 기전**이다. 전체 목록은 §6-F로 옮겼다.

조치: `acceptance.md` §0에 **규약 6(식별자 대조는 단어 경계 또는 집합 연산으로, 부분
문자열 매칭 금지)** 신설. 동반 정정 — §A.2 목록에 `preshow_check` 추가, §D Q1,
`plan.md` 게이트 C·M0 3항, `acceptance.md` AC-009 기준값·§D.9 기대값(`>= 17`), §E E2.

plan 단계에서 "`pointing.py`는 있으나 도구로 노출됐는지 **미확인**"으로 남기고 M0 게이트

감사자가 세 번 다 "재지 않았다 — '조준 기능이 없다'고 읽지 말 것"이라 남긴 것과 같은 방향.

## §6-F. 헛도는 검사의 기전 목록 — 이 SPEC이 실제로 배운 것

같은 병이 **여섯 번**, 매번 다른 옷을 입고 나왔다. 이 목록이 이 SPEC의 가장 값진 산출물이다.

| # | 발견 시점 | 기전 | 방향 |
|---|---|---|---|
| 1 | 감사 1회차 | `grep -E`의 이스케이프된 파이프 `\|`가 선택이 아니라 문자 | fail-open (상시 0) |
| 2 | 감사 2회차 | 검사 대상 경로가 `.gitignore`에 있어 `git diff`에 원리적으로 안 나옴 | fail-open (상시 0) |

### §6-F.1 방향이 뒤집힌 것들 (6·7)

1~5는 전부 **"잡아야 하는데 못 잡음"** 이었다. 6과 7은 반대다 — **"통과해야 하는데 불가"**.
6은 run이 무엇을 하든 AC-013이 실패하는 상태였고, 7은 결함 없는 사실 서술을 지우라고
강제하는 검사였다. 헛도는 검사를 고칠 때 반대 방향으로 넘어가기 쉽다는 실증이다.

### §6-F.2 감사가 왜 못 잡았나 — 이유가 서로 다르다

- **1~5**: 감사도 **같은 깨진 명령을 봤다.** 검사 대상과 검사 도구가 결함을 공유하면
  감사는 원리적으로 그것을 볼 수 없다. 감사를 한 번 더 돌려도 안 잡힌다.
- **6**: **rebase가 감사보다 나중에 일어났다.** 시점이 원인인 결함이라 감사 회차를
  늘리는 것으로는 잡을 수 없었다. 기준점을 고정 SHA로 박는 습관 자체가 원인이다.
- **7**: 애초에 감사 대상이 아니었다 — 감사 종료 후 수정 과정에서 새로 생겼다.

### §6-F.3 결론

**남은 일은 규약을 더 만드는 것이 아니다.** 규약 5(뮤테이션 사전 검증)와 규약 6(단어 경계·
집합 연산)이 이미 있고, 적용된 자리에서는 새 결함이 나오지 않았다. 실패는 전부 **적용
범위**에서 났다. §G가 19/19로 닫힌 지금, 다음 위험은 "새 명령을 추가하면서 규약 5를
