## §6-D. Tier M REQ/AC 예산 초과 — 예외 승인 기록

**다음 세션이 "왜 이 SPEC만 예산을 넘겼나"를 재발굴하지 않도록 남긴다.**

      `grep -oE 'AC-LDG-[0-9]+' acceptance.md | sort -u | wc -l` → `19`

### §6-D.2 규칙이 SPEC보다 나중이다 — 기계 확인

`spec-workflow.md`의 REQ/AC 예산 절은 **`f30ab4c`(PR #45)** 가 들여왔다.

```

```

```
② plan-audit 3회  base 2092a42  — 규칙 없음 (감사가 이 항목을 채점한 적 없다)

```

**따라서 0.79라는 점수는 이 항목을 아예 채점하지 않은 값이다.** 감사 3회 중 어느 회차도
예산 초과를 지적하지 않았고, 지적할 수 없었다.

### §6-D.3 결정 — 현행 유지 (17/19 그대로 run 진입)

**두 축 모두 사용자 결정이다. 뒤집으려면 사용자에게 다시 물어야 한다.**

| 축 | 결정 | 라운드 위치 |
|---|---|---|
| **예산** (감축/승격/분할/현행유지) | **현행 유지 · 다음 SPEC부터 적용** | lead 세션의 별도 AskUserQuestion 라운드 — plan 세션이 올린 (a)(b)(c)에 lead가 (d) 현행 유지를 더한 4지선다에서 사용자가 (d) 선택 |

결정 근거(예산 축) — (a) 규칙 본문의 "예산을 완화하지 말라"는 **SPEC 작성자가 자기 편의로
상한을 늘리는 것**을 막는 조항이고, (b) 규칙에 소급 조항이 없으며, (c) Tier L 승격·감축·분할은
전부 이미 종료된 3회 감사의 전제를 되돌린다. 특히 Tier L 승격은 통과선을 0.80 → 0.85로
올려 승인된 PASS-WITH-DEBT의 전제를 깬다.

> **출처 표기**: 예산 축 라운드는 lead 세션에서 수행됐고 **이 세션은 그것을 직접 관측하지
> 못했다** — 위 귀속은 lead-tjueej의 보고에 근거한다. 이 세션이 처음 기록할 때는 "답을

> 관측하지 않은 것을 관측한 것처럼 적지 않기 위해 출처를 함께 남긴다.

### §6-D.4 이 예외는 규칙의 진단을 부정하지 않는다

규칙이 겨냥한 부담은 실재한다. **이 SPEC 자체가 그 실측 사례다** — 감사 3회를 쓰고도

**적용 범위: 이 SPEC 한 건에 한정한다. 다음 SPEC부터 16/16을 적용한다.**

사용자 결정이므로 **사용자에게 다시 물어야 한다.** lead나 후속 세션이 단독으로
