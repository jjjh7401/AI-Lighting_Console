## 3. 발견 결함

### P0 — 차단

#### D1. AC-005 · AC-012 정규식 파손 — 두 AC가 영구히 무효

`grep -E`에서 `\|`는 **선택(alternation)이 아니라 문자 그대로의 파이프**다.

- `acceptance.md` L41 (AC-LDG-005): `grep -cE 'SPEC-[A-Z]+\|server/\|\.py\b\|manager-\|\.moai/' $G`
- `acceptance.md` L48 (AC-LDG-012): `grep -cE '<script\|<link' $G`
- `plan.md` L115 (§C.2 기준선 측정): 같은 `<script\|<link` 패턴

이 패턴들은 문서 안에 `|` 문자가 낀 그 문자열이 통째로 있어야만 매치한다. 즉
**어떤 문서를 넣어도 0을 반환**한다. REQ-LDG-004(식별자 노출 금지)와
REQ-LDG-011(외부 의존 0)은 사실상 아무 강제력이 없다.

내가 실행한 대조:

```
$ grep -cE 'SPEC-[A-Z]+\|server/\|\.py\b\|manager-\|\.moai/' docs/user-guide.html
0                       # 적힌 그대로 — 종료코드 1
$ grep -cE 'SPEC-[A-Z]+|server/|\.py\b|manager-|\.moai/' docs/user-guide.html
0                       # 진짜 선택으로 고친 것 — 우연히 값은 같다
$ grep -cE '<script\|<link' docs/user-guide.html
0
$ grep -cE '<script|<link' docs/user-guide.html
0
$ grep -oE '<(script|link|style)[^>]*>' docs/user-guide.html | sort | uniq -c
   1 <style>
```

지금 값이 0인 것은 **맞다.** 하지만 그 0은 검증이 통과한 0이 아니라 명령이 아무것도
묻지 않아서 나온 0이다. `plan.md` §C.2의 "`<script>`/`<link>` 0" 기준선은 이 깨진
명령으로 측정된 값이므로 **귀속 불가**(verification-claim-integrity §2)다 —
참값이 0인 것은 내가 따로 재서 확인했다.

**조치:** 세 곳의 `\|`를 `|`로 고치고, `plan.md` §C.2 기준선을 고친 명령으로 재측정해
다시 기록한다. AC-005 패턴에는 REQ-004가 금지하는 "함수명"을 담을 항(예: `\b[a-z]+_[a-z_]+\(`)도
추가해야 조항 전체가 덮인다.

#### D2. 가이드에 실존하지 않는 도구 이름 3건 — SPEC의 결함 목록이 한 방향만 쟀다

`spec.md` §A.2는 **등록 도구 33종 → 가이드 등장 여부**만 셌다. 반대 방향
(가이드에 적힌 이름 → 실제 등록 여부)은 재지 않았다. 재보니 결함이 나온다:

| 가이드에 적힌 이름 | 위치 | 실제 |
|---|---|---|
| `run_preshow_check` | `docs/user-guide.html` L352 | 등록명은 `preshow_check`. `run_preshow_check`는 `server/` 어디에도 없다(내부 함수는 `run_preshow_checklist`) |
| `check_patch` | `docs/user-guide.html` L353 | 등록명은 `precheck_patch`. `check_patch`는 `precheck_patch`의 부분 문자열로만 등장 |
| `generate_groups` | `docs/user-guide.html` L355 | `grep -rn "generate_groups" server` → **출력 0줄.** 저장소 어디에도 없다 |

측정:

```
$ grep -rn "generate_groups" server | head
(출력 없음)
$ grep -rn "run_preshow_check" server | head
server/preshow/runner.py:57:def run_preshow_checklist(     # ← 다른 이름
...
```

이것은 §A.1이 지목한 "능력 주장 드리프트"와 **같은 종류의 결함**인데 SPEC의 결함
목록에 없다. 더 나쁜 것은 AC로도 안 걸린다: AC-006은 실존 33종 이름의 등장 위치만
보므로, `check_patch` 같은 유령 이름은 개정본 본문에 그대로 남아도 전 항목 그린이다.

**조치:** (1) `spec.md` §A에 네 번째 결함으로 실측 기재. (2) REQ 신설 —
"the 가이드 **shall not** 등록되지 않은 도구 식별자를 쓴다". (3) 역방향 AC 신설 —
가이드의 모든 `<code>` 스네이크케이스 토큰이 `TOOL_NAMES` ∪ 명시 허용목록에 속할 것.

#### D3. AC-014가 자기 모순 — 게이트 D의 NEGATIVE 분기가 REQ 위반으로 착지한다

`acceptance.md` L50 AC-LDG-014의 판정 기준은 한 칸 안에서 두 가지를 동시에 요구한다:

> "4건 전부 배치 **AND** 각 근거가 `$E`에 귀속. 근거 재확인 실패분은 본문에서 제외됐음(REQ-008)"

근거 재확인에 실패한 경고를 제외하면 배치된 것이 4건 미만이 되고, 그러면 첫 절
"4건 전부 배치"가 깨진다. `spec.md` REQ-LDG-013도 "**최소** 다음 4건을 다룬다"로
4건을 하한으로 못박았다. `plan.md` §A.4 게이트 D의 NEGATIVE 분기("확인 실패 → 그
경고는 싣지 않는다")를 타면 REQ-013 위반이 확정된다.

§D 엣지 E3이 "AC-014는 실은 것의 근거가 귀속됐는가로 판정"이라며 뒤집으려 하지만,
E3은 §D(엣지 케이스)에 있고 판정 기준은 §C(AC 표)에 있다. 다른 절의 서술이 AC 표를
무효화한다는 규정은 어디에도 없다. 감사 시점에 둘 중 무엇을 적용할지 결정 불가다.

**조치:** REQ-013을 "근거가 원장에 귀속된 위험은 해당 단계 절 안에 배치한다(후보 4건)"로,
AC-014를 "본문에 실린 안전 경고 전량이 지정 단계 안에 있고 각 근거가 `$E`에 귀속되어
있으며, 제외분은 `$E`에 제외 사유가 기재됨"으로 고친다. 그러면 GO/NEGATIVE 양쪽 모두
유효한 출력이 된다 — `plan.md`가 원래 의도한 대로.

### P1 — 통과 전 수정 필요

#### D4. REQ-LDG-005에 조동사가 없다 (MP-2 위반)

`spec.md` L103-105. `[Ubiquitous]` 라벨은 붙어 있으나 본문이 "…배제하고, …둔다"로

**조치:** "the 가이드 **shall** 도구 식별자를 본문에서 배제하고, 문서 말미의 참조 부록
한 곳에만 대조표로 둔다."

#### D5. REQ-LDG-007의 본체 의무에 대응 AC가 없다

REQ-007은 "가이드의 **모든 능력 주장**이 원장의 한 행에 대응한다"를 요구한다.
그런데 AC-008이 검사하는 것은 "도구 배정표 행 수 == 등록 도구 수(33)"뿐이다.
33행이 있다는 것과 본문의 각 주장이 어느 행에 대응하는지는 전혀 다른 명제다.
가이드에는 주장에 원장 행을 붙이는 장치(태그·각주·id)가 하나도 요구되지 않으므로,
"대응"은 원리적으로 아무도 확인할 수 없다. `acceptance.md` §B의 판독 기준도 행의
**형식**(명령 열·출력 열이 비었는가)만 보지 대응 관계는 보지 않는다.

**조치:** 능력 주장 문장에 원장 행 id를 달게 하고(예: `<span data-ev="E-17">`),
AC를 둘로 나눈다 — (a) 모든 `data-ev` 값이 `$E`의 실재 행으로 해석됨, (b) 능력 주장
문장 중 `data-ev` 없는 것 0건.

#### D6. AC-016은 검증 자체가 불가능하다

`acceptance.md` L52는 "`moai todo` 출력을 plan 세션 시작 시점과 대조"하라고 한다.
세 가지가 동시에 막는다:

1. **기준선이 없다.** `progress.md` §2의 증거 11행(E1~E11) 어디에도 plan 착수 시점의
   `moai todo` 출력이 없다. 대조할 상대가 존재하지 않는다.
2. **큐가 이 워크트리에 없다.** `moai todo --help`로 확인한 큐 경로는
   `.moai/state/kanban/backlog.json`인데, `ls .moai/state/kanban/` → `No such file or
   directory`. 이 워크트리에서 bare `moai todo`를 치면 plan 세션이 무엇을 했든 항상
   비어 나온다 → 상시 그린(공허한 통과).
3. **제3자가 큐를 바꾼다.** REQ-015 자체가 등록을 lead의 몫으로 넘긴다. 감사 시점에는
   lead가 이미 항목을 넣었을 수 있고, AC는 누가 넣었는지 구분할 수단이 없다.

**조치:** `moai todo` 대조를 버리고 산출물 쪽 음성 증거로 바꾼다 —
`git diff --name-only main...HEAD`에 kanban/backlog 경로가 없을 것(AC-013이 이미
사실상 덮는다). 굳이 남기려면 M0에서 큐 스냅샷 해시를 `$E`에 박아야 한다.

#### D7. AC-011은 자기 인증이다

"보존 대상 서술 목록(M1에서 확정, `$E`에 기재)의 각 항목이 개정본에 존재."
목록을 고르는 주체와 그 목록으로 채점받는 주체가 같은 run 단계 행위자다. 하한도,
선정 기준도, 최소 개수도 없다. **빈 목록을 고르면 통과한다.**

**조치:** 목록을 기계적으로 고정한다. 개정 전 파일의 `<h3>`는 실측 **25개**
(`grep -c '<h3' docs/user-guide.html` → `25`)이므로, "25개 각각에 keep/merge/drop
판정을 `$E`에 기록하고, keep 판정분 전량이 개정본에 존재"로 바꾸면 선정 재량이 사라진다.

#### D8. AC-006은 존재가 보장되지 않는 경계선에 의존한다

"도구 식별자 최초 등장 행 번호 ≥ **참조 부록 시작 행 번호**." 그런데 REQ-005도
`plan.md` M1도 그 부록에 고정 id나 고정 제목 문자열을 요구하지 않는다. 시작 행을
기계적으로 특정할 방법이 없으므로 AC는 실행 불가다.

**조치:** REQ-005에 `<h2 id="appendix-tools">` 같은 리터럴 마커를 명시하고, AC-006을
그 id 기준으로 다시 쓴다.

#### D9. "전 항목 기계 검증"은 사실이 아니다 — 명령 없는 AC 9건

`acceptance.md` §A.1은 "AC-LDG-001~017 전부 그린. **전 항목이 기계 검증**(grep / wc /
git diff)"이라고 선언한다. 실제로 실행 가능한 명령이 적힌 것은 AC-001·005·007·012·013
4건뿐이다(§C 표 기준 실행 가능 명령 5칸). AC-002·003·004·006·008·011·014·015·017은
서술만 있다.

추가로 AC-002의 "9단계 × 3부 = `<h3>` 27개"는 문서 전체 개수로 읽히는데, `plan.md`
M1은 도입부(3절)와 말미(설정·FAQ·부록)를 **보존해 옮기라**고 한다. 현재 파일의 `<h3>`가
이미 25개다. 보존분이 h3를 가지면 총계는 27을 넘고 AC-002는 구조가 옳아도 깨진다.

**조치:** 9건에 리터럴 명령을 붙이고, AC-002를 "각 단계 `<h2>` 구간 **내부**의 `<h3>` 3종"
으로 다시 쓴다(문서 전체 총계 아님).

#### D10. AC-004는 술어가 미정의이고 하한이 너무 낮다

### P2 — 개선 권고

#### D11. 증거 원장의 순환은 절반만 닫혔다 + §A.4와 §B.5가 서로 어긋난다

원장을 쓰는 주체와 그 원장으로 채점받는 주체가 같다. `acceptance.md` §B는 행의

도구 설명문도 증거가 아니다"로 문턱을 올린 것은 좋은 규율이지만, 대안으로 제시한

더 직접적인 문제: `spec.md` §B.5의 안전 경고 4건 중 **2건의 근거 칸이
"`compile_scene` 설명 원문" · "`apply_vectorworks_patch` 설명 원문"**이다.
`plan.md` §A.4가 증거가 아니라고 못박은 바로 그 부류다. 내가 `tools.py` L7631부터
`compile_scene`의 description을 읽어 확인했다 — 조용한 실패를 경고하는 문장은 실제로
거기 있다. 하지만 그것이 확인해 주는 것은 **설명문이 존재한다**는 사실이지
그 실패 양상이 실재한다는 사실이 아니다.

**조치:** (a) `$E`의 각 행의 명령이 그대로 재실행되어 기록된 출력을 재현할 것을 AC로
요구하고, sync 단계에서 표본(≥5행) 재실행을 의무화한다. (b) §A.4와 §B.5의 증거 등급
충돌을 명시적으로 해소한다 — 설명문 기반 2건을 "설명문 확인만 됨" 등급으로 강등하든지,
게이트 D에서 코드 경로로 승격하든지 택일.

#### D12. §A.1의 "차이 11"은 의미 있는 수가 아니다

`spec.md` §A.1은 "검증됨, 산술로 확정" 제목 아래 22 / 33 / 차이 11을 놓았다.
22와 33은 각각 참이지만(둘 다 재측정 확인), 11은 **두 주장 수의 뺄셈**이지 집합 차가
아니다. 실측하면:

- 가이드 표의 명시 행: 19행 + "+ 3개 내부 도구" 각주 = 주장 22
- 그 19행 중 실존 도구: **16** (유령 3건이 D2)
- 등록 33종 중 가이드에 없는 것: 17

즉 실제 격차는 17이고, 11은 어느 쪽도 가리키지 않는다. "확정"이라는 말이 붙은 표에
확정되지 않은 수가 섞여 있다.

**조치:** "가이드 주장 22 / 실제 등록 33 / 목록에 실린 실존 도구 16 / 목록 밖 실존 도구 17 /
실존하지 않는 이름 3"으로 다시 쓴다.

#### D13. 백분율 주장이 REQ-009·AC-010의 그물을 빠져나간다

REQ-009는 수치 주장을 "도구 수·이펙트 수·문서 종류 수"로 열거하고, AC-010은
`N가지`/`N종`/`N 이펙트` 패턴만 훑는다. 그런데 가이드에서 가장 근거가 약한 주장은
백분율이다:

```
$ grep -oE '커버리지[^<]*' docs/user-guide.html
커버리지 약 70% &mdash; 어휘, 초안, 공간 인식까지 구현
커버리지 약 78% &mdash; 실전 수준
$ grep -oE '[0-9]+%' docs/user-guide.html | sort | uniq -c
   2 100%   1 40%   3 50%   2 70%   1 78%
```

"커버리지 약 70%"는 무엇을 분모로 한 70%인지 문서 어디에도 없다. REQ-007의
"모든 능력 주장"에 문언상 걸리기는 하나 기계 검증에서는 전부 통과한다.

**조치:** REQ-009와 AC-010의 열거에 `%`를 넣거나, "근거 없는 커버리지 백분율 금지"
REQ를 따로 세운다.

#### D14. Out of Scope가 H2 단독 — 린트 `MissingExclusions` 위험

`spec.md` L157이 `## C. Out of Scope`(H2)다. 린트 규약은 `### <X.Y> Out of Scope`
형태의 H3 하위 절을 요구하며, H2 단독은 `MissingExclusions` ERROR를 낸다.
내용(5개 `-` 항목, 각각 구체적)은 충분하다 — 형식만 문제다.

**조치:** `### C.1 Out of Scope — 범위 제외`로 한 단계 내린다.

#### D15. ①②는 비어 있어도 통과한다

AC-003이 길이를 지키는 것은 **③(한계)뿐**이다. AC-002는 `<h3>` 3종의 존재와 순서만

**조치:** AC-003의 비어 있지 않음 검사를 3부 전체로 넓힌다.

#### D16. M0 종료 조건 자체를 검증하는 AC가 없다

`plan.md` L61-62의 M0 종료 조건은 4개 표(33행 배정표 · 수치 재측정표 · 16건 판정표 ·

## 4. 감사 항목별 응답 (지시받은 8개 축)

### ① 결함 주장 재측정 — 22와 33은 **둘 다 참**

```
$ grep -cE '^            name="[a-z_]+",$' server/orchestrator/tools.py
33
```

독립 2차 확인: `tools.py` L219의 `TOOL_NAMES` 튜플을 파싱하면 **33개, 중복 0**.
파일 전체의 `name="…"` 줄은 36개이나 3개는 다른 들여쓰기(L2717·L2896·L4800)의 중복
등장이고, 12칸 들여쓰기 스키마 블록(L6394~L8340)이 정확히 33개다. 서로 다른 두 방법이
같은 33을 낸다.

```
$ grep -n '22가지' docs/user-guide.html
345:<h3>22가지 AI 도구 전체 목록</h3>
```

표를 세어 보면 명시 19행 + "+ 3개 내부 도구" 각주 = 22. 주장 자체는 정확히 22다.
**→ §A.1의 두 수는 통과. 다만 "차이 11"의 해석은 D12, 목록의 유령 3건은 D2.**

### ② 미검증 절제가 지켜지는가 — **대체로 지켜진다, 두 곳 예외**

`spec.md` §A.2, `plan.md` 게이트 C, AC-009, §D 엣지 E2 — 네 곳 모두 16건을 미판정으로
다루고 "개수 차이만으로 단정하지 않는다"를 유지한다. 실제로 절제가 새는 REQ/AC/마일스톤은
찾지 못했다. 다만 두 군데가 절제 원칙과 어긋난다:

- §A.1 제목 "검증됨, 산술로 확정" 아래 확정되지 않은 수 11이 있다(D12).
- §B.5가 "설명 원문"을 근거로 쓰는데, §A.4는 설명문이 증거가 아니라고 못박았다(D11).

### ③ AC 공허성 — 요청받은 7건 전수 판정

| AC | 판정 | 요지 |
|---|---|---|
| AC-002 | **결함** | 실행 명령 없음. "27개" 총계 해석이 M1의 보존 지시와 충돌(현재 h3 25개). ①② 본문이 비어도 통과(D9·D15) |
| AC-004 | **결함** | "중복 문장" 술어 미정의, "최소 1회"라 9단계 중 1곳만 있어도 통과(D10) |
| AC-006 | **결함** | 부록 시작 행을 특정할 마커가 SPEC에 없음 → 실행 불가. 유령 식별자는 애초에 검사 범위 밖(D8·D2) |
| AC-011 | **결함** | 자기 인증. 보존 목록을 채점 대상 본인이 고르고 하한이 없음 → 빈 목록도 통과(D7) |
| AC-014 | **결함** | 자기 모순. "4건 전부" ∧ "실패분 제외"가 동시에 성립 불가(D3) |
| AC-016 | **결함** | 기준선 부재 + 큐 파일이 이 워크트리에 없음 + 제3자 변경 → 상시 그린(D6) |
| AC-005 | **결함** | 정규식 파손으로 항상 0(D1) |

### ④ REQ-004 vs REQ-005 정합 — **논리적으로는 양립, 경계가 정의되지 않아 강제 불가**

REQ-004는 닫힌 목록(SPEC ID / 내부 모듈 경로 / 소스 파일명 / 함수명)을 **본문**에서
금지하고, REQ-005는 도구 식별자를 **부록**으로 몬다. 부록이 본문의 부분집합이 아니라면
모순은 없다. 문제는 그다음이다:

- "본문"과 "부록"의 경계가 어디에도 정의되지 않았다(D8).
- AC-005의 명령은 `$G` **전체**를 훑는다. 부록까지 포함하므로, 패턴이 제대로
  고쳐지고 REQ-004의 "함수명" 항이 추가되는 순간 AC-005와 AC-006이 정면 충돌한다
  (도구 식별자 상당수가 파이썬 핸들러 함수명과 같은 문자열이다 — 예: `precheck_patch`).
- 지금은 AC-005 패턴에 함수명 항이 없어서 충돌이 드러나지 않을 뿐이고,
  그래서 REQ-004의 "함수명 금지" 조항은 **어떤 AC에도 덮이지 않는다.**

즉 두 REQ는 양립하지만 **AC-005/006이 의도한 경계를 강제하지 못한다.** D1·D8을 함께
고칠 때 AC-005의 적용 범위를 "부록 시작 행 이전"으로 한정해야 한다.

### ⑤ 증거 원장 순환성 — **문턱은 올렸으나 자기 인증은 닫히지 않았다**

주장과 증거를 같은 행위자가 쓴다. §B가 검사하는 것은 행의 형식이고, 재실행 요구도
제3자 확인 요구도 없다. §A.4의 "`ok:true`·설명문은 증거가 아니다"는 유의미한 상승
(단순 단언보다는 명백히 위)이지만 순환 자체는 남는다. §B.5가 설명문을 근거로 쓰는
모순까지 겹친다. **닫지 못한다** — 조치는 D11.

### ⑥ 카드 산출물 커버리지 — **누락 없음**

D21 참조. 두 산출물 모두 REQ로 덮이고, Out of Scope의 "발행 제외"는 근거를 밝힌
국소 결정이다. 부당 배제 아님.

### ⑦ 마일스톤 건전성 — **게이트 D만 결함, 나머지 3개는 건전**

- 게이트 A·B·C: GO/NEGATIVE 양쪽 모두 산출물이 정의돼 있고 어느 쪽도 정지하지 않는다.
  특히 A는 `spec.md` Q2가 "`server/spatial/pointing.py`는 존재하나 노출 여부 미확인"으로
  적절히 유보했다 — 내가 확인해 보니 `tools.py`에서 `pointing`은 산문 문자열 1회
  (L7976)로만 등장하고 임포트는 없다. 즉 게이트 A는 답할 수 있는 상태다(답은 M0의 몫).
- 게이트 D: NEGATIVE 분기가 REQ-013 위반으로 착지한다(D3).
- M0 종료 조건은 형식상 판정 가능하나, 그 조건 자체를 보는 AC가 절반뿐이다(D16).

### ⑧ Tier · 범위 — **Tier M 유지, PRESERVE는 보완, REQ-012는 강제 가능**

Tier M은 D20대로 방어 가능. PRESERVE 누락은 D18(실질 위험 낮음).
REQ-012의 파일 범위 제한은 AC-013으로 **강제된다** — 이 워크트리에서 직접 확인했다:
