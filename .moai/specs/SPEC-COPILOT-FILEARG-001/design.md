## 1. 우리는 다른 물음에 답하는 함수를 판별자로 썼다 — 관대함이 아니라 축이 다르다

v0.3.0은 VW 술어를 `has_address_family`에 위임했다. 그 함수가 답하는 물음은 **"이 바이트에서 패치를 뽑을 수 있는가"**(사용성)이고, 레지스트리가 묻는 물음은 **"이것은 무엇인가"**(신원)다. **축이 다르므로 술어는 양쪽으로 다 틀린다** — 단순히 너무 느슨한 것이 아니다.

| 파일 | 패치 가능? | 무엇인가? | `has_address_family` | 결과 |
|---|---|---|---|---|
| LX-SEQ 패치 CSV | 그래 보인다(9열 중 **7열이 VW 별칭으로 해소**된다) | **LX-SEQ** | **True** | **F2 — 남의 종류 파일을 자기 것이라 주장한다** |
| `vwx_worksheet_grid_from_screenshot.csv` | 아니다(주소 계열 열이 없다) | **Vectorworks** | **False** | 진짜 VW 파일을 **놓친다** |

LX-SEQ 시트가 VW export와 **우연히 닮은 것이 아니다** — 둘 다 픽스처·유니버스·주소·모드를 기술하므로 LX-SEQ는 VW **어휘의 부분집합**이다(`FID→fixture_id` · `FixtureType→instrument_type` · `Mode→mode` · `Ch→channel` · `Universe→universe` · `Address→absolute_address` · `Position→position`; LX-SEQ 고유는 `Group`·`AddrRange` **둘뿐**). 그러므로 **어떤 주소 계열 검사로도 둘을 가를 수 없다**. 근거와 측정 명령은 `research.md` §11이 소유한다.

**교정(결정 L)**: 술어를 신원 축으로 옮긴다.

```
patch        = 9열 서명 (불변)
vectorworks  = 신원( _best_header_candidate(rows)[0] >= 0 )
               AND NOT (레지스트리의 다른 행의 서명에 맞음)
사용성        = 판별에 쓰지 않는다 — 대상 툴이 판단한다
               (`not_patch_source`는 VW 대상으로 그대로 통과시킨다)
```

두 가지를 명시한다.

- **배제 절은 레지스트리를 참조하며 종류 이름을 열거하지 않는다.** 002/003/004가 행을 더해도 문면은 그대로다(O(1)). 실행은 O(N)이지만 그 비용은 REQ-FILEARG-002의 전수 계수가 **이미 치르고 있다** — **N² 증식은 없다**.
- **이것은 우선순위 순서가 아니다.** 술어들이 **서로 배타적**이 되는 것이며 순차 평가가 아니다. REQ-FILEARG-002(전체 훑기·계수)와 §F 속성 A는 **손대지 않는다**.

### 1.0 [HARD] 신원 축은 둘을 가르지 않는다 — 배제 절이 가른다 (M1 뮤테이션 ⑦ 실측)

§1은 "사용성 축은 양방향으로 틀린다"를 말한다. 그 교정으로 신원 축을 골랐지만, **신원 축이 `patch`와 `vectorworks`를 갈라 준 것은 아니다.** M1이 실측했다 — 뮤테이션 ⑦(배제 절 제거)이 `count == 2` → `ambiguous_sheet_kind`를 냈고, 그것이 뜻하는 바는 하나다:

> **LX-SEQ 패치 헤더는 원시 신원 술어를 만족한다**(`idx=0, score=7`). 신원 술어 단독으로는 `patch`와 `vectorworks`가 **갈리지 않는다**. 그 헤더를 `patch`에 붙들어 두는 것은 **오직 배제 절**이다.

당연한 결과다 — 신원 술어는 "헤더를 찾았는가"를 묻고 LX-SEQ 패치 CSV에는 헤더가 있다. 술어를 신원 축으로 옮긴 것은 **사용성 축이 내던 양방향 오류를 없앤 것**이지, 그 자체로 두 종류를 가른 것이 아니다. **가르는 일은 배제 절이 한다.**

**이 문장을 그대로 적어 두는 이유**: 같은 사실이 **"신원 축이 둘을 가른다"로 한 번만 잘못 읽히면 배제 절이 장식으로 보인다** — 그리고 그렇게 읽은 다음 사람은 배제 절을 지워도 안전하다고 생각한다. 배제 절은 장식이 아니라 **`ASSUMPTION-75-b`를 성립시키는 유일한 장치**이며, 뮤테이션 ⑦이 그것을 기계로 고정한다(`AC-FILEARG-025`).

### 1.1 같은 결함이 한 층 아래에서 되풀이됐다 — `대상` 열 (결정 M)

§1의 진단은 **"판별자 없이 한 자리에 두 가지"**다. 그 형태가 레지스트리 표 자체에서 한 번 더 나왔다.

| | 형태 | 두 가지 |
|---|---|---|
| `has_address_family` (v0.3.0까지) | **함수 하나**가 두 물음에 답한다 | 신원("무엇인가") · 사용성("패치를 뽑을 수 있는가") |
| `대상` 열 (v0.8.0까지) | **열 하나**가 두 종류를 담는다 | 등록된 툴 · 세션 메서드 |

실측이 그 둘을 갈랐다:

```
$ git show origin/main:server/orchestrator/tools.py | grep -c 'name="upload_vectorworks_export"'   → 0
$ git show origin/main:server/web/session.py       | grep -c 'def upload_vectorworks_export'       → 1
```

`patch`의 수신자는 **등록된 툴**, `vectorworks`의 수신자는 **세션 메서드**다. 판별자가 없으니 `AC-FILEARG-023`("등록 툴 집합에 없으면 후보에서 제외")을 문면대로 읽으면 **`vectorworks` 행이 매번 제외되고 결정 I가 무효**가 된다.

**교정도 같은 모양이다** — 앞의 것은 **축**을 갈랐고(결정 L: 신원과 사용성을 분리), 뒤의 것은 **태그**를 붙인다(결정 M: `(kind_tag, name)`). 열 이름은 `대상` → **`핸들러`**로 넓혔다. 열의 목적이 "누가 이 시트를 받는가"이고 툴도 세션 메서드도 받을 수 있으므로, 툴 전용으로 좁히는 것은 결정 I를 뒤집는 일이고 `vectorworks` 행만 이름으로 면제하는 것은 **002/003/004가 같은 물음에 부딪혔을 때 따를 규칙을 남기지 않는 일**이다.

**후속 SPEC에 대한 구속**: 002/003/004는 행을 더할 때 **자기 핸들러의 태그를 반드시 선언한다**. 선언하지 않은 행은 어느 레지스트리로 확인할지 정해지지 않아 `AC-FILEARG-023`이 검사할 수 없고, 검사할 수 없는 행은 등록으로 치지 않는다. 정본 표와 판정 규칙은 `spec.md` §G·§G.0이 소유한다.

## 2. 왜 좁은 쪽(신원)을 골랐는가 — 두 후보를 실측했다

느슨한 후보(`len(ReadResult.header) > 0`)와 좁은 후보(`_best_header_candidate >= 0`)는 **정확히 한 파일 부류에서 갈린다**(`research.md` §11).

- `vectorworks_export_instrument_data_no_header.txt` — 신원 술어 **False**(idx = -1), 느슨한 술어 **True**(header 비어 있지 않음, records 17, delimiter `\t`). `_process_rows`(`reader.py:253-266`)에 **균일폭 폴백**이 있어, 헤더 탐색이 실패해도 탭 구분 + 균일폭이면 `col_0..` 헤더를 지어내고 전 행을 데이터로 삼는다.
- 그 폴백에 **날조 대조군**을 쏘면: 장바구니 목록(`milk\t2\t3000\n…`)이 `header 비어 있음 = False · records = 3 · path_kind = A · failures = []`로 **Vectorworks가 된다**. 균일폭 폴백은 VW 어휘가 아니라 **모양**(탭 + 균일폭)으로 받으므로 `_MIN_HEADER_ALIAS_MATCHES`를 **통과하는 것이 아니라 우회한다**.

즉 좁은 후보는 진짜 VW 파일 하나를 떨어뜨리고, 느슨한 후보는 장바구니 목록을 받아들인다.

**무엇이 결정을 갈랐나 — 헤더 없는 VW 파일은 살아 있는 능력이 아니다.** `server/tests/fixtures/vwx/README.md:84-95`가 기록한다: 그 파일은 **오늘 패치를 만들어 내지 못하며**, 시스템의 올바른 답은 *"Export field names as first record"를 켜고 재수출하라*는 안내다. 장바구니 목록과 그 실물 VW 파일은 **바이트 동일한 `headerless_path_a_export` 판정**을 받는다(해소되는 열 0/28 · 0/3). 그러므로 좁히기는 **능력을 잃지 않는다 — 문구 하나를 잃을 뿐이다**. 그 문구는 `unknown_sheet_kind` 경로의 **조건부 힌트**로 복원한다(REQ-FILEARG-023).

**기각한 두 안.** (ㄱ) 느슨한 술어 유지 — 전제가 "장바구니 목록은 VW 안에서 안전하게 죽는다"였으나, **진짜 VW 파일도 같은 자리에서 같은 이유로 죽는다**. 둘 다 받아들여 얻는 것이 없고 판별만 뒤로 미룬다. (ㄷ) 운영자에게 두 종류 중 고르게 하기 — 입력이 **어느 쪽이든 쓸 수 없는** 상황에서 선택지를 내미는 것이다. 운영자에게 필요한 것은 메뉴가 아니라 재수출 지시다.

## 3. 앞선 네 결정은 이 교정에서도 전부 살아남는다

- **0건 → 거절**은 그대로 발화한다 — 헤더를 못 찾은 바이트(장바구니 목록 · 헤더 없는 VW 파일)는 어느 술어에도 맞지 않아 `unknown_sheet_kind`가 된다.
- **2건 이상 → 거절**도 그대로다. 배제 절은 술어를 **배타적으로** 만들 뿐 계수를 없애지 않으며, 계수 구조는 002가 행을 더할 때를 위해 그대로 남는다(§F 속성 A 불변).
- **파서·핸들러 0건**도 그대로다. 신원 술어는 `_best_header_candidate`를 **호출**할 뿐이고, 배제 절은 이미 표에 있는 서명을 재사용한다.
- **`.mvr` · `.xlsx`가 계속 동작한다.** 단, **그 분기는 `reader.py`에 없다**(F1) — 아래 §4가 소유한다.

## 4. 위임 계약 — 두 갈래 전역 함수 (F1 · D1)

**`.mvr`은 `_best_header_candidate`에 도달하지 못한다.** `PK` 매직이 `server/vwx/reader.py:360`에서 `_read_xlsx`로 라우팅하므로 `_process_rows`가 아예 호출되지 않는다. v0.4.0이 술어를 `_best_header_candidate(rows)[0] >= 0` 한 줄로 적은 것은 **`.mvr`에 대해 정의되지 않은 함수**였다 — 값이 없는 자리가 남아 있었다는 뜻이다.

**교정: 두 갈래 전역 함수.** 어떤 바이트가 들어와도 True/False 하나가 나온다.
```
vectorworks 술어
  ├ PK 매직(zip)
  │    ├ SCENE_ENTRY 있음  → .mvr   → 신원 True
  │    └ SCENE_ENTRY 없음  → .xlsx  → 신원 True     ← v1.0.0에서 채운 갈래(G-2)
  └ zip 아님 → _best_header_candidate(rows)[0] >= 0   (server/vwx/reader.py:158)

판정이 일어나는 곳: server/orchestrator/tools.py:2861   (핸들러 본문 안의 판정 줄)
상수를 가져오는 곳: server/vwx/mvr.py                    (SCENE_ENTRY의 정의 지점)
```

**zip 갈래가 둘 다 True인 이유(G-2).** **둘 다 Vectorworks가 내보낼 수 있는 형식**이다. 신원 술어가 묻는 것은 "이것은 무엇인가"이고, **그 zip이 `.mvr`인지 `.xlsx`인지는 신원이 아니라 다음 단계의 물음**이다. v0.9.0까지 zip 갈래에 `SCENE_ENTRY` 검사 하나만 있어서 **진짜 `.xlsx`가 신원 False로 떨어졌다** — `REQ-FILEARG-019`가 "`.xlsx`는 계속 동작한다"고 약속한 것과 정면으로 어긋난다. 채운 갈래는 아카이브가 **열리는지만** 묻고 곧장 반환한다(`zipfile.ZipFile`이 `BadZipFile`·`OSError`를 내면 False).

**[HARD] 바뀐 것과 바뀌지 않은 것을 갈라 적는다.** 이 재정이 뒤집은 것은 `.xlsx`의 신원 **한 칸**뿐이다.

| | 재정 전 | 재정 후 |
|---|---|---|
| `.mvr` 신원 | 참 | 참 |
| `.xlsx` 신원 | **거짓** → `unknown_sheet_kind` | **참** |
| 판독 불가 zip | 거짓 | 거짓 (경계를 넓히지 않았다) |
| 신원 단계에서 판독기 도달 | 안 함 | **안 함 — 그대로** |
| ④ `unapproved_dependency` 소관 | A의 결과표에 **미도달 칸**으로 남아 있었다 | **`SPEC-COPILOT-SHEETPIPE-001`(B) 소관으로 넘긴다** — `.xlsx`가 **뒷단 판독기**에 닿을 때 openpyxl 없는 환경에서 발생한다 |

**되살아난 것은 결과 ④가 아니라 그 앞의 도달성이다.** `.xlsx`가 `unknown_sheet_kind`로 떨어지지 않고 뒷단까지 가게 됐으므로 ④는 이제 **B에서** 관측될 수 있다.

**[HARD] 처분: ④를 A의 미도달 칸으로 두지 않고 B 소관으로 넘긴다.** A 안에서 영원히 도달할 수 없는 결과를 A의 결과표에 남겨 두면 다음 읽는 이가 **"언젠가 열리는 칸"**으로 읽는다. **거기서 안 나는 것이 아니라 거기 것이 아니다.** 그래서 아래 표의 ④ 자리에는 값 대신 **발생 지점**을 적어 넘긴다 — zip 갈래가 조기 반환하므로 판독기가 낼 수 있는 어떤 결과도 이 함수 안에서는 나오지 않고, `.xlsx`가 뒷단 판독기에 닿아 openpyxl이 없을 때 나며, 그 판정은 B의 몫이다.

> **[HARD] "신원이 참이 됐다"와 "그 뒤의 갈래가 실행된다"는 다른 문장이다 — 술어가 조기 반환하면 참이어도 뒤가 안 돈다.**
>
