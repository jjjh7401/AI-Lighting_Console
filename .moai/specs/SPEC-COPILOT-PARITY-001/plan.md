# SPEC-COPILOT-PARITY-001 — plan

> spec.md §A.4 **설계 결정 A(번역 지점)** 가 미결이다. 이 계획은 **A-1(판독 경계) 채택을 전제로 쓰되**, A-2가 선택될 경우 어느 항목이 어떻게 좁아지는지를 각 마일스톤에 함께 적는다. 결정은 Kickoff 승인의 몫이다(§E).

---

## A. 마일스톤

두 개다. 리드 배차의 M1/M2와 **경계가 다르다** — 배차의 M2(전수조사 방법 설계)는 실기가 필요해 이 SPEC 밖으로 밀고(§F 제안 1), 그 자리에 오프라인으로 끝나는 **번짐 범위 실측**을 넣었다. 근거는 spec.md §A.3이다.

### M1 — D2 정합 (오프라인 완결 · 콘솔 무접촉)

| 단계 | 하는 일 | 거는 REQ |
|---|---|---|
| M1-1 | `FakeConsole`에 핸들 갈래를 생성자 인자로 추가한다. 기본값은 현재 동작(이름). `FixtureTypes` 트리 열거는 이름을 유지한다 | REQ-PARITY-001 · 003 |
| M1-2 | 핸들 갈래를 켜고 `apply` → `preview` 를 돌려 **수정 전 기준선**을 관측한다. `fid_occupied`가 나와야 한다(RED) | REQ-PARITY-002 |
| M1-3 | 정방향(슬롯→이름) 번역을 넣는다. 대응표는 이미 수행되는 `FixtureTypes` 트리 판독에서 얻는다 | REQ-PARITY-004 · 006 · 007 |
| M1-4 | 번역 불가 경로를 설계대로 막는다 — 추측 금지, 원값 보존 + 미번역 표식 | REQ-PARITY-005 |
| M1-5 | M1-2의 테스트가 `already_patched`로 뒤집히는지 확인하고, 수정을 되돌리면 다시 빨개지는지 **뮤테이션으로 반증**한다 | REQ-PARITY-002 |
| M1-6 | 전체 스위트를 돌려 회귀 0을 확인한다. 기준선은 **이 배차에서 새로 잰다** | — |

[HARD] **M1-2는 M1-3보다 먼저다.** 순서가 뒤집히면 「빨개진 적 없는 테스트」가 남고, 그것이 바로 이 카드가 고치려는 결함의 모양이다(공허한 검사).

**A-2가 선택되면**: M1-3·M1-4의 대상이 `server/orchestrator/tools.py`의 `occupants` 구성 직전으로 좁아진다. M1-1·M1-2·M1-5·M1-6은 변동 없다.

### M2 — 번짐 범위 실측 (오프라인 · 분류만, 수정 아님)

| 단계 | 하는 일 | 거는 REQ |
|---|---|---|
| M2-1 | spec.md §A.3의 C2~C13 열두 자리 각각에 「핸들이 들어오면 어긋나는가」를 **측정**한다. 측정 수단은 자리마다 다르다 — 테스트를 쓸 수 있으면 테스트, 아니면 원문 인용 + 그 인용이 왜 결론을 정하는지 | REQ-PARITY-008 |
| M2-2 | 분류표를 `progress.md`에 남긴다. 각 행은 「측정됨/미측정」과 근거를 반드시 함께 적는다 | REQ-PARITY-009 |
| M2-3 | A-1을 채택했다면, 분류에서 **어긋남**으로 나온 자리가 판독 경계 수정으로 실제로 닫혔는지 확인한다. 닫히지 않은 자리는 후속 카드 재료로 넘긴다 | REQ-PARITY-008 |

[HARD] **M2는 C2~C13을 고치는 마일스톤이 아니다.** A-1이 구조적으로 함께 닫는 부분은 예외이되, 그 밖의 개별 수정은 이 카드의 범위가 아니다 — 범위를 넓히면 「작은 카드」라는 판단이 무너진다.

**A-2가 선택되면**: M2-3은 성립하지 않는다(판독 경계를 고치지 않으므로). 대신 M2-1의 분류 결과 전체가 후속 카드 재료가 된다.

## B. 종료 조건 — 무엇을 보면 끝난 것인가

각 마일스톤은 **관측된 증거**로만 닫힌다. 「했다」는 진술은 증거가 아니다.

| 마일스톤 | 닫히는 증거 |
|---|---|
| M1 | (a) 핸들 갈래를 켠 테스트가 수정 전 `fid_occupied`, 수정 후 `already_patched`를 낸 두 번의 실행 출력 (b) 수정을 되돌렸을 때 다시 빨개진 뮤테이션 출력 (c) 전체 스위트 출력 원문과 이 배차에서 새로 잰 기준선 |
| M2 | C2~C13 열두 행이 모두 채워진 분류표. 각 행에 「측정됨/미측정」과 근거가 붙어 있어야 한다 |

[HARD] **인용하는 수치에는 범위를 함께 적는다.** 좁은 선택자로 잰 값을 전체 스위트 값처럼 적으면 판정이 뒤집힌다.

## C. 순서와 의존

```
M1-1 (가짜 갈래)
  └─ M1-2 (RED 재현)        <- 반드시 M1-3 앞
       └─ M1-3 (정방향 번역)
            └─ M1-4 (번역 불가 경로)
                 └─ M1-5 (GREEN + 뮤테이션)
                      └─ M1-6 (전체 스위트)
                           └─ M2-1 → M2-2 → M2-3
```

M2는 M1 뒤다 — A-1을 채택하면 M2-3이 M1의 결과를 읽어야 하고, A-2를 채택하더라도 M1이 만든 핸들 갈래가 M2-1의 측정 수단이 되기 때문이다.

## E. Kickoff 승인에서 받아야 할 결정

**결정 A — 핸들→이름 번역을 어디서 하는가** (spec.md §A.4)

- **A-1 판독 경계**(`server/prechk/inventory.py`) — plan 레인 권고. C1~C13을 한 번에 닫는다. 공용 표면 변경과 트리 판독 1회 추가가 대가다.
- **A-2 툴 경계**(`server/orchestrator/tools.py`) — 리드 배차의 원안에 가장 가깝다. 파급 최소, C2~C13은 남는다.
- **A-3 비교 지점**(`server/lxseq/mapper.py`) — 매퍼가 콘솔 판독 개념을 새로 알게 되어 A-2보다 이점이 없다. 권고하지 않는다.

이 결정 하나로 M1-3·M1-4의 대상 파일과 M2-3의 성립 여부가 갈린다. **결정 전에는 run 진입하지 않는다.**

## F. 큐 제안 — 카드를 추가하지 않는다

리드 배차 ⑥에 따라 **제안까지만** 적는다. 큐 변경은 감독 몫이다.

### 제안 1 — 전수조사 방법 설계 (실기 필요, 일정 미정)

리드 배차의 원래 M2다. 「오프라인은 통과하는데 실기에서만 다르게 도는 자리」를 체계적으로 찾는 **방법을 설계**하는 일이다.

**별도 카드를 권고하는 이유**: onPC 실기가 필요하고 일정이 없다. 이 SPEC의 두 마일스톤은 콘솔 무접촉으로 완결되므로, 실기 대기 항목을 같은 카드에 두면 **닫을 수 있는 일이 닫을 수 없는 일에 묶인다.** t9에서 M4 라이브가 같은 이유로 카드 전체를 붙잡았다.

**그 카드가 받아 갈 재료**(이 SPEC이 남긴다): 괴리 3건의 목록(D1 절단 · D2 핸들 · RV1/RV2 폭 산정), 각 괴리가 오프라인에서 어떤 갈래로 가려졌는지, 그리고 `truncate_at`·핸들 갈래라는 두 선례의 모양.

### 제안 2 — 워크트리 기본 상태가 품질 게이트를 무력화한다

새 워크트리에는 `ui/node_modules`가 없어 pre-commit 품질 게이트가 `vitest: command not found`로 죽는다(run 레인 보고 · 이 세션 미재현). 「검사가 도는데 눈이 없다」는 이 SPEC의 주제와 계열이 같으나 **대상이 다르다** — 제품 코드가 아니라 개발 환경이다.

**범위에 넣지 않은 이유**: 이 SPEC의 REQ는 전부 제품 코드의 판독 충실도를 다룬다. 개발 환경 설정을 같은 카드에 섞으면 AC의 성격이 둘로 갈라지고, 어느 쪽 실패가 카드를 막는지 모호해진다.

## G. 하네스 마찰 — 이 세션이 실제로 겪은 것 (리드 보고용, SPEC 범위 아님)

plan 작성 중 도구 두 개가 이 워크트리에서 막혔다. 기록해 두지 않으면 다음 레인이 같은 자리에서 시간을 쓴다.

| 마찰 | 관측 | 우회 |
|---|---|---|
| `Write` 도구가 워크트리에 쓸 수 없다 | 절대경로·상대경로 모두 `Path traversal detected: file is outside project directory`. 같은 도구가 주 체크아웃 경로에는 「워크트리 사본을 고쳐라」라고 답한다 — 즉 워크트리를 알면서도 접근은 막는다 | 파일 작성을 `Bash`로 돌렸다 |
| `Bash` 가드가 마크다운 표를 담은 heredoc을 거부한다 | 표의 `|` 를 셸 파이프로 읽어 「too complex to verify」로 거부. 파이프가 없는 짧은 heredoc은 통과한다 | 인용부호로 감싼 `printf` 인자 방식으로 작성. 인용 안에서는 파이프가 통과한다 |

`Read`·`Grep`·`Glob`은 정상 동작했다. 막힌 것은 **쓰기 경로뿐**이다.
