## §A. 접근 요약 (Context)

본 절은 **변경 가능성이 높은 결정을 먼저** 배치한다(가장 되돌리기 어렵거나 후속 결정을 규정하는 순서). 빌드 순서(§B)와 다를 수 있다 — §A.2가 그 편차를 설명한다.

### §A.1 결정 검토 우선순위 (되돌리기 어려운 순 — 빌드 순서 아님)

### §A.2 빌드 순서 vs 리뷰 순서 — 그리고 M0가 필요한 이유 (v0.3.0 논거 정정)

본 SPEC은 데이터 계층부터 쌓는 순수-우선 구조라 빌드 순서가 결정 우선순위와 대체로 일치한다. 편차는 하나다: **M0(라이브 프로브)가 M1보다 앞선다.**

**v0.2.0의 논거는 과일반화였다.** v0.2.0은 "전제 검증이 그 전제에 의존하는 저작보다 먼저 와야 한다"를 네 프로브 항목 전부에 균일하게 적용했다. 실제로는 항목마다 **막는 대상이 다르고**, 그중 M1을 진짜로 막는 것은 하나뿐이다:

| 프로브 항목 | 진짜 차단 대상 | 왜 그 마일스톤인가 | M0에 있는 이유 |
|---|---|---|---|
| **ASSUMPTION-15** (빔 attribute 문자열) | **M1 (로더)** | 로더가 REQ-003 구간 3의 허용 목록을 검증하려면(REQ-005) 그 목록이 **비었는지 채워졌는지**를 먼저 알아야 한다 | **진짜 순서 제약** — 이것 하나가 프로브를 M1 앞으로 끌어온다 |
| **ASSUMPTION-14** (`Store Preset` 캡처) | **M4 (번들 빌더)** | 번들 형상(1회 캡처 + 풀별 Store vs 패밀리별 격리 사이클)이 여기서 갈린다 | 의도적 배칭 |
| **슬롯 탐색 실현성** | **M4 (번들 빌더)** | 런타임 빈 슬롯 탐색(결정 B)을 구현하는 곳 | 의도적 배칭 |
| **ASSUMPTION-13** (그룹 명명 관례) | **M3 (리졸버)** | 힌트 문자열을 소비하는 곳. 그나마 **차단이 아니라 튜닝 입력**이다 — 0건 매칭이어도 정직한 축소(REQ-009)로 M3은 성립한다 | 의도적 배칭 |

따라서 정확한 논거는 **"진짜 순서 제약 1건 + 의도적 배칭 3건"**이다. 배칭의 근거: 라이브 세션 1회의 실제 비용은 실물 콘솔·쇼파일 준비와 사람의 일정 확보이지 프로브 항목 하나를 더 발화하는 한계 비용이 아니다. ASSUMPTION-15 때문에 어차피 M1 앞에 세션이 서므로, M4·M3용 항목을 같은 세션에 묶는 것이 세션을 쪼개는 것보다 싸다.

**이것이 "라이브 세션 2회"에 대해 무엇을 뜻하는가 (사용자 확정 ⑧과의 관계).** 사용자는 "빔을 v1에 유지하면 세션이 2회가 된다"는 대가를 제시받고 유지를 택했다(spec.md §A). 그 거래를 정확히 적으면: **빔이 결정한 것은 프로브의 위치이지 세션의 개수가 아니다.** 빔을 뺐더라도 ASSUMPTION-14와 슬롯 탐색이 M4를 막으므로 M4 이전 프로브 세션은 여전히 필요했고, M7 종단과 합쳐 총 2회는 그대로였다 — 빔이 한 일은 그 프로브를 **M4 직전에서 M1 직전으로 앞당긴 것**이며, 그 대가로 저작 착수 전에 빔 어휘의 존부가 확정된다. 사용자 결정은 유효하고 그대로 유지되며, 여기서 바로잡는 것은 **그 결정에 붙어 있던 논거의 정밀도**다.

M0는 `SPEC-COPILOT-EXECBODY-001`의 M1 GO/DESCOPE 라이브 프로브 패턴(`SPEC-COPILOT-EXECBODY-001/acceptance.md:117-123` AC-EXECBODY-010)을 그대로 계승한다.

### §A.3 정직한 축소 원칙

역할 매핑이 특정 리그에서 전멸(전 역할 미매핑)하더라도 SPEC 실패가 아니다 — 명시적 미매핑 보고 + 폴백(룰북 무드 절)이 정직한 출력이다(REQ-LOOKLIB-009/017). EXECREF/EXECBODY의 "부분 성공을 성공으로 위장하지 않는다" 규율을 계승한다: M6 라이브에서 ASSUMPTION-13(명명 관례 실효성)이 부정으로 실측되면, 그 사실을 progress.md에 기록하고 매핑 휴리스틱 확장을 후속 항목으로 남긴다.

### §A.4 결정 현황 — **해소 11건 / 미해결 0건**

> **미해결 마커는 남아 있지 않다.** v0.1.0은 6건, v0.2.0은 3건이었고, v0.3.0에서 **0건**이 되었다. 폐쇄 경로는 세 갈래다 — **사용자 확정**(⑨ 역할 어휘, ⑩ 매핑 UX), **엔지니어링 판단**(H 다이내믹스 척도, I 프리셋 풀 범위 + 스킵 단위), **리포지토리/문서 증거**(A 저장 형식, E 매칭 표면 — v0.2.0에서 이미 폐쇄). 따라서 clarification 마커는 이 문서에 **0건**이며, §A.4b(미해결 결정 절)는 삭제되었다.
>
> **design.md와의 대응 관계 (최종).** v0.1.0의 "마커 6건 ↔ 슬롯 A~F 1:1" 주장은 거짓이었다(감사 D6a — ③④가 슬롯 C로 접히고, 슬롯 F는 대응 마커 없이 Kickoff 게이트를 통과). v0.2.0은 이를 "미해결 3건 ↔ 슬롯 R1/R2/R3 진짜 1:1"로 정정했다. **v0.3.0에서는 R1/R2/R3가 전부 해소되어 design.md §5.2가 해체되고 §5.1로 흡수되었다** — 이제 대응 관계는 **§A.4a 결정 11건 ↔ design.md §5.1 항목 11건**이며, 열린 슬롯은 양쪽 모두 0건이다.

##### §A.4a-H — 다이내믹스 척도가 사용자 질의 대상이 아닌 이유

이 항목은 v0.2.0에서 마커였으나 **물어보지 말았어야 할 질문**이었다. 두 선택지(`1..5` vs `0.0..1.0`)의 판단 근거가 전부 SPEC 내부에 있어 사용자가 SPEC보다 더 잘 답할 수 없다.

- **5단계인 근거**: (a) 장르당 6~10룩(사용자 확정 ②)을 5단계에 배분하면 단계당 1~2룩으로 자연스럽다 — 3단계면 단계당 2~3룩이 뭉치고, 7단계 이상이면 6룩 장르가 단계를 다 못 채워 AC-002의 스팬 조건이 빈 단계를 만든다. (b) 순서 있는 정수는 P1-1(섹션 에너지 → 룩 선택)이 가장 단순하게 소비할 수 있는 형상이다(research.md §10 (a)). (c) 양 끝점 이름표(잔잔함 / 클라이맥스)는 사용자 확정 ②의 표현을 그대로 쓴다.
- **실수 0.0~1.0 기각 근거**: 무단계 축은 REQ-005의 "범위 이탈" 검증을 `0.0 <= x <= 1.0`이라는 거의 항상 참인 조건으로 만들고, AC-002의 "최저·최고 각각 1개 포함" 판정에 **임의의 임계값을 새로 도입해야** 성립한다(예: "0.3 이하가 최저 구간"). 즉 실수 척도는 마커 하나를 없애고 **새 미해결 결정(임계값) 하나를 만든다.** 저작 시 값 선택 기준이 사라지는 것도 같은 문제다.
- **P1-1과의 관계**: P1-1이 연속 에너지 곡선을 다루더라도 정수 척도로의 양자화는 소비자 쪽 한 줄이며, 반대 방향(정수 계약을 실수로 확장)은 하위호환 확장이다 — 정수 시작이 안전하다.

##### §A.4a-I — 프리셋 풀 범위와 "N개 건너뜀"의 단위 (v0.3.0 신설)

**왜 이것이 결정이어야 했는가.** v0.2.0은 여섯 아티팩트 전부에서 프리셋 주소를 `Preset <pool>.<slot>`으로만 적고 `<pool>`을 끝내 정하지 않았다. 그런데 이 자리는 마커도 아니었다 — **묻지도 않고 정하지도 않은 채 남은 결정**이었고, 그 미결이 네 곳으로 번졌다: (a) 번들 형상(룩당 `Store` 몇 개 — REQ-011의 기계화 규율), (b) "N개 건너뜀"의 단위(REQ-013 (c), AC-018 (c)), (c) ASSUMPTION-14가 "풀 타입별로" 실측한다고 적었으나 **in-scope 풀 타입이 정의되지 않아 실측 대상이 없던 문제**, (d) AC-018 (a)의 보고 형상.

**증거.** 프리셋은 **속성 패밀리별 풀**로 조직되고 `Preset <pool>.<slot>`으로 주소지정된다 — `10_object_model.md:18-20`("organized in pools by attribute family: Dimmer, Position, Gobo, Color, Beam, Focus, Control, Shapers, Video, All" / "Addressed as `Preset <pool>.<slot>` (e.g. `Preset 4.1` = Color pool slot 1)"), `00_grammar.md:18`(`Preset 4.1` = pool 4 "Color", slot 1), 저장 레시피 `00_grammar.md:67-68`. 패밀리 경계는 `10_object_model.md:38-40`이 정의한다 — **Beam = iris/prism/frost, Focus = zoom/focus**(v0.1.0이 zoom을 Beam으로 묶은 오류의 정정 근거이기도 하다).

**결정.**

1. **in-scope 풀 = Dimmer + Color** (무조건), **+ Beam / Focus** (ASSUMPTION-15 GO 시, 수용된 문자열의 패밀리에 따라 라우팅).
2. **Position 풀 제외** — 정적 pan/tilt가 금지되어(사용자 확정 ①, REQ-009) 담을 값이 없다. **All 풀 제외** — 무차별 캡처라 ASSUMPTION-14의 패밀리별 검증을 불가능하게 만들고 per-show 포지션 값의 유입 경로가 된다. Gobo·Control·Shapers·Video는 매핑되는 v1 룩 속성이 없다.
3. **번들 형상** = 룩 1개당 **in-scope 풀 타입 중 값이 있는 것마다 `Store Preset <pool>.<slot>` + `Label` 1쌍**. 기본 2쌍, 최대 4쌍. 역할×풀로 쪼개지 않는다 — 6역할 × 2풀 = 룩당 12프리셋이 되어 슬롯 탐색·충돌 보고가 무의미해진다.
4. **풀 번호 하드코딩 금지** — `Preset 4.1 = Color`는 룰북의 **예시 산문**이지 이 쇼파일의 계약이 아니다. 풀 타입 → 실번호 해석은 런타임 preset_pools 드릴다운이 답하며, 이 데이터는 이미 **풀 TYPE을 실번호 `no`와 함께** 노출한다(`server/orchestrator/tools.py:39-44` "preset_pools - the preset TYPES (Dimmer, Position, Gobo, Color, ...)", `:81` 드릴다운 기본값, `:185-190` 실번호 키잉). 근거: `tools.py:53-55` "Guessed paths are how ... shipped dead".
5. **"N개 건너뜀"의 단위 = 건너뛴 프리셋 저장 1회** (룩이 아니다). 두 근거: (a) REQ-013 (c)가 이미 "건너뛴 항목 수와 **그 슬롯**"을 요구하는데 **슬롯을 갖는 것은 룩이 아니라 프리셋**이므로 요구 문언 자체가 프리셋 단위를 함의한다. (b) 룩 단위로 세면 부분 충돌(Color 슬롯은 비었는데 Dimmer 슬롯이 점유)이 표현 불가능해져 룩 전체를 버리거나 0건으로 보고하게 되며, 둘 다 "부분 성공을 전체 성공으로 위장하지 않는다"에 반한다.
6. **건너뜀 사유 2종을 항목별로 구분**: `conflict`(같은 룩 이름의 프리셋이 이미 존재하거나 대상 슬롯 점유 — 재인스턴스화 시 주 경로) / `no_free_slot`(드릴다운 상한 안에서 빈 슬롯 미관측 — `drilldown_capped`와 함께 보고). N은 둘의 합이되 사유는 잃지 않는다. 관측 범위 밖의 슬롯을 "비었을 것"으로 가정해 발화하지 않는다(그룹 발명 금지와 같은 규율).

**남은 사용자 대면 여지 — 없음.** 풀 번호는 런타임 해석이라 물을 것이 없고, 풀 타입 배제 근거는 전부 SPEC 내부 제약(사용자 확정 ①, ASSUMPTION-14의 검증 가능성, REQ-004)에서 나온다. **M0가 확인하는 것은 결정이 아니라 실현성**이다 — preset_pools 드릴다운이 반환하는 풀 이름이 Dimmer / Color 패밀리로 해석 가능한지(§B M0 슬롯 탐색 항목에 추가).

##### §A.4a-J — 역할 어휘 6종 + **6종 전부**의 힌트 문자열 (사용자 확정 ⑨)

**확정 내용**: `백라이트`(back/backlight) · `프론트`(front/FOH) · `사이드`(side) · `탑`(top/downlight) · `배경`(cyc/backdrop, 샤막 포함) · `스페셜`(special/key). **힌트 문자열 표의 정본은 spec.md §A**이며 6종 전부가 힌트를 갖는다.

- **왜 6종 전부에 힌트가 필요한가**: 힌트 문자열은 ASSUMPTION-13이 실측하는 대상 그 자체이며 매핑 성패를 결정하는 기제다. v0.2.0은 백라이트 하나에만 예시 힌트를 달았는데, **그 상태의 "제안 기본값"은 그대로 채택될 수 없다** — 나머지 다섯 역할은 매핑 규칙이 없어 M0에서 실측할 대상조차 없다. 그대로 수락할 수 없는 기본값은 해소된 결정이 아니다.
- **6종인 근거**: (a) 너무 넓으면 미매핑률이 올라 정직한 축소가 상시 발동해 기능이 무력해지고, 너무 좁으면 4장르 24~40룩의 표현력이 준다. (b) 6종은 `20_korean_terms.md`의 showfile 행 7종과 같은 자릿수로, 명명 관례 스타일(REQ-006)의 무게감이 일치한다. (c) 각 역할이 **소규모 리그에서도 그룹 하나로 존재할 개연성**이 있는 굵은 구분이다 — 세분화(`사이드-상수` vs `사이드-하수`)는 매핑 실패를 구조적으로 늘린다.
- **힌트 설계 규율**(상세는 spec.md §A): 픽스처 타입 클래스 어휘(`워시`/`스팟`/`빔`)를 힌트에서 **의도적으로 배제** — D3 교훈의 기계적 형태다. 토큰 경계 매칭 + 약어는 정확 토큰 일치, **둘 이상 역할에 걸리면 `ambiguous` 미매핑**(REQ-009). 알려진 충돌 위험(`Key`/`Keys` — 밴드 쇼파일의 키보드 그룹, `SP`/`Spot`)은 제거되지 않고 규율로 관리되며 그대로 기록된다.
- **집합은 시작점이다**: M0의 ASSUMPTION-13 결과로 **힌트 문자열은 조정될 수 있다**(집합 자체의 변경은 M1 착수 전까지만). 조정 여부·근거는 progress.md §E.2에 기록한다. 부정 실측이어도 실패 방향은 안전하다(REQ-009 명시 미매핑).

##### §A.4a-K — 역할 매핑 확정 UX (사용자 확정 ⑩)

**확정 내용**: 자동 휴리스틱 + 적용 전 요약 보고. 별도의 "이 매핑으로 진행할까요" 확인 왕복을 넣지 않는다.

- **사용자에게 제시된 근거**: 최종 방어가 **세 겹으로 이미 존재**한다 — (i) `gate.screen()` 3-스테이지(`server/safety/gate.py:260-265`), (ii) 위험 시 deny-all 승인 카드(`server/safety/gate.py:17`), (iii) **스크리닝을 감싸는 실행 프리뷰**(`server/web/session.py:161-165`)가 대상·경고를 콘솔 송신 전에 표시한다. 네 번째 왕복의 한계 효용이 낮다. 제약 축은 "AI는 초안, 사람이 확정"(product.md §6) vs 지시→실행 왕복 <10초(product.md:37).
- **반대 논거는 기각되지 않았다 — 수용된 위험으로 존치한다**: 프리뷰는 **커맨드**를 보여주지 역할→그룹 **매핑 의도**를 설명하지 않는다. `Group 11`이 사용자가 생각한 백라이트인지는 프리뷰만으로 판단하기 어렵고, 오매핑의 결과는 쇼파일에 남는 비가역 프리셋이다(design.md §4 위험 #1 — 본 SPEC의 유일한 실질 신규 노출면). 이 논거는 사용자에게 제시되었고 사용자는 알고도 이 쪽을 택했다. 따라서 위험 #1은 **제거된 위험이 아니라 표면화된 뒤 수용된 위험**이며 design.md §4에 그렇게 기록된다.
- **추가 왕복 없이 가능한 완화**: 요약 보고가 역할→그룹 바인딩을 **그룹 이름과 함께** 보여주면(REQ-013 (a)(b)) 사용자가 사후에라도 오매핑을 알아챌 수 있다 — `Group 11`이 아니라 `Group 11 'Front Truss' ← 백라이트` 형태. 확인 단계 추가가 아니라 기존 보고의 정보 밀도를 높이는 것이므로 확정 ⑩과 충돌하지 않는다.

- **ASSUMPTION-15 (빔 attribute 문자열) — 차단: M1(로더)**: 후보 문자열 `Attribute 'Zoom'` / `'Focus'` / `'Iris'` / `'Frost'` / `'Prism1'` / `'Shutter'`를 실물 콘솔에 발화하고 수용 여부·값 범위를 관측. 판정: **GO**(≥1개 수용 → 해당 문자열만 REQ-003 구간 3에 진입하며, 패밀리에 따라 **Beam 풀 / Focus 풀**로 라우팅 — 결정 I) / **DESCOPE**(0개 수용 → REQ-001 빔 게이트 발동: 스키마 필드는 정의하되 v1 라이브러리 미사용, in-scope 풀은 Dimmer·Color 2종에 그침).
- **ASSUMPTION-14 (`Store Preset` 캡처 의미론) — 차단: M4(번들 빌더)**: 컬러 값만 활성인 프로그래머에서 `Store Preset <Color 풀>.<slot>` → `Label` 후, 저장된 프리셋이 **Color 패밀리 값만** 담았는지 확인(반대 방향도 1회: Dimmer 값만 활성 → Dimmer 풀 저장). in-scope 풀 타입이 결정 I로 확정되었으므로 이제 "풀 타입별로"가 실제 실측 대상을 갖는다. **판정은 3분기이며 어느 분기가 발동했는지 progress.md §E.2에 명시 기록한다** (spec.md §C ASSUMPTION-14가 정본):
  - **GO** — 패밀리 스코프 캡처 확인. 번들 = 룩당 1회 캡처 + 풀 타입별 `Store`.
  - **FALLBACK (번들 형상 게이트)** — 과캡처 관측(Color만 활성인데 다른 패밀리 값까지 담김). 번들이 **패밀리별 격리 캡처 사이클**로 분해된다: 패밀리마다 `ClearAll` → 선택 → 그 패밀리 값만 → `Store` → `Label` → `ClearAll`. 프리셋 개수·슬롯 정책 불변, 커맨드 수만 증가. 라이브러리 재저작은 없다 — REQ-001의 **패밀리 분할 가능성 스키마 규칙**이 이 분기를 흡수한다.
  - **HALT** — `Store Preset` 자체가 성립하지 않음(저장 실패 / 빈 프리셋). 프리셋이 v1의 유일한 산출물이므로 M4/M7이 성립하지 않는다. **run-phase를 진행하지 않고 오케스트레이터에 블로커 보고를 반환**하고 산출물 축 재설계 여부를 사용자 결정에 부친다. 조용히 GO로 처리하는 것은 금지.
- **ASSUMPTION-13 (그룹 명명 관례 실효성) — 차단: M3(리졸버), 그나마 튜닝 입력**: 실물 리그의 groups 목록(`get_rig_context`)을 판독해, **결정 J의 6종 역할 힌트 문자열**(정본: spec.md §A 표)이 실제 그룹명과 얼마나 매칭되는지 실측. 기록 항목: (a) 역할별 매칭 여부, (b) **모호 매칭**(둘 이상 역할 힌트에 걸린 그룹 이름) 목록 — 힌트 충돌 규율의 실측 근거, (c) 어떤 힌트 문자열도 걸리지 않은 그룹 이름 목록 — 힌트 확장 후보. 판정: 매칭 역할 수를 기록(0이어도 DESCOPE가 아니라 **힌트 문자열 조정 입력**).
- **슬롯 탐색 실현성 + 풀 타입 해석 (결정 I·B의 실현성) — 차단: M4(번들 빌더)**: preset_pools 드릴다운으로 (a) 반환된 **풀 이름이 Dimmer / Color 패밀리로 해석 가능한지**(결정 I 4항 — 풀 번호를 하드코딩하지 않고 런타임에 타입을 해석할 수 있는가), (b) 각 풀의 점유 슬롯을 읽어 쿼리 상한 16(`tools.py:88`) 안에서 빈 슬롯을 판별할 수 있는지를 관측. `drilldown_capped` 발생 여부 기록. **(a)가 부정이면** 풀 타입 해석 방식이 재설계 대상이 되며(예: 사용자에게 풀 번호를 묻는 표면 추가 — 현재 §D 범위 밖), 그 사실을 블로커로 보고한다.
- **산출물**: progress.md §E.2에 판정 4건 + 실측 원문(콘솔 응답·감사 로그·GUI 스크린샷)을 **각주가 아니라 명시적 섹션으로** 기록(EXECBODY-001 **AC-EXECBODY-010**의 GO/DESCOPE 조건부 인수 형식 계승 — `SPEC-COPILOT-EXECBODY-001/acceptance.md:117-123`. v0.2.0이 인용한 `AC-EXECBODY-013`은 "`Go+ Page N.M` 구문 계속 보류(regression)"로 이 형식과 무관한 AC였다). 부정 실측도 유효한 완료 상태다(§A.3).

### 라이브 세션 회계 (감사 D9)

v0.1.0은 "라이브 검증은 정확히 1 AC"(design.md §6.5)를 설계 성질로 주장했다. M0 신설로 이 성질은 **바뀐다** — 숨기지 않고 명시한다:

| | 세션 | AC | 무엇을 측정하는가 | 왜 합칠 수 없는가 |
|---|---|---|---|
| 1 | **M0 프로브** | AC-LOOKLIB-020 | ASSUMPTION-13/14/15 + 슬롯 탐색 실현성 | **M1 저작 전**에 답이 필요하다 |
| 2 | **M7 종단** | AC-LOOKLIB-014 | 매칭→매핑→인스턴스화→게이트 종단 통합 | **M6 완료 후**에만 존재한다 |

**라이브 세션 수 = 2.** 두 세션은 시간축의 양 끝(저작 전 / 통합 후)에 있어 물리적으로 병합 불가능하다. 이는 프로젝트 관례("라이브 검증 마일스톤 1개")로부터의 의식적 이탈이며, 그 대가로 "전제 미검증 상태에서 24~40룩을 저작하고 마지막에 무너지는" 위험을 제거한다. M0는 코드 변경 0인 측정 세션이라 준비 비용이 M7보다 낮다.

## §C. 기술 제약

1. **신규 런타임 의존성 0.** 기존 stdlib + PyYAML(기존 의존) + 기존 Python 스택만.
2. **@MX:ANCHOR 경계 (위반 불가)**: `server/safety/gate.py:260-265`(스크리닝 경로 하나), `server/safety/classify.py:169`(분류 의미론 하나), `server/rulebook/assembly.py:69-72`(프리픽스 조립 하나).
3. **fail-safe는 협상 대상이 아니다.** 미매핑·충돌·리그 불능의 실패 방향은 항상 축소/보류이지 추측 보완이 아니다.
4. **per-show 값의 정적 데이터 진입 금지**(REQ-004/022) — 룩 자산과 룰북 어디에도 구체 그룹/슬롯/FID 없음.

## §G. Phase 4 Mode Selection — 사전 평가 (오케스트레이터 확정용 권고)

> 구속력 있는 기록은 `progress.md` §F이며 오케스트레이터 소유다(첫 run-phase `Agent()` 스폰 전 작성). 본 절은 plan-phase 권고이며 오케스트레이터가 확정·기각한다.

### 입력 파라미터

- **tier**: L (5-artifact 세트 + progress.md)
- **scope (file count)**: 예상 14~20 파일(신규 looks 패키지 6~8 + YAML 자산 4 + 테스트 5 + 배선 2~3 + 룰북 안내 축 1)
- **domain count**: 2 (Python 서버 도메인 + 룩/연출 데이터 도메인) — 콘솔 Lua·UI 무변경으로 도메인 확장 없음
- **file language mix**: Python + 정적 데이터(YAML) + markdown. 코딩 중심
- **concurrency benefit**: **LOW** — M0가 M1을, M1 스키마가 M2~M5 전부를 규정하는 순차 의존(프로브 → 스키마 → 라이브러리 → 리졸버 → 빌더 → 매칭)
- **Agent Teams prereqs**: 해당 없음 (Mode 3 RETIRED)

### 모드 평가

| # | 모드 | 선택 | 근거 |
|---|---|---|---|
| 1 | trivial | 미선택 | 신규 패키지 + 배선 + 라이브 AC — 단일 라인 변경 아님 |

### Decision: sub-agent

### 정당화

M0(프로브)가 M1의 전제를, M1(스키마)이 M2~M5의 데이터 계약을 규정하는 순차 게이트이므로 병렬화 이득이 없고, 코딩 중심 작업은 Anthropic coding-task parallelism caveat상 순차 sub-agent가 안전한 기본값이다. Tier L이므로 `manager-develop` 위임에 Section A-E 전체 템플릿을 적용한다.

**오케스트레이터가 확보해야 할 사용자 접점 2건**(전부 AskUserQuestion):

1. **Kickoff 시점** — **M0 라이브 세션 접근 가능성** 확인. M0는 M1의 전제이므로 run-phase 진입 자체가 여기에 걸린다(§C.6 M0 접근 불가 절차 — 접근 불가 시 빔 DESCOPE 선확정으로 M1~M3만 진행하고 M4 직전에 프로브를 재시도하는 경로가 있다).
2. **M6 완료 직후** — **M7 라이브 세션 접근 가능성** 재확인.

**결정 해소용 접점은 0건이다** (v0.1.0 6건 → v0.2.0 3건 → v0.3.0 **0건**). §A.4b가 삭제되었으므로 Kickoff 전에 물어볼 미해결 결정이 없고, Implementation Kickoff Approval은 "이 계획대로 진행할지"의 승인 게이트로만 남는다. 남은 두 접점은 **결정이 아니라 물리적 접근 가능성**을 묻는다 — 사람과 실물 콘솔의 일정 확보는 SPEC이 스스로 답할 수 없는 유일한 종류의 질문이다.
