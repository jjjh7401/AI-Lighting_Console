## §1. 설계 의도

문법 계층(자연어→커맨드)은 "어떻게 만드는가"를 안다. 룩 라이브러리는 "무엇을 만들지"를 아는 첫 번째 연출 계층이다. 설계의 핵심 선택은 **지식과 바인딩의 분리**다:

- **지식(정적)**: 장르×다이내믹스×역할×속성의 룩 템플릿 — 쇼파일 무관, 서버 자산으로 버전 관리.
- **바인딩(런타임)**: 역할→실존 그룹 매핑, 프리셋 풀·슬롯 결정 — 오직 인스턴스화 시점에 `get_rig_context` 실측으로.

이 분리는 이 프로젝트가 이미 두 번 확립한 원칙의 반복이다: 20_korean_terms.md의 "어휘 클래스는 룰북에, 구체 id는 런타임에"(research.md §2), 그리고 rig 경로 라이브 캘리브레이션의 "추측된 경로는 죽은 채 출하된다"(tools.py:53-55). 룩 데이터에 per-show 값을 넣지 않는 것(REQ-LOOKLIB-004)은 미학이 아니라 이 두 사고의 재발 방지다.

두 번째 핵심 선택은 **새 실행 표면을 만들지 않는 것**이다. 룩 적용의 모든 콘솔 송신은 기존 `run_commands → gate.screen()` 단일 경로를 탄다. 룩 계층은 게이트 위에 앉은 "번들 작성자"일 뿐, 게이트의 소비자 목록에 하나 더 추가되는 것 이상이 아니다 — EXECBODY-001이 "새 방어를 만드는 게 아니라 기존 방어 안으로 밀어 넣는다"고 부른 원칙의 계승.

## §3. 데이터 흐름 (설계 목표)

```
[채팅] "웅장한 금색 코러스로 가자"
   → [session.run_instruction — 기존 1턴 파이프라인, session.py:354]
   → [LLM: 룩 라이브러리 매칭 축 소비 (§5.1 결정 E — 하이브리드)]
        → 매칭 성공: look id 확정   /   실패: 룰북 31 무드 폴백 (무변경)
   → [역할 리졸버: get_rig_context groups 실측 → 역할별 그룹 바인딩
        (미매핑 역할 = 명시 보고, 발명 금지)]
   → [번들 빌더: ChangeDestination Root → (ClearAll → 선택 → 값 → Store/Label)*
        → ClearAll  (빈 슬롯 런타임 탐색, 충돌 슬롯은 건너뛰기 — §5.1 결정 B/D)]
   → [run_commands → _ObservingBundleGate.screen  ← session.py:161-165]
        │
        ├─(1) _on_preview(commands)               ← 스크리닝 **이전**
        │      → build_execution_preview (preview.py:36)
        │      → execution_preview_event → 클라이언트
        │      ※ 커맨드별 경고 분류: preview.py:99-170
        │         · strobe|shutter|hz        → severity="danger"   (:131-139)
        │         · blinder|audience|객석     → severity="danger"   (:140-148)
        │         · pan|tilt                 → severity="caution"  (:149-157)
        │         · store /overwrite         → severity="caution"  (:113-121)
        │
        ├─(2) gate.screen(commands)               ← 기존 3-스테이지
        │      health / 문법 / 분류 → (위험 시) 승인 카드 → LiveLock 제안 강등
        │
        └─(3) _on_decision(decision)              ← 스크리닝 **이후**
   → [콘솔 송신 + 감사 1:1] → [결과 요약 보고 + _last_created 캡처]
```

핵심 설계 목표: 이 흐름 전체가 **룩발(發) 번들에 대해 손으로 쓴 지시와 완전히 동일**하다는 것 — 룩 계층은 번들 문자열을 만들 뿐, 파이프라인의 어느 단계도 특례를 갖지 않는다.

> **정정 (감사 D5).** v0.1.0은 "`gate.screen()` **이후**의 모든 단계가 완전히 무변경"이라고 서술했다. 이 표현은 프리뷰 계층을 놓쳤다 — `_ObservingBundleGate.screen`(`server/web/session.py:161-165`)은 `self._on_preview(commands)` → `self._gate.screen(commands)` → `self._on_decision(decision)` 순서로, **스크리닝을 감싸고(around) 있지 이후가 아니다.** 프리뷰는 스크리닝보다 **먼저** 발화하며 배선 지점은 `session.py:213`이다. 정확한 진술은 "**스크리닝 경로와 그 관찰 래퍼 전체가 무변경**"이다. 이 차이는 사소하지 않다 — 프리뷰가 스크리닝 앞에 있다는 사실이 §4 위험 #9(스트로브 danger 상시 발화)의 성립 근거다.

## §4. 위험 검토 (False-Negative / 오작동 노출면)

| 7 | 매칭 과신(무관한 지시를 룩으로 강제 매칭) | 신뢰 실패 시 폴백 강등(REQ-017) — 폴백 경로 자체가 회귀 테스트 대상 | 신규 위험, 신규 방어 |
| 8 | 슬롯≠FID 재발(fixtures 번호로 범위 합성) | REQ-008 + 기존 gotcha 방어 상속 | 기존, 상속 |
| **9** | **스트로브를 담은 룩 → 인스턴스화할 때마다 `danger` 등급 프리뷰** | **v1 라이브러리에서 스트로브/셔터 기본 제외**(spec.md §A 사전 결정 규칙, §D Out of Scope). 포함하려면 M0 문법 실측 + 명시적 사용자 결정 둘 다 필요 | **신규 위험, 신규 정책** |
| **10** | **빔 attribute 문자열 추측 → 콘솔이 조용히 거부하거나 오해석** | **M0 프로브 선행**(ASSUMPTION-15). 부정 실측 시 REQ-001 빔 게이트(필드 정의 유지 + v1 미사용) | **신규 위험, 신규 방어** |

**위험 #9 상세 (감사 D5).** `server/web/preview.py:131-139`는 커맨드에 `strobe|shutter|hz`가 있으면 `severity="danger"`, label `"스트로브/셔터 변화"`, 상세 `"스트로브 Hz 또는 셔터 상태가 관객과 카메라에 직접 영향을 줄 수 있습니다."`를 붙이고, `_risk_level`이 이를 번들 전체 위험 등급으로 승격시킨다. 이 분류는 `server/tests/test_web_preview.py:39-43`이 핀으로 고정한다. 프리뷰는 스크리닝 **이전**에 발화하므로(§3), 스트로브를 담은 룩은 **적용할 때마다 예외 없이** 최고 위험 등급으로 사용자에게 표시된다. 이는 프리뷰의 결함이 아니라 **의도된 관객 안전 장치**다 — 룩 라이브러리는 이 장치를 무디게 만드는 방향으로 설계되어서는 안 된다. "장르 템플릿이니까 스트로브가 들어가는 게 자연스럽다"는 생각이 정확히 그 무디게 만드는 경로다: 워십/록/EDM 클라이맥스 룩에 스트로브를 넣으면 클라이맥스 룩 전체가 상시 danger가 되고, 사용자는 곧 danger 표시를 무시하기 시작한다(경보 피로). v1이 스트로브를 배제하는 진짜 이유는 문법 미검증이 아니라 이것이다.

위험 #1이 이 SPEC의 설계 중심이다 — 룩 계층이 스스로 도입하는 유일한 실질 신규 노출면은 "리그를 잘못 읽고 자신 있게 잘못된 대상을 조준하는 것"이며, 방어의 방향은 항상 **정직한 축소**(미매핑 보고·스킵)이지 추측 보완이 아니다.

## §5. 설계 슬롯

### §5.0 대응 관계 (감사 D6a 정정)

v0.1.0은 "슬롯 A~F ↔ plan.md §A.4 마커 6건이 1:1"이라고 주장했다. **거짓이었다:**

| v0.1.0 슬롯 | v0.1.0 마커 | 실제 대응 |
|---|---|---|
| A 저장 형식 | ① | 1:1 ✓ |
| B 슬롯 할당 | ② | 1:1 ✓ |
| C 산출물 범위 **+ 충돌 정책** | ③ **와** ④ | **2:1 — 두 마커가 한 슬롯으로 접힘** |
| D 매칭 표면 | ⑤ | 1:1 ✓ |
| E 매핑 UX | ⑥ | 1:1 ✓ |
| **F 역할 어휘 폐쇄 집합** | **(없음)** | **0:1 — 대응 마커 부재** |

슬롯 F의 결함이 가장 무겁다. 마커가 없으므로 "Kickoff 전 해소" 대상 목록에 오르지 않았고, 슬롯 본문은 그 결정을 "M1 설계 산출물로 확정"으로 이연시켰다 — 즉 **역할 어휘 집합이라는 SPEC에서 가장 미래-구속적인 결정이 Implementation Kickoff Approval 게이트를 통과하지 않고 구현 단계로 흘러가는 구조**였다. 여기에 감사 D3(어휘의 사전 근거 부재)가 겹치면, M1이 근거도 게이트도 없이 어휘를 창작하게 된다.

**개정 후 대응 관계**: §5.2 슬롯 R1/R2/R3 ↔ plan.md §A.4b 마커 1/2/3 — **진짜 1:1**. 해소된 결정은 §5.1에 마커 없이 기록된다(마커는 미해결 항목 전용 표시).

### §5.1 해소된 결정 (fold-in 완료)

| 결정 | 확정 | 근거 요약 |
|---|---|---|
| **A. 룩 저장 형식·위치** | **YAML repo 자산** (`server/looks/library/*.yaml`) | `server/safety/blacklist.yaml`이 정확한 선례 — 정적·repo-shipped·주석을 담는 **규칙 데이터**. PyYAML은 이미 런타임 의존(`pyproject.toml:16`; `server/safety/ruleset.py:16,63`). v0.1.0이 병렬 후보로 든 `PinStore` JSON(`server/web/panel.py:186-330`)은 **런타임 사용자 데이터**로 클래스가 다르며(원자 쓰기·자격증명 거부가 그 증거), 정적 규칙 데이터의 선례가 아니다 — 이 구분을 하지 않은 것이 v0.1.0이 결정을 사용자 질의로 미룬 원인이다. frozen 번들 경로는 `server.resources.resource_base` 관례를 따른다(`server/rulebook/assembly.py:30-37` 선례). |
| **B. 프리셋 풀 슬롯 배정** | **런타임 빈 슬롯 탐색** | 사용자 확정 ⑤. `RIG_DRILLDOWN_QUERY_CAP = 16`(`server/orchestrator/tools.py:88`) 안에서 preset_pools 드릴다운으로 점유 실측. 고정 예약 대역은 그 자체가 미검증 관례이므로 기각. 캡 도달 시 `drilldown_capped`를 전파하고 부분 탐색을 전체로 위장하지 않는다. |

### §5.2 열린 슬롯 (Kickoff 전 해소 — plan.md §A.4b와 1:1)

**이 절은 아직 해소되지 않았다.** 각 슬롯은 plan.md §A.4b의 동번호 마커와 1:1이며, 해소 시 §5.1로 이동한다.

#### 슬롯 R1 — 역할 어휘 폐쇄 집합 (↔ 마커 1)

- **v0.1.0의 슬롯 F를 승격한 것.** 마커가 없어 게이트를 빠져나갔던 결정을 정식 미해결 항목으로 올렸다.
- **전제 정정**: v0.1.0 슬롯 F는 이 집합이 "`20_korean_terms.md` showfile 행과 정합해야" 한다고 적었으나, 감사 D3 실측 결과 **대응 행이 존재하지 않는다**(그 파일의 showfile 행은 픽스처 타입 클래스이고, `백라이트`/`FOH`/`사이드`/`스페셜`은 리포지토리 0건). 정합 대상이 없으므로 제약은 **명명 관례 스타일 준수**로 약화되고, 그만큼 **집합 구성 자체가 실질 설계 결정**으로 무거워진다.
- **제안 기본값**: 6종 — `백라이트` / `프론트`(FOH) / `사이드` / `탑` / `배경`(cyc·샤막) / `스페셜`. 각 역할 = 한국어 1급 + 영어 별칭 + 매핑 힌트 문자열 목록.
- **트레이드오프**: 넓을수록 표현력↑·미매핑률↑(정직한 축소가 상시 발동해 기능 무력화), 좁을수록 매핑 성공률↑·룩 표현력↓. 6종 근거는 plan.md §A.4b 마커 1 참조.
- **M0와의 관계**: ASSUMPTION-13 실측이 이 집합의 힌트 문자열을 조정할 수 있다. Kickoff 결정은 "이 집합으로 시작한다"이며 M0 결과로 힌트가 보정된다 — 집합 자체의 변경은 M1 착수 전에만 허용한다.

#### 슬롯 R2 — 다이내믹스 단계 척도 (↔ 마커 2)

- **신설**(감사 D8c). v0.1.0은 이 축을 "순서 있는"으로만 규정하고 척도를 정의하지 않았는데, REQ-005가 "다이내믹스 **범위 이탈**"을 검증 에러로, AC-002가 "**최저~최고** 스팬"을 인수 조건으로 삼았다 — **두 조건 모두 평가 불가능**한 상태로 출하될 뻔했다.
- **제안 기본값**: 정수 **1~5** (1 정적/앰비언트 · 2 잔잔함 · 3 빌드업 · 4 고조 · 5 클라이맥스). 검증식 `1 <= level <= 5`. 스팬 판정: 각 장르가 `{1,2}`에서 ≥1, `{4,5}`에서 ≥1.
- **왜 이 결정이 스키마 결정인가**: 척도는 단순한 상수가 아니라 **P1-1의 소비 계약**이다(research.md §10 (a) — 섹션 에너지 → 룩 선택). 정수/실수 선택이 P1-1의 매핑 알고리즘 형상을 규정하므로, 출하 후 변경은 소비자를 깨뜨린다.

#### 슬롯 R3 — 역할 매핑 확정 UX (↔ 마커 3)

- **v0.1.0의 슬롯 E에서 변경 없음** — 감사가 지적하지 않은, 진짜로 열린 트레이드오프다.
- 후보: (i) 자동 휴리스틱 + 적용 전 요약 보고(마찰 최소), (ii) 적용 전 매핑 확인 단계(안전 최우선 — 왕복 1회 추가).
- **제안 기본값**: (i). 근거 — 최종 방어가 세 겹(게이트 3-스테이지 / 승인 카드 deny-all / **실행 프리뷰**)으로 이미 존재하며, 그중 프리뷰(`server/web/session.py:161-165`)는 콘솔 송신 전에 대상과 경고를 사용자에게 보여준다.
- **반대 논거**: 프리뷰는 **커맨드**를 보여주지 **매핑 의도**를 설명하지 않는다 — `Group 11`이 사용자가 생각한 백라이트인지는 프리뷰만으로 판단하기 어렵다. 매핑 오류의 결과는 쇼파일에 남는 비가역 프리셋이며, 이는 §4 위험 #1(본 SPEC의 유일한 실질 신규 노출면)이다.

## §6. 테스트 설계 방향

### §6.1 순수 함수 우선, 인메모리 리그

로더/리졸버/번들 빌더/매칭 축은 전부 순수 — 주입된 dict 형상(rig_section 산출물과 동형)의 fake rig로 결정론 테스트. 스크리닝 경로 유닛 테스트에 OSC 0(EXECBODY-001 `DictBodyFetcher` 전통 계승).

### §6.2 실패 모드는 개별 테스트 (병합 금지)

미매핑 역할 / rig 도달 불능(`console_unreachable`) / 경로 미해석(`path_not_resolved`) / truncated 리그 / 슬롯 충돌 / 매칭 실패 폴백은 서로 다른 실패 모드 — 각각 개별 AC·개별 테스트(EXECREF/EXECBODY §6.2 원칙).

### §6.3 번들 규율은 문자열 수준 assert

생성 번들에 대해 `ChangeDestination Root` 선두 1회, Store 전후 ClearAll 쌍, Label 존재, `/Overwrite` 부재, 미등재 그룹 번호 부재를 문자열 수준으로 assert — 게이트 통과 여부와 독립적으로 빌더 자체의 불변식을 고정.

### §6.4 회귀 방어선

`test_safety_gate.py`, `test_safety_classify.py`, `test_architecture.py`, 기존 채팅/세션 스위트 + 룰북 프리픽스 byte 검증(AC-MVP-014 계열) — 룩 계층 추가가 기존 파이프라인·프리픽스를 건드리지 않았음의 기계 증거.

### §6.5 라이브 검증은 2 AC (v0.1.0의 "정확히 1 AC"에서 변경 — 감사 D9)

| 세션 | AC | 시점 | 측정 대상 |
|---|---|---|---|
| **M0 프로브** | AC-LOOKLIB-020 | **M1 저작 전** | ASSUMPTION-13(명명 관례 실효성) / 14(`Store Preset` 캡처 의미론) / 15(빔 attribute 문자열) + 슬롯 탐색 실현성 |
| **M7 종단** | AC-LOOKLIB-014 | **M6 완료 후** | 매칭 → 역할 매핑 → 인스턴스화 → 프리뷰 → 게이트 종단 통합 |

**왜 관례를 깼는가.** v0.1.0은 "라이브 검증 마일스톤 1개"라는 프로젝트 관례를 지키느라 ASSUMPTION-13/14를 M6에 배치했다. 그 배치의 실제 의미는 "**24~40룩을 저작하고 리졸버·번들 빌더를 다 만든 뒤에** 그것들이 딛고 선 전제를 처음 확인한다"였다. 여기에 감사 D2가 ASSUMPTION-15를 추가하자 — 빔 attribute 문자열은 리포지토리에 존재하지 않으므로 라이브러리에 쓸 값을 **모르는 상태에서 라이브러리를 쓸 수는 없다** — 저작 전 실측이 선택이 아니라 필연이 되었다.

**왜 합칠 수 없는가.** 두 세션은 시간축의 양 끝에 있다. M0는 정의상 M1보다 앞서야 하고, M7은 정의상 M6보다 뒤여야 한다. 하나로 만들려면 둘 중 하나를 제자리에서 옮겨야 하는데, M0를 뒤로 옮기면 순서 결함이 복원되고 M7을 앞으로 옮기면 측정 대상이 아직 존재하지 않는다.

**대가와 완화.** 라이브 세션이 1회 늘어나는 것이 비용이다. 완화: M0는 **코드 변경 0**의 순수 측정 세션이라 준비물이 M7보다 가볍다(콘솔 실행 + 이름 있는 그룹이 있는 쇼파일). 또한 M0의 부정 실측은 SPEC 실패가 아니라 **정직한 축소의 입력**이다(plan.md §A.3, EXECBODY-001 M1 GO/DESCOPE 선례).
