# SPEC-COPILOT-LOOKLIB-001 — 설계 근거 (design)

status: draft (v0.1.0, 2026-07-26) · Tier L · 본 문서는 spec.md 요구의 설계 근거와 위험 검토를 담는다. §5는 **열린 설계 슬롯**이다 — plan.md §A.4의 [NEEDS CLARIFICATION] 6건이 Implementation Kickoff Approval 전 해소되어야 하며, 해소 결과가 §5에 fold-in된다(EXECBODY-001 design.md §5의 열린 슬롯 → fold-in 구조 계승).

## §1. 설계 의도

문법 계층(자연어→커맨드)은 "어떻게 만드는가"를 안다. 룩 라이브러리는 "무엇을 만들지"를 아는 첫 번째 연출 계층이다. 설계의 핵심 선택은 **지식과 바인딩의 분리**다:

- **지식(정적)**: 장르×다이내믹스×역할×속성의 룩 템플릿 — 쇼파일 무관, 서버 자산으로 버전 관리.
- **바인딩(런타임)**: 역할→실존 그룹 매핑, 프리셋 풀·슬롯 결정 — 오직 인스턴스화 시점에 `get_rig_context` 실측으로.

이 분리는 이 프로젝트가 이미 두 번 확립한 원칙의 반복이다: 20_korean_terms.md의 "어휘 클래스는 룰북에, 구체 id는 런타임에"(research.md §2), 그리고 rig 경로 라이브 캘리브레이션의 "추측된 경로는 죽은 채 출하된다"(tools.py:53-55). 룩 데이터에 per-show 값을 넣지 않는 것(REQ-LOOKLIB-004)은 미학이 아니라 이 두 사고의 재발 방지다.

두 번째 핵심 선택은 **새 실행 표면을 만들지 않는 것**이다. 룩 적용의 모든 콘솔 송신은 기존 `run_commands → gate.screen()` 단일 경로를 탄다. 룩 계층은 게이트 위에 앉은 "번들 작성자"일 뿐, 게이트의 소비자 목록에 하나 더 추가되는 것 이상이 아니다 — EXECBODY-001이 "새 방어를 만드는 게 아니라 기존 방어 안으로 밀어 넣는다"고 부른 원칙의 계승.

## §2. 변경 표면 (예상)

1. **`server/looks/` (신규 패키지)** — 스키마 + 로더 + 내장 라이브러리 자산 + 역할 리졸버 + 인스턴스화 번들 빌더 + 매칭 축. 전부 순수(콘솔/OSC 무접촉), 주입된 rig 데이터/포트에만 의존.
2. **`server/orchestrator/tools.py` + `server/web/session.py`** — 매칭 표면의 툴/컨텍스트 배선(§5 슬롯 D의 결정에 따름). `build_toolset` 파라미터 확장 또는 신규 툴 등록.
3. **`server/rulebook/assets/v2.4.2/`** — (§5 슬롯 D가 채택할 경우에만) 얇은 정적 안내 축. 기존 31 무드 절과의 관계 정리 포함.
4. **테스트** — `server/tests/test_looks_*.py` 신규 + `test_architecture.py` 경계 무변경 확인.

**무변경**: `server/safety/**`(소비만), `server/bridge/**`, `console/lua/**`, `ui/src/**`, `server/web/panel.py`(룩의 패널 노출은 기존 `_last_created` 핀 경로 범위 내).

## §3. 데이터 흐름 (설계 목표)

```
[채팅] "웅장한 금색 코러스로 가자"
   → [session.run_instruction — 기존 1턴 파이프라인]
   → [LLM: 룩 라이브러리 매칭 축 소비 (§5 슬롯 D 형상)]
        → 매칭 성공: look id 확정   /   실패: 룰북 31 무드 폴백 (무변경)
   → [역할 리졸버: get_rig_context groups 실측 → 역할별 그룹 바인딩
        (미매핑 역할 = 명시 보고, 발명 금지)]
   → [번들 빌더: ChangeDestination Root → (ClearAll → 선택 → 값 → Store/Label)*
        → ClearAll  (슬롯 할당은 §5 슬롯 B 정책)]
   → [run_commands → gate.screen() — 기존 3-스테이지: health/문법/분류
        → (위험 시) 승인 카드 → LiveLock 제안 강등]
   → [콘솔 송신 + 감사 1:1] → [결과 요약 보고 + _last_created 캡처]
```

핵심 설계 목표: `gate.screen()` 이후의 모든 단계가 **완전히 무변경**이라는 것 — 룩발(發) 번들이든 손으로 쓴 지시든 동일한 파이프라인을 탄다.

## §4. 위험 검토 (False-Negative / 오작동 노출면)

| # | 위험 | 방어 | 신규/기존 |
|---|---|---|---|
| 1 | 잘못된 역할 매핑 → 엉뚱한 그룹에 룩 저장 | 실존 그룹만 후보(REQ-007) + 미매핑 명시 보고(REQ-009) + 적용 전 결과 보고(REQ-013) + 사람 확정 철학 | **신규 위험, 신규 방어** |
| 2 | 프리셋 슬롯 충돌 → 사용자 프리셋 파괴 | `Store /overwrite` 블랙리스트(기존) + 충돌 기본 방향 = 스킵/보류(REQ-012) + §5 슬롯 B/C 정책 | 기존 방어 + 신규 정책 |
| 3 | 룩 번들에 위험 커맨드 혼입 | 기존 게이트 분류·블랙리스트·승인(무변경 소비, REQ-021) | 기존, 상속 |
| 4 | LiveLock 중 적용 시도 | 제안 강등 + lock-FIRST 재확인(REQ-020) | 기존, 상속 |
| 5 | 트래킹 오염(잔류 프로그래머 값이 다음 캡처에 유입) | ClearAll 규율을 번들 빌더가 기계적으로 보장(REQ-011) — 사람 실수 아닌 코드 불변식으로 | **신규 방어** |
| 6 | 고정 프리픽스 오염(룩 데이터가 룰북에 유입 → 캐시/토큰 회귀) | REQ-022 + 분리 원칙(§1) + AC의 프리픽스 byte-diff 검증 | **신규 위험, 신규 방어** |
| 7 | 매칭 과신(무관한 지시를 룩으로 강제 매칭) | 신뢰 실패 시 폴백 강등(REQ-017) — 폴백 경로 자체가 회귀 테스트 대상 | 신규 위험, 신규 방어 |
| 8 | 슬롯≠FID 재발(fixtures 번호로 범위 합성) | REQ-008 + 기존 gotcha 방어 상속 | 기존, 상속 |

위험 #1이 이 SPEC의 설계 중심이다 — 룩 계층이 스스로 도입하는 유일한 실질 신규 노출면은 "리그를 잘못 읽고 자신 있게 잘못된 대상을 조준하는 것"이며, 방어의 방향은 항상 **정직한 축소**(미매핑 보고·스킵)이지 추측 보완이 아니다.

## §5. 열린 설계 슬롯 (Kickoff 전 해소 — plan.md §A.4와 1:1)

**이 절은 아직 해소되지 않았다.** 각 슬롯은 plan.md §A.4의 동번호 [NEEDS CLARIFICATION] 마커와 1:1이며, 해소 시 본 절에 결정과 근거를 fold-in한다(재감사 여부는 결정의 크기에 따름).

### 슬롯 A — 룩 저장 형식·위치

- 후보: (i) YAML repo 자산(blacklist.yaml 선례 — 주석 가능, 사람이 읽고 고치기 좋음, PyYAML 기존 의존), (ii) JSON(PinStore/stdlib 선례), (iii) Python 리터럴 모듈(로더 불요, 단 데이터/코드 분리 약화).
- 제약: repo-shipped 정적 템플릿이 단일 진실원(REQ-004). frozen 번들 경로는 `server.resources.resource_base` 관례를 따라야 함(assembly.py:30-37 선례).

### 슬롯 B — 프리셋 풀 슬롯 할당 전략

- 후보: (i) 고정 예약 대역(예: 슬롯 101+ — 예측 가능, 충돌 검사 단순, 단 대역 자체가 관례 가정), (ii) 빈 슬롯 런타임 탐색(충돌 최소, 단 드릴다운 캡 16쿼리와 풀 크기 미지의 비용), (iii) 설정값(effective settings 경유).
- 제약: 풀 번호·점유는 쇼파일 종속 — 어떤 전략이든 인스턴스화 직전 실측 확인이 선행되어야 한다.

### 슬롯 C — 인스턴스화 산출물 범위 + 충돌 정책

- 후보: 프리셋만 / 프리셋+데모 시퀀스 / +익스큐터 바인딩까지. 충돌: 스킵 / 재슬롯 / 명시 승인 경유 덮어쓰기.
- 제약: 산출물이 클수록 blast radius·승인 마찰 증가. `Store /overwrite` 블랙리스트가 하한을 규정(REQ-012). 익스큐터 바인딩은 빈 익스큐터 탐색 문제를 추가로 연다.

### 슬롯 D — 매칭 표면 형상

- 후보: (i) 신규 조회 툴(예: 룩 라이브러리 조회 — 구조화 반환, 토큰은 필요 시만), (ii) 얇은 룰북 정적 안내 축 + 툴(하이브리드 — research.md §2 권고 방향), (iii) 시스템 컨텍스트 주입(세션 조립 시).
- 제약: 고정 프리픽스 byte-stability(REQ-022)·매 턴 토큰 비용·제공자 중립(REQ-016). 기존 31 무드 절과의 서술 관계(대체/보완) 정리 필요.

### 슬롯 E — 역할 매핑 확정 UX

- 후보: (i) 자동 휴리스틱 + 결과 보고(마찰 최소 — 게이트/승인이 최종 방어), (ii) 적용 전 매핑 확인 단계(안전 최우선 — 왕복 1회 추가).
- 제약: "사람이 확정" 철학과 지시→실행 <10초 목표(product.md Phase 1 기준)의 트레이드오프.

### 슬롯 F — 역할 어휘 폐쇄 집합의 정확한 구성

- 백라이트/FOH 워시/사이드/사이크·샤막/스페셜 등 — 20_korean_terms.md showfile 행과 정합해야 하며, 너무 넓으면 매핑 실패가 늘고 너무 좁으면 표현력이 준다. M1 설계 산출물로 확정.

## §6. 테스트 설계 방향

### §6.1 순수 함수 우선, 인메모리 리그

로더/리졸버/번들 빌더/매칭 축은 전부 순수 — 주입된 dict 형상(rig_section 산출물과 동형)의 fake rig로 결정론 테스트. 스크리닝 경로 유닛 테스트에 OSC 0(EXECBODY-001 `DictBodyFetcher` 전통 계승).

### §6.2 실패 모드는 개별 테스트 (병합 금지)

미매핑 역할 / rig 도달 불능(`console_unreachable`) / 경로 미해석(`path_not_resolved`) / truncated 리그 / 슬롯 충돌 / 매칭 실패 폴백은 서로 다른 실패 모드 — 각각 개별 AC·개별 테스트(EXECREF/EXECBODY §6.2 원칙).

### §6.3 번들 규율은 문자열 수준 assert

생성 번들에 대해 `ChangeDestination Root` 선두 1회, Store 전후 ClearAll 쌍, Label 존재, `/Overwrite` 부재, 미등재 그룹 번호 부재를 문자열 수준으로 assert — 게이트 통과 여부와 독립적으로 빌더 자체의 불변식을 고정.

### §6.4 회귀 방어선

`test_safety_gate.py`, `test_safety_classify.py`, `test_architecture.py`, 기존 채팅/세션 스위트 + 룰북 프리픽스 byte 검증(AC-MVP-014 계열) — 룩 계층 추가가 기존 파이프라인·프리픽스를 건드리지 않았음의 기계 증거.

### §6.5 라이브 검증은 정확히 1 AC

실물 onPC 검증은 AC-LOOKLIB-014 하나로 수렴(프로젝트 관례: 라이브 검증 마일스톤 1개). ASSUMPTION-13/14가 이 AC에서 실측된다.
