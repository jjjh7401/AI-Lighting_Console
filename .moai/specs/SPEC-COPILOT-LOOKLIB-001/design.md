## §1. 설계 의도

문법 계층(자연어→커맨드)은 "어떻게 만드는가"를 안다. 룩 라이브러리는 "무엇을 만들지"를 아는 첫 번째 연출 계층이다. 설계의 핵심 선택은 **지식과 바인딩의 분리**다:

- **지식(정적)**: 장르×다이내믹스×역할×속성의 룩 템플릿 — 쇼파일 무관, 서버 자산으로 버전 관리.
- **바인딩(런타임)**: 역할→실존 그룹 매핑, 프리셋 풀·슬롯 결정 — 오직 인스턴스화 시점에 `get_rig_context` 실측으로.

이 분리는 이 프로젝트가 이미 두 번 확립한 원칙의 반복이다: 20_korean_terms.md의 "어휘 클래스는 룰북에, 구체 id는 런타임에"(research.md §2), 그리고 rig 경로 라이브 캘리브레이션의 "추측된 경로는 죽은 채 출하된다"(tools.py:53-55). 룩 데이터에 per-show 값을 넣지 않는 것(REQ-LOOKLIB-004)은 미학이 아니라 이 두 사고의 재발 방지다.

두 번째 핵심 선택은 **새 실행 표면을 만들지 않는 것**이다. 룩 적용의 모든 콘솔 송신은 기존 `run_commands → gate.screen()` 단일 경로를 탄다. 룩 계층은 게이트 위에 앉은 "번들 작성자"일 뿐, 게이트의 소비자 목록에 하나 더 추가되는 것 이상이 아니다 — EXECBODY-001이 "새 방어를 만드는 게 아니라 기존 방어 안으로 밀어 넣는다"고 부른 원칙의 계승.

## §3. 데이터 흐름 (설계 목표)

```
[채팅] "웅장한 금색 코러스로 가자"
   → [session.run_instruction — 기존 1턴 파이프라인, session.py:354]
   → [LLM: 룩 라이브러리 매칭 축 소비 (§5.1 결정 E — 하이브리드)]
        → 매칭 성공: look id 확정   /   실패: 룰북 31 무드 폴백 (무변경)
   → [역할 리졸버: get_rig_context groups 실측 → 역할별 그룹 바인딩
        (미매핑 역할 = 명시 보고, 발명 금지)]
   → [번들 빌더: ChangeDestination Root → (ClearAll → 선택 → 값 → Store/Label)*
        → ClearAll  (빈 슬롯 런타임 탐색, 충돌 슬롯은 건너뛰기 — §5.1 결정 B/D)]
   → [run_commands → _ObservingBundleGate.screen  ← session.py:161-165]
        │
        ├─(1) _on_preview(commands)               ← 스크리닝 **이전**
        │      → build_execution_preview (preview.py:36)
        │      → execution_preview_event → 클라이언트
        │      ※ 커맨드별 경고 분류: preview.py:99-170
        │         · strobe|shutter|hz        → severity="danger"   (:131-139)
        │         · blinder|audience|객석     → severity="danger"   (:140-148)
        │         · pan|tilt                 → severity="caution"  (:149-157)
        │         · store /overwrite         → severity="caution"  (:113-121)
        │
        ├─(2) gate.screen(commands)               ← 기존 3-스테이지
        │      health / 문법 / 분류 → (위험 시) 승인 카드 → LiveLock 제안 강등
        │
        └─(3) _on_decision(decision)              ← 스크리닝 **이후**
   → [콘솔 송신 + 감사 1:1] → [결과 요약 보고 + _last_created 캡처]
```

핵심 설계 목표: 이 흐름 전체가 **룩발(發) 번들에 대해 손으로 쓴 지시와 완전히 동일**하다는 것 — 룩 계층은 번들 문자열을 만들 뿐, 파이프라인의 어느 단계도 특례를 갖지 않는다.

> **정정 (감사 D5).** v0.1.0은 "`gate.screen()` **이후**의 모든 단계가 완전히 무변경"이라고 서술했다. 이 표현은 프리뷰 계층을 놓쳤다 — `_ObservingBundleGate.screen`(`server/web/session.py:161-165`)은 `self._on_preview(commands)` → `self._gate.screen(commands)` → `self._on_decision(decision)` 순서로, **스크리닝을 감싸고(around) 있지 이후가 아니다.** 프리뷰는 스크리닝보다 **먼저** 발화하며 배선 지점은 `session.py:213`이다. 정확한 진술은 "**스크리닝 경로와 그 관찰 래퍼 전체가 무변경**"이다. 이 차이는 사소하지 않다 — 프리뷰가 스크리닝 앞에 있다는 사실이 §4 위험 #9(스트로브 danger 상시 발화)의 성립 근거다.

**위험 #9 상세 (감사 D5).** `server/web/preview.py:131-139`는 커맨드에 `strobe|shutter|hz`가 있으면 `severity="danger"`, label `"스트로브/셔터 변화"`, 상세 `"스트로브 Hz 또는 셔터 상태가 관객과 카메라에 직접 영향을 줄 수 있습니다."`를 붙이고, `_risk_level`이 이를 번들 전체 위험 등급으로 승격시킨다. 이 분류는 `server/tests/test_web_preview.py:39-43`이 핀으로 고정한다. 프리뷰는 스크리닝 **이전**에 발화하므로(§3), 스트로브를 담은 룩은 **적용할 때마다 예외 없이** 최고 위험 등급으로 사용자에게 표시된다. 이는 프리뷰의 결함이 아니라 **의도된 관객 안전 장치**다 — 룩 라이브러리는 이 장치를 무디게 만드는 방향으로 설계되어서는 안 된다. "장르 템플릿이니까 스트로브가 들어가는 게 자연스럽다"는 생각이 정확히 그 무디게 만드는 경로다: 워십/록/EDM 클라이맥스 룩에 스트로브를 넣으면 클라이맥스 룩 전체가 상시 danger가 되고, 사용자는 곧 danger 표시를 무시하기 시작한다(경보 피로). v1이 스트로브를 배제하는 진짜 이유는 문법 미검증이 아니라 이것이다.

**위험 #1 상세 (v0.3.0 — 수용된 잔여 위험으로 재기술).** 위험 #1은 이 SPEC의 설계 중심이다 — 룩 계층이 스스로 도입하는 유일한 실질 신규 노출면은 "리그를 잘못 읽고 자신 있게 잘못된 대상을 조준하는 것"이며, 방어의 방향은 항상 **정직한 축소**(미매핑·모호 보고·스킵)이지 추측 보완이 아니다.

그러나 이 방어들은 위험 #1을 **제거하지 않는다.** 방어가 잡는 것은 "매핑할 수 없다"(후보 없음 / 모호)이지 "**자신 있게 틀리게 매핑했다**"가 아니다. `Front Truss`라는 이름의 그룹이 실제로는 백라이트 트러스라면, 힌트는 확신을 갖고 `프론트`에 배정하고 미매핑도 모호도 발생하지 않으며, 프리뷰는 `Group 11`이라는 **커맨드**만 보여줄 뿐 그 배정이 사용자 의도와 맞는지는 말해주지 않는다. 결과는 쇼파일에 남는 비가역 프리셋이다.

**사용자 확정 ⑩**(자동 휴리스틱 + 요약 보고, 별도 확인 왕복 없음)은 이 잔여 위험을 알고 내린 결정이다 — 반대 논거(프리뷰는 매핑 의도를 설명하지 않는다)가 사용자에게 제시되었고, 사용자는 그것을 보고도 마찰 최소 쪽을 택했다. 따라서 위험 #1은 **제거된 위험이 아니라 표면화된 뒤 수용된 위험**으로 기록된다. 추가 왕복 없이 가능한 완화는 요약 보고가 바인딩을 **그룹 이름과 함께** 제시하는 것이다(`Group 11 'Front Truss' ← 백라이트`) — 사후 발견 가능성을 높이되 왕복은 늘리지 않는다(plan.md §A.4a-K).

## §6. 테스트 설계 방향

### §6.1 순수 함수 우선, 인메모리 리그

| **M7 종단** | AC-LOOKLIB-014 | **M6 완료 후** | 매칭 → 역할 매핑 → 인스턴스화 → 프리뷰 → 게이트 종단 통합 |

**왜 관례를 깼는가.** v0.1.0은 "라이브 검증 마일스톤 1개"라는 프로젝트 관례를 지키느라 ASSUMPTION-13/14를 M6에 배치했다. 그 배치의 실제 의미는 "**24~40룩을 저작하고 리졸버·번들 빌더를 다 만든 뒤에** 그것들이 딛고 선 전제를 처음 확인한다"였다. 여기에 감사 D2가 ASSUMPTION-15를 추가하자 — 빔 attribute 문자열은 리포지토리에 존재하지 않으므로 라이브러리에 쓸 값을 **모르는 상태에서 라이브러리를 쓸 수는 없다** — 저작 전 실측이 필연이 되었다.

**v0.3.0 논거 정정 — 네 항목이 균일하게 M1을 막는 것은 아니다.** v0.2.0은 위 논거를 네 프로브 항목 전부에 균일하게 적용했으나, 항목별 차단 대상은 서로 다르다(plan.md §A.2 표가 정본): **ASSUMPTION-15만 M1(로더)을 진짜로 막고**, ASSUMPTION-14와 슬롯·풀 실현성은 **M4(번들 빌더)** 를, ASSUMPTION-13은 **M3(리졸버)** 를 대상으로 하며 그나마 차단이 아니라 튜닝 입력이다. 정확한 진술은 **"진짜 순서 제약 1건 + 의도적 배칭 3건"**이다 — 라이브 세션의 실제 비용은 콘솔·쇼파일 준비와 일정 확보이지 항목 하나를 더 발화하는 한계 비용이 아니므로, 어차피 M1 앞에 서는 세션에 M3·M4용 항목을 묶는 편이 세션을 쪼개는 것보다 싸다.

**"라이브 세션 2회"의 정확한 귀속 (사용자 확정 ⑧).** 사용자는 "빔 유지 = 세션 2회"라는 대가를 제시받고 유지를 택했다. 그 거래를 정확히 적으면 **빔이 결정한 것은 프로브의 위치이지 세션의 개수가 아니다** — 빔을 뺐더라도 ASSUMPTION-14·슬롯 탐색이 M4를 막으므로 M4 이전 세션은 여전히 필요했고, M7과 합쳐 2회는 그대로였다. 빔이 한 일은 그 프로브를 **M4 직전에서 M1 직전으로 앞당긴 것**이며, 대가로 저작 착수 전에 빔 어휘의 존부가 확정된다. 사용자 결정은 유효하게 유지되고, 정정 대상은 그 결정에 붙어 있던 **논거의 정밀도**다.

**왜 합칠 수 없는가.** 두 세션은 시간축의 양 끝에 있다. M0는 정의상 M1보다 앞서야 하고(ASSUMPTION-15 때문에), M7은 정의상 M6보다 뒤여야 한다. 하나로 만들려면 둘 중 하나를 제자리에서 옮겨야 하는데, M0를 뒤로 옮기면 순서 결함이 복원되고 M7을 앞으로 옮기면 측정 대상이 아직 존재하지 않는다.

**대가와 완화.** 라이브 세션이 1회 늘어나는 것이 비용이다. 완화: M0는 **코드 변경 0**의 순수 측정 세션이라 준비물이 M7보다 가볍다(콘솔 실행 + 이름 있는 그룹이 있는 쇼파일). 또한 M0의 부정 실측은 SPEC 실패가 아니라 **정직한 축소의 입력**이다(plan.md §A.3, EXECBODY-001 M1 GO/DESCOPE 선례).
