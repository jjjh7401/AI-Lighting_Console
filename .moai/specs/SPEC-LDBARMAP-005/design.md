# SPEC-LDBARMAP-005 — design.md

박자표 판별기의 설계와 사전 등록. 이 문서는 plan-phase 산출물이다 — 코드를 쓰지 않았고 시험을 돌리지 않았다. 아래 알고리즘은 **설계**이며 한 번도 실행된 적이 없다. 성능을 말하는 문장은 전부 예측이거나 합성 관문(M1)이 앞으로 재야 할 기준이다.

## 0. 읽는 법

**출처 표기 세 가지.** 문서 안의 숫자는 아래 셋 중 하나를 붙인다.

- `[measured: <명령> @ <트리>]` — 이 plan-phase에서 명령을 실행해 본 값. 트리는 `bef3e16d`(이 워크트리의 HEAD)다.
- `[carried: <파일:줄>]` — 다른 문서나 코드에서 옮긴 값. 이 plan-phase가 다시 재지 않았다.
- `[predicted]` — 측정 전에 정한 값. 사전 등록 문턱, 합성 픽스처 매개변수, 산술 결과, 규모 추정이 모두 여기에 든다. 관측이 아니다.

**동결(freeze).** §6 사전 등록 표를 M1 합성 실행 전에 굳히는 일이다. 동결 시점은 이 문서를 담은 plan-phase 커밋이다. 동결 뒤 표의 값을 바꾸려면 §6.3의 개정 절차를 밟아야 하고, 실제 곡의 결과를 이유로 바꿀 수 없다(REQ-LDBARMETER-003).

## 1. 문제와 결정 범위

오디오에서 박 격자(`beat_times`)가 이미 나온다(`server/audio/bar_map.py:241-243` [carried]). 지금은 이 격자를 4칸씩 묶어 마디로 삼는다(`bar_map.py:462` [carried]). 이 설계가 정하는 것은 하나다 — **한 마디가 격자의 몇 칸인가(분자 N)**.

- 입력: 칸 시각 목록, 칸마다의 온셋 세기, BPM 검사 결과(`BpmCandidateCheck`, `bar_map.py:80-101` [carried]).
- 출력: `MeterDecision` — 분자 N ∈ {3, 4, 6}, 상태 ∈ {확신, 추정}, 근거 기록(통계량, p 값, 사유 코드).
- 하지 않는 것: 칸 격자를 바꾸는 일, `bpm`을 바꾸는 일, 첫 박 오프셋을 정하는 일(D-3), 곡을 거절하는 일(P1).

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 칸 | 박 격자 `beat_times`의 항목 하나. 음악 값(4분음표인지 8분음표인지)은 추적기가 정하고 이 설계는 묻지 않는다 |
| 분자 N | 한 마디에 든 칸 수. 후보는 3, 4, 6 |
| 표기 분모 | 분자에 붙이는 이름표. 3→4, 4→4, 6→8. 마디 시작 계산에 쓰이지 않는다(§3.4) |
| 확신 / 추정 | 판별 상태. 확신은 §5의 조건을 모두 채운 경우뿐이다. 그 밖은 전부 추정이고, 추정이면 N=4로 나누고 「박자 추정」 표지를 붙인다 |
| 칸 세기 A_k | k번째 칸 자리의 온셋 세기 |

## 3. 비트 단위 문제

### 3.1 같은 격자를 나누는 두 쌍

칸이 일정한 간격으로 늘어서 있다고 하자. 마디 길이를 정하는 것은 **강세가 몇 칸마다 돌아오는가**뿐이다.

- **3/4 대 6/8.** 두 박자 모두 3칸마다 강세가 돈다(`강 약 약 강 약 약`). 6/8은 거기에 한 겹이 더 있다 — 3칸 묶음 둘이 한 마디(6칸)를 이루고, 두 묶음의 첫 칸 강세가 서로 다르다(강과 중강). 그래서 3과 6을 가르는 신호는 **3칸 떨어진 강세 쌍의 비대칭**이다.
- **2/4 대 4/4.** 같은 구조다. 2칸 묶음 둘이 한 마디를 이루는지, 묶음 하나가 한 마디인지를 가르는 신호는 2칸 떨어진 강세 쌍의 비대칭이다.

### 3.2 2/4를 후보에서 뺀 이유

2/4는 후보 집합에 넣지 않는다(합성 픽스처로는 참고용으로만 만든다, §7.7). 이유는 둘이다.

1. **오판의 모양이 다르다.** 진짜 분자가 N일 때 4로 나누면 — N=2이면 경계가 4칸 간격이라 2/4 경계의 부분집합이다(성긴 경계, 틀린 경계는 없다). N=3이나 6이면 4와 겹치는 경계가 일부뿐이라 마디 경계가 틀어진다. 폴백 N=4가 안전한 쪽은 2의 배수뿐이다. 이 비대칭이 P3의 「4/4로 진행」을 2/4에 대해서는 이미 무해하게 만든다.
2. **2칸 주기 강세는 4/4 안에도 흔하다.** 카드 t547이 잰 실제 10곡의 홀짝 칸 부호검정에서 `p_two < 0.01`인 곡이 6곡이었다(`.moai/reports/t547/probe_sign.txt`의 `p_two` 열 [carried: `.moai/specs/SPEC-LDBARMAP-001/research.md:153`]; 이 plan-phase가 같은 파일을 열어 10행 가운데 `p_two < 0.01`이 6행임을 세어 보았다 [measured: `cat .moai/reports/t547/probe_sign.txt` @ bef3e16d]). 2를 후보에 두면 정상 4/4 곡을 2/4로 오확신할 위험이 커진다.

### 3.3 칸이 무엇이냐는 추적기가 정한다

`librosa.beat.beat_track`이 4분음표 펄스를 잡을지 8분음표나 점4분음표 펄스를 잡을지 이 SPEC은 정하지 않는다(`bar_map.py:241-243` [carried]). 판별은 **잡힌 칸 단위에서** N을 센다. 같은 곡이라도 추적기가 잡는 펄스에 따라 N이 달라질 수 있다.

- 6/8 곡을 **8분음표 펄스**로 잡으면 칸 6개가 한 마디다 — 후보 6이 맞는 경우다.
- 같은 곡을 **점4분음표 펄스**로 잡으면 한 마디가 2칸이고 강세는 `강 중강 강 중강`이 된다. 후보 집합에 2가 없으므로 이 구조는 확신 4(2칸 주기 강세가 4칸 구간에서 `강 중 강 중`으로 보인다)이거나 추정 4가 될 것으로 본다 [predicted: 이 구조를 실행한 적이 없다]. 마디 경계는 진짜 경계의 부분집합이라 틀린 경계는 아니다.
- 이 경우를 가르는 신호(칸 사이를 3등분하는 온셋과 2등분하는 온셋의 비교)와, 판별한 복합박을 6칸 마디로 저장하기 위해 칸 사이를 보간해 하위 박 격자를 만드는 일은 **이 SPEC의 범위 밖**이다(spec.md OQ-3, Out of Scope).
- 따라서 **이 SPEC의 6/8 주장은 「추적기가 8분음표 펄스를 잡은 경우」에 한정된다.** 합성 관문의 6/8 픽스처는 그 조건을 만족하도록 만든다(§7.2).

### 3.4 저장 값의 뜻 — 소비자 식과 맞춘다

소비자는 마디 N의 시작을 `1마디 시작 + (N−1) × beats_per_bar × 60 / bpm`으로 계산한다(`server/design/beat_grid_emit.py:216` [carried]). `beats_per_bar`는 저장된 `time_signature[0]`이고(`server/design/beat_grid_send.py:255` [carried]) 분모는 읽지 않는다(같은 함수, `:248-255` [carried]).

그래서 저장 값은 이렇게 정한다.

- `time_signature[0]` = 분자 N = **마디당 칸 수**.
- `bpm` = **칸의 분당 횟수**(현재와 같다 — `bar_map.py:267`, `bpm_check.adopted_bpm` [carried]).
- `time_signature[1]` = 표기 분모(3→4, 4→4, 6→8). 소비자가 읽지 않는 이름표다.
- 마디당 `beats_ms`의 길이는 N이다 — 저장 검증이 이미 요구한다(`server/audio/bar_map_store.py:258-267` [carried]).

6/8을 8분음표 펄스로 잡았다면 `bpm`은 점4분음표 템포가 아니라 8분음표 빈도다. 화면에 어떤 템포를 보여 줄지는 후속 UI 카드의 일이다(spec.md OQ-8).

## 4. 신호와 통계

### 4.1 신호

**칸 세기 A_k** = 칸 시각 t_k 자리의 온셋 세기. 기존 온셋 강도 환경(`librosa.onset.onset_strength`, hop 512, `bar_map.py:247-249` [carried])에서 칸 시각 ±1프레임 안의 최댓값을 취한다(`_strength_at`, `bar_map.py:273-289` [carried]). 새 신호를 만들지 않고 두 배 BPM 검사가 이미 쓰는 것을 재사용한다.

`detect_beat_grid`는 지금 이 환경을 BPM 검사에 쓰고 버린다(`bar_map.py:260-262` [carried]). 판별을 위해 `BeatGridResult`가 칸 세기 목록을 함께 돌려줘야 한다(plan.md §C).

**이 신호의 한계(미리 적는다).** 진폭 차이로 드러나는 강세만 본다. 같은 크기에 음색만 다른 강세(킥과 스네어가 같은 세기로 번갈아 오는 경우)는 잡지 못한다. 합성 픽스처의 강세는 진폭으로 넣으므로 M1은 이 신호에 가장 유리한 조건에서 잰다. 실제 곡에서 이 신호가 충분한지는 이 SPEC이 말하지 않는다(spec.md Gaps 7).

### 4.2 검정 세 가지

전부 부호검정이다. p 값은 기존 함수와 같은 식으로 계산한다 — 정확 이항검정, `math.comb` 사용, scipy 없음(`bar_map.py:292-308` [carried]).

**주기 검정 T_P (P ∈ {3, 4}).** 위상 φ ∈ [0, P)마다 다음을 한다.

1. 마디 b의 첫 칸 k_b = φ + b·P (b = 0, 1, …, 끝까지 온전히 든 마디만).
2. U_b = A[k_b] − 평균(A[k_b+1 … k_b+P−1]) — 마디 첫 칸이 같은 마디의 나머지 칸 평균보다 센 정도.
3. 0인 U_b를 빼고 개수 n, 양수 개수 s를 센다. p_{P,φ} = P(X ≥ s), X ~ 이항(n, 0.5). 단측(H1: 마디 첫 칸이 더 세다).
4. T_P의 p 값 p_P = min(1, P × min_φ p_{P,φ}). 위상 P개를 고르는 다중성은 곱하기 P로 보정한다(본페로니).

**홀짝 검정 T_par (3과 6을 가른다).** T_3이 유의할 때만 실행한다. 최적 위상 φ* = argmin_φ p_{3,φ}(동률이면 작은 쪽). j = 0, 1, …에 대해 D_j = A[φ*+6j] − A[φ*+6j+3]. 0을 빼고 n_par, s_par를 센다. p_par = 양측 부호검정(`two_sided=True`).

- 3/4이면 두 묶음의 첫 칸 세기가 기대값이 같아 D_j의 부호가 무작위다 → p_par는 유의하지 않다.
- 6/8이면 한쪽이 체계적으로 세다 → 유의하다. 방향(어느 쪽이 강한가)은 묻지 않는다. φ*가 강 쪽에 앉을지 중강 쪽에 앉을지 위상 선택이 정하기 때문이다.

### 4.3 유의수준

| 검정 | 수준 | 근거 |
|---|---|---|
| T_3, T_4 | α_period = α / 2 = 0.005 | 주기 검정 둘에 대한 본페로니. α = 0.01은 기존 상수(`bar_map.py:61` [carried]) |
| T_par | α_par = α = 0.01 | T_3이 유의한 경우에만 실행하는 순차 절차라 추가 보정을 하지 않는다 |

### 4.4 입력 길이

각 검정은 비교 쌍이 `MIN_PAIRS = 12`개 이상일 때만 「실행 가능」하다. 한계 산술: T_3은 `3 × 2^−n < 0.005` ⇒ n ≥ 10, T_4는 `4 × 2^−n < 0.005` ⇒ n ≥ 10, T_par는 `2 × 2^−n < 0.01` ⇒ n ≥ 8 [predicted: 산술]. 12는 그 위에 둔 여유다 [predicted]. 실행 가능하지 않은 검정이 하나라도 결정에 필요하면 추정이다(§5의 U-3).

2. 코드의 상수는 이 표와 같아야 한다 — 코드가 표를 인용하는 `@MX:NOTE`를 달고(원칙 출처: `bar_map.py:57-61` [carried]), AC-LDBARMETER-007이 표와 코드의 값을 대조한다.

### 6.3 동결 뒤 개정

M1이 문턱을 못 넘으면 표를 고쳐서 다시 돌리지 않는다. 절차는 다음과 같다.

1. 실행을 멈추고 실패한 칸과 수치를 progress.md에 그대로 적는다(지우거나 덮어쓰지 않는다).
2. 설계 결함의 원인을 합성 데이터와 이론으로만 찾는다.
3. 표를 고친다면 날짜·이유·이전 값을 적은 개정 행을 §6.4에 더하고, M1을 처음부터 다시 돌린다. 이전 실행의 결과는 기록에 남는다.
4. **실제 곡의 어떤 결과도 개정의 이유가 될 수 없다.** M3의 결과는 이 표를 바꾸는 데 쓰지 않는다(§11.5).

## 7. 합성 정답지 관문(M1) 설계

### 7.1 무엇을 재는가

박자를 아는 합성 오디오에서 판별기가 정답 분자를 내는 비율과 오확신 비율이다. 두 층으로 나눈다.

- **G-A (판별기 단독).** 생성한 칸 시각을 그대로 칸으로 쓰고, 칸 세기는 합성 오디오에서 기존 온셋 강도 환경으로 잰다. 추적기를 거치지 않는다.
- **G-B (끝에서 끝까지).** 오디오를 `detect_beat_grid`에 통과시켜 추적기가 낸 칸으로 판별한다. 추적기가 생성한 칸을 못 잡으면 판별기 탓이 아니어도 실패로 센다 — 그 비율을 따로 적는다(PR-17).

### 7.2 픽스처

시험 실행 중 임시 폴더에 만들고 저장소에 커밋하지 않는다. 시드로 결정적이다.

| 항목 | 값 |
|---|---|
| 클릭 | 1760 Hz 사인, 길이 0.08 s, 지수 감쇠 `exp(−40 t)`. 진폭만 칸마다 다르다 [carried: `tools/barmap/make_phase_clicks.py:22-24` 의 `_click`] |
| 표본율 | 44100 Hz [carried: `tools/barmap/make_phase_clicks.py:18`] |
| 칸 수 | 96 (PR-12). 짧은 입력은 24 |
| 칸 빈도 | 시드마다 분당 90~130회에서 균등 추출 [predicted]. 생성기 매개변수이고 곡 고유값이 아니다 |
| 진폭 흔들림 | 칸마다 ±10 % 균등 [predicted] |
| 잡음 | 백색 가우시안, 표준편차 0.01 [predicted] |
| 첫 칸 시각 | 시드마다 0.3~0.8초 [predicted] |

**강세 패턴.** 단서 수준 c에서 칸 k의 상대 진폭은 `pattern_N[k mod N]`이다. 중강 m = (1 + c) / 2.

| 분자 | 패턴 |
|---|---|
| 3 | [1.0, c, c] |
| 4 | [1.0, c, m, c] |
| 6 | [1.0, c, c, m, c, c] |

**단서 수준.** 강(c = 0.4), 중(c = 0.7), 약(c = 0.9), 없음(c = 1.0, 모든 칸 같은 세기) [predicted].

**6/8의 칸 조건.** 6칸이 한 마디인 픽스처는 칸 빈도가 위 범위(분당 90~130칸)에 있다. 곧 점4분 템포로는 분당 30~43회인 아주 느린 6/8에 해당한다 [predicted: 산술, 90÷3과 130÷3]. 이 숫자 범위는 §3.3의 한정(8분음표 펄스)을 합성 쪽에서 만족시키기 위한 것이고, 실제 6/8 곡이 이 범위에 든다는 주장이 아니다.

### 7.3 칸(cell)과 문턱

칸 하나 = (가족, 분자, 단서 수준) 조합이며 시드 30개로 돈다(PR-11).

| 관문 | 대상 칸 | 통과 조건 |
|---|---|---|
| 재현율 | 클릭 가족 × 분자 {3, 6} × 단서 {강, 중} | 확신이면서 N이 정답인 시드가 30개 중 27개 이상 (PR-13) |
| 대조군 | 클릭 가족 × 분자 4 × 단서 {강, 중} | 결과 N=4(확신이든 추정이든)가 30개 중 29개 이상 (PR-14) |
| 오확신 | 모든 게이트 칸과 드럼 가족 칸 | 확신이면서 N이 정답과 다른 시드가 칸당 1개 이하 (PR-15). 분자 4 대조군의 거짓 양성 상한이 이 줄이다 |
| 단서 없음 | 클릭 가족 × 분자 {3, 4, 6} × 단서 없음, 그리고 짧은 입력 | 추정(N=4)이 30개 중 29개 이상이고 곡 거절이 0개 (PR-16) |
| 참고 | 약 단서 | 수치만 적는다. 문턱 없음 |

**왜 약 단서를 문턱에서 뺐나.** 약 단서는 진폭 흔들림(±10 %)과 강세 차(0.1)가 비슷한 크기라 검정력이 경계에 있다 — 문턱을 걸면 설계 결함이 아니라 시드 운이 판정한다.

### 7.4 관문 자신이 공허하지 않음을 보이는 음성 대조군

관문이 어떤 판별기든 통과시키면 쓸모가 없다. 같은 관문 함수에 다음 두 대역을 넣어 FAIL이 나와야 한다(AC-LDBARMETER-001).

- 항상 `확신, N=4`를 내는 판별기 → 재현율 칸 (3/4, 6/8)에서 0/30으로 FAIL이어야 한다.
- 항상 `추정, N=4`를 내는 판별기 → 재현율 칸에서 FAIL이어야 한다(오확신 줄은 통과하지만 재현율이 0이다).

### 7.5 G-B의 칸 일치

추적기가 낸 칸 간격의 중앙값이 생성 간격의 ±5 % 안이면 「칸 일치」다(PR-18). 시드 30개 중 27개 이상이 일치해야 한다(PR-17). 일치한 시드에서는 G-A와 같은 문턱을 적용한다. 일치하지 않은 시드는 재현율 분모에 남기고 실패로 센다.

### 7.6 드럼 가족

킥(60 Hz 사인 + 클릭)을 칸마다 패턴 진폭으로 치고, 닫힌 하이햇(고역 잡음 버스트, 진폭 0.3)을 칸 사이 중간점마다 친다. 목적은 두 가지다 — 하위 박 에너지가 있을 때 BPM 배수 검사가 `adopt_double`로 뒤집지 않는지, 뒤집히지 않은 입력에서 판별기가 오확신하지 않는지. 문턱은 오확신 상한(PR-15)과 곡 거절 0개다. 재현율과 `adopt_double` 비율은 수치만 적는다. `adopt_double`이 나온 시드는 기존 규칙으로 거절되므로(U-0) 재현율 분모에서 빼고 개수를 따로 적는다.

근거: 같은 종류의 입력(균일 박 + 8분 하이햇)이 기록상 `keep`으로 나왔다(`.moai/reports/t547/probe_synth.txt` 의 「112 박+8분 하이햇 0.3」행, `p_mid = 8.98e-12` [carried: `.moai/specs/SPEC-LDBARMAP-001/research.md:142`]). 이 설계는 그 결과를 재현할 것이라고 예측하지 않는다 — 드럼 가족이 실제로 재는 것이다.

### 7.7 2/4 픽스처(참고)

패턴 [1.0, c], 칸 96, 단서 {강, 중}. 문턱을 걸지 않는다. 판별기 결과 분포(N과 상태)를 적는다. 2는 후보가 아니므로 결과는 4이거나 추정 4가 된다 — 이 분포가 §3.2의 「성긴 경계」 주장을 합성에서 확인하는 자료다.

### 7.8 관문이 실패했을 때

§6.3 절차를 따른다. 문턱을 고쳐서 통과시키지 않고, M2를 시작하지 않는다(REQ-LDBARMETER-013).

## 8. BPM 배수 검사와의 상호작용

두 검사는 **서로 다른 방향**을 본다.

- BPM 배수 검사(SPEC-LDBARMAP-001 REQ-LDBARMAP-006 계열, `bar_map.py:311-438` [carried]): 칸 **사이**(중간점)가 칸보다 센가 — 칸이 진짜 박의 절반 빠르기인지 묻는다.
- 박자 판별: 칸 **위**(3칸·4칸 묶음)의 강세 구조 — 칸을 몇 개 묶어 마디로 삼는지 묻는다.

순서와 규칙은 다음과 같다.

| 순서 | 단계 | 규칙 |
|---|---|---|
| 1 | `detect_beat_grid` | 칸 시각, `bpm`, `bpm_check`, 칸 세기를 낸다 |
| 2 | 두 배 거절 | `bpm_check.outcome == adopt_double`이면 기존대로 거절(`bar_map_entry.py:146-152` [carried]). 박자 판별은 실행하지 않는다 (U-0) |
| 3 | 박자 판별 | `bpm_check.ambiguous`이면 추정 (U-1). 그 밖에는 §5를 따른다 |
| 4 | 마디 파생 | 판별한 N으로 `derive_bars` |

- 박자 판별은 칸 시각, `bpm`, 두 배 판정 결과를 **읽기만 한다**. 바꾸지 않는다(REQ-LDBARMETER-004).
- 절반 후보는 지금처럼 자동 채택하지 않는다(`bar_map.py:73-74` [carried]). 칸이 진짜 박의 절반 빠르기로 잡힌 곡은 두 배 검사가 `adopt_double`로 거절하는 쪽이거나, 감지하지 못해 판별이 칸 단위로 N을 센다.
- `adopt_double` 거절은 P1(어떤 음악이든 진행)과 문면상 부딪힌다. 이 SPEC은 BPM 확정 계약과 그 거절을 바꾸지 않는다 — 바꿀지는 열린 질문이다(spec.md OQ-5).

## 9. 「박자 추정」 표지와 OD-3

### 9.1 표지 계약

- **언제**: 판별 상태가 추정일 때만. 확신이면 표지가 없다.
- **어디에**: 저장 성공 응답(`chat_response`)의 본문(`text`)에 「박자 추정」 문구를 싣는다. 요약(`summary`) 라벨은 늘리지 않는다 — 성공 요약은 저장 관문이 정하는 고정 라벨이고(`server/web/session.py:9457-9460` [carried]), 요약 라벨 집합을 늘리면 응답 라벨 목록을 고정해 둔 쪽(후속 UI 카드)을 건드린다.
- **몇 번**: 성공 응답은 지금처럼 정확히 1개다(SPEC-LDBARMAP-002 REQ-LDBARENTRY-012). 표지 때문에 응답을 하나 더 보내지 않는다.
- **사유 코드**는 응답에 싣지 않고 로그에만 남긴다(분석 실패 원문을 로그에만 남기는 기존 관행과 같다, `session.py:9521-9523` [carried]).

### 9.2 OD-3 — 표지를 어디에 저장하는가 (미결 — 착수 승인 게이트에서 감독 확정)

SPEC-LDBARMAP-001 P3의 저장 검증은 알 수 없는 필드를 거절한다(`server/audio/bar_map_store.py:175-177` [carried]). 표지를 저장하려면 이 제약을 어떻게든 피해야 한다.

**선택지 1 (기본안) — 저장하지 않는다. 응답에만 싣는다.**

- 근거(코드): 성공 응답은 저장 관문이 만든다(`session.py:9457-9466` [carried]). 표지는 관문에 선택 인자(문구 한 줄)를 넘겨 그 응답의 본문에 붙이는 방식으로 실린다. 진입 메서드는 성공을 「방금 넘긴 페이로드가 읽혀 나오는지」로 가르므로(`session.py:9569-9572` [carried]) 페이로드 모양은 건드리지 않아도 된다.
- 바뀌지 않는 것: `validate_bar_map` 본문, `_TOP_LEVEL_KEYS`(`bar_map_store.py:54-56`), SPEC-LDBARMAP-001 §5 모양, SPEC-LDARRANGE-001 미러 문단, SPEC-LDBARMAP-002 REQ-LDBARENTRY-010의 「그 밖의 키는 바이트까지 같다」.
- 치르는 값: 표지가 **저장되지 않는다.** 연결을 다시 맺으면 서버가 저장된 타임라인을 다시 밀어 주는데(`server/web/app.py:535` [carried], `session.py:10388` [carried]) 거기에는 표지가 없다. 추정으로 만든 4/4 지도가 새 연결에서는 확신한 4/4와 구별되지 않는다. 라이브러리 저장(`SongTimelineLibrary`)에도 실리지 않는다.

**선택지 2 — 저장한다.** 두 갈래가 있다.

- **2a. 마디 지도 사전 안의 선택 필드**(예: 최상위 키 하나). 근거(코드): 최상위 키 집합이 여섯 개로 고정돼 있고(`bar_map_store.py:54-56`) 알 수 없는 필드와 빠진 필드를 둘 다 검사한다(`:175-180`). **검증기 본문이 바뀐다.** 저장 형태를 담은 SPEC-LDBARMAP-001 §5(`spec.md:147-160`)와 AC-LDBARMAP-010·011(`acceptance.md:167-190`), SPEC-LDARRANGE-001 §5 미러 문단, 저장 시험이 같이 움직인다.
- **2b. 타임라인의 형제 키**(`bar_map`과 같은 단계의 새 키). 근거(코드): `attach_bar_map`은 `bar_map` 키 하나만 쓴다(`bar_map_store.py:338-339`) — **검증기는 그대로**다. 하지만 SPEC-LDBARMAP-002 REQ-LDBARENTRY-010이 저장 성공 때 `bar_map`과 `draft` 표식 밖의 키를 바이트까지 같게 둔다고 약속하므로(`spec.md:111` [carried]) 그 요구를 개정해야 한다. `store_timeline_bar_map`이 두 키를 한 번의 되돌리기 기록 안에서 같이 써야 하고(`session.py:9450-9455`), `song_timeline` 프레임에 새 키가 실린다. 타임라인 저장소가 알 수 없는 최상위 키를 보존하는지는 읽지 않았다.

**기본안을 선택지 1로 둔 이유.**

1. SPEC-LDBARMAP-001의 검증기 본문을 바꾸지 않는 두 안(1, 2b) 가운데 SPEC-LDBARMAP-002의 요구까지 건드리지 않는 것은 1뿐이다.
2. 같은 종류의 문제를 다른 SPEC이 이미 다루고 있다 — 형제 워크트리의 SPEC-LDBARMAP-004(draft)는 REQ-LDBARLEN-002에서 자기 기록이 마디 지도 사전 안에 들어가지 않고 최상위 키 집합(여섯 개)과 `validate_bar_map`이 바뀌지 않는다고 적었고(`../WT-barmap-song-match/.moai/specs/SPEC-LDBARMAP-004/spec.md:94`), 저장 성공 때 타임라인의 다른 키가 바뀌면 REQ-LDBARENTRY-010 개정이 필요하다고 적었으며(`:188-198`, `:223`), 자기 기록의 자리를 기존 키 `total_duration_ms`로 확정했다(`:123`) [carried — 이 트리의 파일이 아니다. 다른 세션이 계속 고치는 파일이라 이 plan-phase가 두 번 읽는 사이 줄 번호와 내용이 바뀌었다]. 표지의 저장 자리는 그 SPEC의 결정과 함께 정하는 편이 일관된다.
3. 표지를 화면에 보이는 일은 이 SPEC의 범위 밖이다(Out of Scope). 읽는 쪽이 없는 상태에서 저장 모양을 먼저 확정하지 않는다.

**기본안의 위험을 숨기지 않는다.** 위 「치르는 값」이 P3의 목적(추정으로 만든 지도를 사람이 알아본다)을 첫 응답 이후에는 지킨다고 말할 수 없게 만든다. 이 판단은 감독의 몫이므로 OD-3은 열어 둔다.

## 10. 첫 박 오프셋과 OD-4

첫 박 오프셋은 사람이 지정한 정수로 남는다(D-3). 분석기는 이 값을 추정하거나 기본값으로 채우지 않는다.

- 유효 범위는 판별한 분자 N에 따라 0 ~ N−1이다(SPEC-LDBARMAP-001 §5 열린 결정 0의 일반 규칙, `spec.md:147`, `:160` [carried]).
- **오디오를 풀기 전의 싼 점검**(SPEC-LDBARMAP-002 REQ-LDBARENTRY-007)은 분자를 모르는 시점에 돈다. 그래서 형식(정수, bool 아님)과 음수 여부, 그리고 **후보 분자의 최댓값 − 1 = 5**를 넘는지만 본다. 현재의 `0..3` 점검(`bar_map_entry.py:88-89`, `bar_map.py:454-457` [carried])은 이 점검으로 대체된다.
- 정확한 범위 판정은 분자가 정해진 뒤에 한다.

**OD-4 — 오프셋이 판별한 분자 이상일 때 (미결).** 예: 오프셋 3인데 판별이 3/4. 이 SPEC은 정하지 않는다. 선택지만 적는다.

| 선택지 | 내용 | 코드 근거 |
|---|---|---|
| (i) 거절 | 오프셋 전용 사유로 거절한다(`KIND_REJECTED`). 박자를 이유로 한 거절은 아니지만 판별 결과에 따라 거절이 생기는 점이 P1과 닿는다 | 기존 거절 경로 `bar_map_entry.py:134-136` |
| (ii) 나머지로 줄임 | `offset mod N`으로 줄여 진행한다. 다운비트 집합은 같지만 못갖춘마디 길이와 마디 번호가 사람의 기대와 달라진다 | 못갖춘마디 처리 `bar_map.py:464`, `bar_map_store.py:129-134` |
| (iii) 후보 배제 | 오프셋 ≥ N인 후보를 판별에서 빼고 남은 후보로 다시 정한다. 후보가 없으면(오프셋 ≥ 6) (i)로 간다 | 판별기 입력에 오프셋이 들어간다 — D-3과 판별의 독립성이 흐려진다 |

## 11. 회귀 기준선 캡처 절차

### 11.1 기준 곡

저장소 기록의 10곡이다 — LOVE ATTACK 1곡과 샘플 폴더 9곡(`.moai/reports/t547/after_songs.txt`의 곡 열 [carried: `.moai/specs/SPEC-LDBARMAP-001/progress.md:700-701`], 곡 목록의 출처 `.moai/reports/t547/probe_songs.py:31-48`). 「11곡」이라는 진술은 저장소에서 확인하지 못했다(research.md §3). 곡별 박자표 라벨은 저장소에 없다 — 회귀 기준은 「참 박자」가 아니라 「현행 분석 결과와 같다」이다.

### 11.2 언제 캡처하는가

**M2가 `bar_map.py`를 바꾸기 전에** 한다(plan.md M1의 첫 단계). M2 뒤에 캡처하면 새 코드를 새 코드와 비교하게 된다.

### 11.3 무엇을 저장하는가 — 숫자만

곡마다 한 항목. 오디오는 담지 않는다.

| 필드 | 뜻 |
|---|---|
| `file_name` | 파일 이름 (경로는 적지 않는다) |
| `sha256` | 오디오 파일의 SHA-256. 같은 파일에서 잰 값인지 확인한다 |
| `outcome` | `grid` 또는 `failure` 또는 `rejected_adopt_double` |
| `beat_times_ms` | 칸 시각 정수 목록 (`outcome == grid`일 때) |
| `bpm` | 소수 여섯 자리 |
| `bpm_check` | `outcome`·`ambiguous` 값 |
| `failure_reason` | 실패일 때 사유 원문 |

파일 맨 위에는 캡처한 커밋, 파이썬·`librosa`·`numpy`·`soundfile` 버전, 캡처 날짜를 적는다 — 박 추적이 라이브러리 버전에 따라 달라질 수 있기 때문이다 [predicted: 버전 의존 가능성은 측정하지 않았다].

저장 위치(가칭): `.moai/reports/t656/meter-baseline.json`.

### 11.4 캡처 절차

1. 오프셋을 곡마다 따로 고르지 않는다. 마디 경계는 칸 목록과 오프셋 k ∈ {0, 1, 2, 3}에서 `(i − k) % 4 == 0`으로 정해지므로, 칸 목록 하나가 네 오프셋의 경계를 모두 결정한다.
2. 캡처 도구(가칭 `tools/barmap/capture_meter_baseline.py`, 로컬 전용)가 곡 파일 목록을 인자로 받아 `detect_beat_grid`를 돌리고 위 필드를 쓴다. 곡 경로는 저장소 밖에서 읽는다.
3. **결정성 점검.** 캡처를 두 번 돌려 결과 파일이 같음을 확인한 뒤에만 기준선으로 채택한다. 다르면 채택하지 않고 원인을 찾는다(디코드·추적의 비결정성).
4. 캡처 커밋의 SHA를 기준선 파일과 progress.md에 적는다.

### 11.5 비교 절차 (M3)

곡마다 새 분석기를 돌려 다음을 적는다.

- 칸 시각 목록이 기준선과 같은가 (같아야 한다 — `detect_beat_grid`는 이 SPEC이 바꾸지 않는다).
- 오프셋 0·1·2·3 각각에서 새 분석기의 다운비트·마디 경계 목록이 기준선에서 `(i − k) % 4 == 0`으로 만든 목록과 같은가.
- 새 분석기의 N과 상태(확신/추정)와 사유 코드.

곡 10개 × 오프셋 4개 = 비교 40번. 판정은 40번 모두 같아야 PASS다. 기준선의 `outcome`이 `failure`나 `rejected_adopt_double`인 곡은 새 분석기도 같은 종류로 끝나야 같은 것으로 센다.

**M3가 실패하면.** 다른 N을 확신한 곡의 목록과 칸 시각 차이를 progress.md에 그대로 적고 멈춘다. 문턱을 그 결과에 맞춰 바꾸지 않는다(§6.3). 다음 단계는 감독 결정이다.

**증거 형식.** 실제 곡 표에는 「정답/정확도」 열을 만들지 않는다 — 열은 곡, N, 상태, 사유 코드, 40번 비교의 일치 개수, 처음 다른 인덱스다(REQ-LDBARMETER-015).
