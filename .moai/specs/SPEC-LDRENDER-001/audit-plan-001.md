Whichever direction is chosen, it must be a *stated* judgment, not silence.

D2. **req-004-uncited-color-role-assignment** — `spec.md:57` (REQ-LDRENDER-004) — REQ-LDRENDER-004 assigns the primary color (`palette[0]`) to the `KEY/FOH`+`WASH` role groups and all secondary colors (`palette[1:]`) to `BACK`+`SIDE` role groups. Two concerns, both unaddressed: (1) **§6.3 risk** — `docs/proposals/song-structure-lighting-standard.md` §6.3 (line ~230 area, confirmed via `awk` extraction) states "동시에 보이는 색은 최대 2개(지배색 1 + 액센트 1)" (at most 2 simultaneously-visible colors: 1 dominant + 1 accent). `ColorPlan.palette: tuple[str, ...]` is variably sized (REQ-004's own Given is "팔레트가 2개 이상의 색을 담고 있으면" — 2 **or more**). If a palette ever carries 3+ distinct colors, REQ-004 as written sends 3+ distinct simultaneous colors across KEY/FOH/WASH (palette[0]) + BACK/SIDE (palette[1], palette[2], ...) — a direct §6.3 violation the REQ does not guard against. (2) **§6.2 risk** — §6.2 states "프론트 필은 밝은 워시가 아니라 **부드러운 보정광으로 항상 유지**한다" (front fill is kept as a soft correction light, not a bright wash). `FOH` is canonically defined in `src/Lighting_Designer/01_스펙/LX-SEQ-SPEC-v2.1.md` §2.2 as "전면 페이스 라이트" (front face light) — the front-fill role §6.2 describes. REQ-004 sends FOH the same fully-saturated `palette[0]` value as KEY and WASH, with no soft-correction-light treatment, and no citation discusses this. Unlike R1's prefix-policy ambiguity and R4's two-option fork — both explicitly flagged in spec.md §5 "열린 결정" — this specific layer-to-color assignment is presented as settled fact with a citation (spec.md:57 grounds-column) that only supports "palette[0] alone is dropped today", not the specific KEY/FOH·WASH vs BACK·SIDE split. No source (t499, t498, the lighting standard, or the LDDESIGN mapping-card precedent) was found that assigns colors to roles this way. — Severity: **major** — Class: **blocking** — Required fix: Either (a) cite the actual source of this layer→color assignment, or (b) move it to spec.md §5 as a third open decision requiring director confirmation, and (c) regardless, add an explicit guard/REQ clause bounding simultaneous-color count to ≤2 per §6.3 when `len(palette) > 2`.

D3. **ac-006-narrow-verification-scope** — `acceptance.md:40-45` (AC-LDRENDER-006) / `spec.md:65` (REQ-LDRENDER-007) — The card's completion condition states "블라인더/스트로브 액센트 밖 점등 0" (blinder/strobe lit outside accent cues = 0). REQ-007 and AC-006 both scope narrowly to "전체 기구 키 디머 값 줄" (the one `position_cue_bundle`-authored dimmer line) and assert only that this one line's `fids` selection excludes the effect-role group. Per `research.md` §1 (R3 row) and t499 §3 P3, the renderer's current architecture shares **one** `fids` set across the position, dimmer, color, and phaser lines (`song_cue_render.py:1000` `reviewed_song_commands` → `:1028` color, `:1044-1052` `position_cue_bundle(... fids, extra_value_lines=(...))`). REQ-007/AC-006 do not state whether M4's fix updates the *shared* `fids` (which would also stop color/position/phaser lines from addressing effect fixtures) or only builds a second, narrower selection for the dimmer line alone while color/position/phaser continue to include effect fixtures. If the latter, STROBE fixtures in particular may carry a distinct shutter/strobe-rate attribute that could be driven non-zero by a line other than the key dimmer line, independent of dimmer=0 tracking — a case AC-006's single-line check would not catch. — Severity: **major** — Class: **blocking** — Required fix: Either broaden REQ-007/AC-006 to assert the exclusion holds for *every* value line sharing the `fids` selection (not just the dimmer line), or explicitly state in plan.md why checking the dimmer line alone is sufficient to guarantee "0 lit outside accent cues" (e.g., cite that MA3 attributes other than Dimmer cannot independently drive visible brightness/strobing for the specific fixture types in this rig).

D6. **rig-layer-roles-closed-vocabulary-ungrounded** — `spec.md:50` (REQ-LDRENDER-002) / `plan.md:60` (M2) — REQ-002 and M2 both scope the SIDE/WASH/MOVER role-recognition change to extending `server/design/rig.py` `_LAYER_GROUP_ALIASES` (the group-name-heuristic alias table). However, `server/design/rig.py:45` defines a **separate, structurally-enforced** closed vocabulary: `RIG_LAYER_ROLES: tuple[str, ...] = ("key", "back", "effect", "audience")`, documented in the module docstring as "closed on purpose — a role outside this set is a caller typo, not a new role the standard recognises" (rig.py:41-45). This tuple is actively consulted and enforced: `rig.py:305-308` (`_build_layers`) raises `RigProfileError(f"declared layer role {role!r} is not one of {RIG_LAYER_ROLES}")` whenever the **explicit declaration path** (`declared_layers`, RG5 highest-priority source) carries a role not in this tuple. Per plan.md §B.2 itself, the layer-mapping confirmation flow (`_confirm_song_layer_mapping`, SPEC-LDDESIGN-001) feeds `declared_layers` via `server/web/session.py:7550-7556` (`declared_layers = {str(entry["role"]): ... for entry in layer_mapping ...}` → `build_rig_profile(..., declared_layers=declared_layers)`). If `side`/`wash`/`mover` are introduced only into `_LAYER_GROUP_ALIASES` (the heuristic path, which does NOT validate against `RIG_LAYER_ROLES` per rig.py:314-319) but the mapping-confirmation UX actually declares roles through the `declared_layers` path, any song whose confirmed mapping names `side`/`wash`/`mover` will raise `RigProfileError` at runtime. Neither spec.md, plan.md §B (Known Risks), nor research.md mention `RIG_LAYER_ROLES` at all — this is a load-bearing architectural constraint the SPEC's own grounding missed. — Severity: **major** — Class: **blocking** — Required fix: Add `RIG_LAYER_ROLES` extension (or an explicit decision to keep it closed and route side/wash/mover only through the heuristic path, with a stated rationale for why the explicit-declaration path won't need them) to REQ-LDRENDER-002 and plan.md §B/M2, and add a regression check that `_build_layers`'s `declared_layers` path accepts the three new roles without raising.
