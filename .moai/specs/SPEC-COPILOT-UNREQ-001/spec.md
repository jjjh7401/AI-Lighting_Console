# SPEC-COPILOT-UNREQ-001 — 요청되지 않은 쇼파일 쓰기를 응용 층에서 잡는다

> **칸반 카드 t86 에서 파생.** t86 은 「게이트가 Store/Label Preset 을 승인 없이 통과시킨다」를
> 조사했고, 통과시키는 것은 맞으나 그것이 **간과가 아니라 비준된 상태**임을 실측했다.
> 이 SPEC 은 그 비준을 뒤집지 않고, 게이트가 구조적으로 볼 수 없는 축 — **요청 여부** — 을
> 응용 층에서 다룬다.

## A. 개요

### A.1 t86 이 잰 것 — 이 SPEC 의 전제

전부 워크트리 `.claude/worktrees/t86`, 커밋 `8723c97`, 룰셋 `version: 3` 에서 직접 관측했다.
원문 증거: `.moai/reports/t86/measurement.md` (`origin/WT-preset-gate`). 콘솔 발사 0건.

**① 분류**: `Store` 는 `/overwrite` 옵션이 붙을 때만 걸린다. 옵션이 없으면 대상 무관 `safe`
(Preset·Group·Cue·Sequence·Executor·Macro·World·View 전부 실측). `Label` 은 룰셋에 아예 없다.
`gate.py::_stage_classify` 가 `hold = verdict.risky` 이므로 `safe` 는 승인 카드를 안 띄운다.

**② 비준 상태**: `test_writegate.py::UNCHANGED_SAFE` 가 `Store Preset 4.1`·`Store Group 3`·
`Store Cue 12`·`Store Page 3`·`Store Macro 21`·`Assign …`·`Copy …` 를 「분류가 움직이면 안 되는
문형」으로 못박는다. `Label Group 3 'Vocals'` 는 사유가 다르다 — 「labelling is not a patch write」,
비용이 아니라 의미 판단이다.

**③ 게이트 개정 비용** (전량 스위트, 기준선 10167 통과 · 0 실패):

| 넣은 항목 | 코퍼스 | 실패 | 총 테스트 |
|---|---|---|---|
| — (기준선) | 0/21 | **0** | 10179 |
| `Store Preset` | 2/21 | **13** | 10183 |
| `Store Preset` + `Label Preset` | 2/21 | **13** | 10187 |
| `Label` | 9/21 | **17** | 10183 |
| `Store` | 10/21 | **67** | 10183 |
| `Store` + `Label` | 10/21 | **70** | 10187 |

`Store Preset` 단독과 `Store Preset`+`Label Preset` 의 실패 **갈래 분포가 동일**하다
(looks_instantiate 6 · measurement_runner 4 · writegate 2 · safety_ruleset 1).
즉 A 의 13건은 전부 `Store Preset` 몫이고 `Label Preset` 은 0건을 더한다.

**④ 코퍼스 지표는 비용 척도로 못 쓴다**: `Store` 10/21 과 `Label` 9/21 은 거의 같은데 파괴는
67 대 17, 약 4배다. `blacklist.yaml` 헤더의 descope 판단은 코퍼스 시나리오 수 위에서 내려졌다.
방향은 옳았으나 **비용을 과소평가한 값으로** 내려졌다 — 결정을 뒤집는 게 아니라 강화하는 발견이다.

**⑤ 정상 대화가 승인 카드를 탄다**: `Store` 전체를 넣으면
`test_web_session::TestHappyPath::test_korean_instruction_executes_and_reports_in_korean`
이 깨진다. 테스트를 고쳐 넘길 문제가 아니라 제품 동작이 바뀐다는 신호다.

### A.2 측정 단위의 함정 — 분모가 움직인다

블랙리스트에 항목을 넣으면 `test_writegate.py` 가 그 항목을 순회해 **테스트 자체가 늘어난다**
(항목 1개당 4건, 위 표의 「총 테스트」 열). 따라서 「실패 N건」은 고정 분모 위의 값이 아니다.
본 SPEC 이 산출하는 모든 비용 수치는 **분모를 함께 기재**한다.

## B. 배경과 문제

### B.1 사고

LXSEQ-003 M4 에서 사용자가 요청하지 않은 프리셋 1건이 콘솔에 생성됐다.
명령 형태는 `session.py:2951 _preset_store_commands` 가 만드는
`Store Preset <pool>.<n>` + `Label Preset <pool>.<n> '<label>'` 이다 — A.1 ① 표의 첫 두 줄이며,
승인 카드 없이 통과한다.

### B.2 두 층이 같은 절반만 덮는다

| 층 | 무엇을 막나 | 신규 생성은? |
|---|---|---|
| 게이트 (`Store /overwrite`) | 덮어쓰기 | 안 막음 |
| 응용 (PRESETGUARD-001) | 덮어쓰기 (점유 검사 · 되읽기) | **설계상 통과** — 빈 슬롯이면 쓴다 |

두 층이 함께 덮는 것은 덮어쓰기이고, **빈 슬롯 신규 생성은 어느 쪽도 안 덮는다.**
사고가 정확히 그 경로였다.

### B.3 게이트로는 풀 수 없는 이유

사고의 본질은 `Store Preset` 이라는 **문형**이 아니라 *사용자가 요청하지 않은 쓰기가 나갔다*는
것이다. 그런데 게이트는 설계상 **명령 구문만** 본다 — `classify.py` 모듈 독스트링이
「Classification is command-SYNTAX based」라고 스스로 적었다. 의도는 구문에 없다.
게이트를 아무리 넓혀도 「요청된 `Store Preset`」과 「요청되지 않은 `Store Preset`」을 구별할 수
없고, 넓히면 A.1 ⑤ 처럼 요청된 쪽까지 함께 막는다.

### B.4 원리는 이미 코드 한 자리에 있다

`session.py::_position_cue_store` 독스트링:

> The sequence number comes from the instruction or ONE question card — `Store` on an occupied
> cue changes a show object, so the number is the operator's call.

즉 「대상 번호가 지시에 없으면 조용히 고르지 말고 질문 카드를 띄운다」는 판단이 이미 한 경로에
구현돼 있다. 2026-08-16 사용자 방향(`session.py:7926`)도 같다 — 「an occupied run is a QUESTION,
not a dead end」. 이 SPEC 은 새 원리를 도입하는 것이 아니라 **이미 한 자리에 있는 원리의
적용 범위를 재는 것**부터 시작한다.

## C. 범위

### C.1 In Scope

1. **M1 — C 의 비용 측정 형태를 설계하고 실행한다** (본 SPEC 의 게이트, C.4 참조)
2. **M2 — 측정값을 근거로 적용 범위를 확정한다** (어느 쓰기 경로에 대조를 붙일지)
3. **M3 — 요청 대조와 질문 카드를 구현한다** (M1 이 통과했을 때만)
4. **M4 — 게이트 클로즈드셋 v3→v4: `Store Preset` 1항목 추가** (13건, A.1 ③)

### C.2 Out of Scope

- **`Label` 계열 전체** — 사유가 비용이 아니라 의미 판단(「labelling is not a patch write」)이라
  다른 논증이 필요하다. 별도 카드. 게이트 비용 면에서 분리 가능함은 실측됐다(A.1 ③: `Label
  Preset` 이 `Store Preset` 위에 0건을 더한다).
- **`Store` 동사 전체 (갈래 B)** — 2026-08-05 사용자 결정이 유효하고, t86 실측이 그 결정을
  강화했다. 재론하려면 새 근거가 필요하다.
- **`Assign` · `Copy`** — 코퍼스 비용만 쟀다(2/21 · 1/21). 전량 스위트 미측정.
- **`St Preset 1.1 /o` 축약 구멍** — 카드 t91 이 소유한다.
- **MA3 실기 확인 일체** — 이 SPEC 은 콘솔에 아무것도 쏘지 않는다.

### C.3 Out of Scope 근거 — Label 을 왜 빼는가

`Store` 계열의 descope 사유는 **비용**이므로 t86 의 비용 실측이 그 판단을 직접 갱신한다.
`Label` 의 사유는 **의미 판단**이라 비용 수치로는 갱신되지 않는다 — 「패치 쓰기가 아니다」가
참인지 거짓인지를 논해야 한다. 참고로 그 판단에는 반론 여지가 있다: 게이트가 지키는 것은
「패치 쓰기」보다 넓은 **쇼파일 상태**이고(`Set Fixture` 항목 주석이 스스로
「A fixture's patch row is SHOWFILE STATE」라고 적었다), 개체 이름 변경도 쇼파일 상태 변경이다.
그 논증은 이 SPEC 의 범위가 아니다.

### C.4 M1 은 단계가 아니라 게이트다

[HARD] **M1 의 산출 수치가 나오기 전에 M2·M3 에 착수하지 않는다.**

근거: 2026-08-05 판단은 **비용 척도가 부적합한 상태에서** 내려졌고(A.1 ④), 그 실수를 방향만
바꿔 반복하는 것이 이 SPEC 의 가장 큰 실패 모드다. 갈래 A(13건)·B1(67건)·B2(17건)는
같은 단위의 수치가 있는데 C 만 없다. 척도 없이 C 를 고르면 「게이트보다 응용 층이 낫다」는
말은 근거 없는 선호에 지나지 않는다.

## D. 요구 (GEARS)

- **REQ-UNREQ-002** `[Ubiquitous]` 산출 단위는 A·B 와 동일해야 한다 — ① 걸리는 시나리오 수
  (n/21), ② 걸리는 명령줄 수, ③ 전량 스위트 파괴 수(분모 명기).
- **REQ-UNREQ-003** `[Ubiquitous]` 하네스는 **날조 대조군**을 포함해야 한다 — 명백히 요청된
  쓰기(지시에 번호가 명시된 시나리오)가 걸리지 않음을 같은 실행에서 보여야 한다.
  대조군 없는 0 은 증거가 아니다.
- **REQ-UNREQ-004** `[State-driven]` **While** 판정이 「지시에 번호가 없다」에 근거할 때,
  하네스는 그 시나리오를 **판정 불가**(사용자가 슬롯 선택을 위임한 경우)와 **요청되지 않음**
  으로 갈라 세어야 한다. 두 부류를 한 숫자로 합치면 안 된다.

### D.2 M2 — 범위 확정

- **REQ-UNREQ-005** `[Event-driven]` **When** M1 의 수치가 나오면, 적용 범위는 그 수치에 근거해

- **REQ-UNREQ-006** `[Unwanted]` **(D.5 로 개정 — 아래 조건은 두 중단 조건 중 ①에 해당)** **If** M1 의 「판정 불가」 비율이 「요청되지 않음」을 넘으면,
  **then** 이 접근은 갈래 B 와 같은 마찰 문제를 다른 경로로 재현하는 것이므로 중단하고
  대안을 재검토해야 한다.

### D.3 M3 — 구현 (M1 통과 시에만)

  새 UI 를 만들지 않는다.
- **REQ-UNREQ-009** `[Ubiquitous]` 게이트는 변경하지 않는다 — M3 는 응용 층에서만 산다.

### D.4 M4 — 게이트 개정 v3→v4

- **REQ-UNREQ-010** `[Ubiquitous]` `blacklist.yaml` 에 `Store Preset` 1항목을 추가하고

- **REQ-UNREQ-011** `[Ubiquitous]` 개정 이력은 이 파일 헤더의 기존 절차를 따라야 한다 —
  위양성 관측 근거(LXSEQ-003 M4 사고) + 비용 실측(13건/10183) + 범위 명시.
- **REQ-UNREQ-012** `[Ubiquitous]` `UNCHANGED_SAFE` 에서 `Store Preset 4.1` 을 제거하고,

  비준을 말없이 지우면 안 된다.
- **REQ-UNREQ-013** `[Ubiquitous]` 헤더에 **분모가 움직인다는 사실**(A.2)을 기재해야 한다 —
  이후 개정이 「실패 N건」을 고정 분모 위의 값으로 오독하지 않도록.

### D.5 중단 임계의 근거 — REQ-UNREQ-006 개정

**개정 사유 (2026-08-25, 리드 감사).** 최초 REQ-UNREQ-006 은 중단 임계를
「판정 불가 ≥ 요청되지 않음」 하나로 두었다. 그 1:1 값에 **근거가 SPEC 어디에도 없었다.**
뒤집으면 판정 불가가 요청되지 않음보다 하나만 적어도 통과하므로, 신호대잡음 1:1 을 합격선으로
두는 셈이다. B 를 기각한 이유가 「마찰이 정상 동작에 떨어진다」였는데 1:1 이면 그 마찰이
상당량 남아도 통과한다.

**개정 시점이 M2 전이 아니라 M1 측정 전인 이유.** 임계의 반편향 성질은 「측정 전에 정해졌다」는
데서 나온다. M1 이 숫자를 만드므로, 숫자를 본 뒤 조이면 사후 조정이 되어 G.2 가 막으려던 편향이
바로 그 자리로 돌아온다. 그래서 M1 하네스를 짜기 전에 확정한다.

**중단 조건은 둘이고, 하나라도 걸리면 M1 불통과다.**

- **조건 ① (기존 유지)** — 판정 불가 ≥ 요청되지 않음.
- **조건 ② (신설)** — 판정 불가가 대표 과업 유형(`corpus.task_type`, 10종) 중
  **1종 이상을 통째로** 덮으면 불통과.

**조건 ②의 근거는 이 저장소가 이미 쓴 기준이다.** `test_writegate.py` 의 `UNCHANGED_SAFE`
주석이 `Store Group` 3/21 을 기각하며 이렇게 적었다:

> `group_create` is 1 of the AC-MVP-001 10 representatives, so even 3/21 costs a whole task type

즉 이 저장소는 **「대표 과업 유형 1종을 통째로 덮는 비용」을 이미 기각 사유로 채택했다.**
같은 통화로 C 를 재는 것이고, 내가 지어낸 숫자가 아니다. 2026-08-05 결정이 쓴 척도와 같은
기준을 C 에도 적용한다 — C 에만 무른 기준을 쓰면 갈래 비교가 성립하지 않는다.

조건 ②가 조건 ①보다 엄하다: 판정 불가 3건이 한 과업 유형에 몰리면 요청되지 않음이 4건이어도
불통과다. 이것이 의도한 방향이다. A.1 ④ 가 보인 대로 코퍼스 시나리오 **개수**는 비용을
과소평가하므로, 개수 비교(①)만으로는 부족하다.

**보고 형식** — 두 숫자 모두 코퍼스와 분모를 병기한다(A.2). 「판정 불가 N건」이 아니라
「판정 불가 N/21 시나리오, 과업 유형 M/10 종」으로 적는다.

**이 임계가 통과를 보장하지 않는다.** 조건 ②는 C 를 죽일 수 있고, 그것이 설계 의도다
(AC-UNREQ-005: 불통과가 정직하게 기록되면 합격).

  A.1 ④ 가 이미 보였다. M1 의 n/21 은 하한이지 실제 비율이 아니다.

## G. 위험

### G.1 🔴 C 의 술어가 판정 불가일 수 있다 — 이 SPEC 의 중심 위험

「포지션 프리셋 만들어줘」처럼 **번호를 말하지 않은 지시**는 흔하고, 이 앱은 그럴 때 빈 슬롯을
찾아 쓴다(`_position_preset_free_starts`). 그 쓰기는 대상이 지시에 없지만 **요청된 것**이다.
술어가 이 둘을 못 가르면 C 는 요청된 쓰기에도 질문 카드를 띄우고, 그것은 갈래 B 의 마찰 문제를
경로만 바꿔 재현하는 것이다.

REQ-UNREQ-004 와 REQ-UNREQ-006 이 이 위험을 정면으로 겨눈다 — M1 은 C 를 정당화하는 측정이
아니라 **C 를 죽일 수 있는 측정**이어야 한다.

### G.2 🔴 M1 이 자기 결론을 확증하는 형태로 설계될 수 있다

측정 하네스를 SPEC 저자가 설계하고 그 저자가 C 를 권고했다. 대조군(REQ-UNREQ-003)과
양분 집계(REQ-UNREQ-004)가 그 편향에 대한 방어이지만 충분하다는 보장은 없다.
M1 결과는 독립 감사(plan-auditor 또는 사람)를 거치는 편이 낫다.

### G.3 코퍼스가 대표하지 않는다

ASSUMPTION-01. n/21 을 「전체의 n/21」로 읽으면 안 된다. M1 산출물은 이 한계를 명기해야 한다.

### G.4 본 SPEC 이 다루지 않는 위험

- `Label` 계열 — 별도 카드

### H.1 M1 이 남긴 지식 — C 의 운명과 무관하게 유효하다

**「둘 다 재라」가 잡은 것: 술어가 정확해질수록 C 가 나빠 보인다.**

| | 범위 A (번호만) | 범위 B (번호 + 지시어) |
|---|---|---|
| 요청되지 않음 | 3 시나리오 | 0 |
| 판정 불가 | 0 | 3 시나리오 |
| 판정 | 통과 | **불통과** |

갈리는 자리는 「그룹 하나로 묶어줘」류 3건 — 사용자가 종류는 말하고 번호는 앱에 맡긴
경우다. 범위 A 는 이 위임을 **정탐으로 오계상**해서 통과가 나온다. A 의 통과는 C 가 싸다는
증거가 아니라 술어가 위임을 못 알아본다는 증거다.

이 문단은 재측정을 설계할 사람이 **제일 먼저** 읽어야 한다.

### H.2 조건 ②는 안 걸렸다 — C 에 유리한 유일한 실측

통째로 덮인 대표 과업 유형 **0 / 10종** (두 범위 모두). C 의 오탐 부담은 3/21 이고 어떤
과업 유형도 통째로 잃지 않는다. 갈래 B 가 `Store` 하나로 10/21 과 대표 과업 5종을 덮은
것과 대비된다. 저장소 자체 기준(「even 3/21 costs a whole task type」)으로 재면 C 가 B 보다
명확히 싸다 — C 가 죽은 이유는 비싸서가 아니라 **술어가 위임을 못 가르기 때문**이다.

### H.3 조건 ①이 이 코퍼스에서 평가 불가였다는 사실

코퍼스 22개 쓰기 명령 중 진짜 요청되지 않은 쓰기는 0개다. 정탐이 구조적으로 0이면
조건 ①(오탐:정탐 비율)은 「오탐이 하나라도 있는가」와 같은 말이 된다.
이것은 **임계가 틀렸다가 아니라 데이터가 그 임계를 평가 못 한다**이다. 숫자를 보고 임계를
무르게 바꾸는 것은 D.5 가 막으려던 사후 조정이므로 하지 않았다.

재측정은 별도 카드가 소유한다. 그 카드의 설계자는 이 SPEC 의 저자가 아니어야 한다
(G.2 편향 재현 방지).
