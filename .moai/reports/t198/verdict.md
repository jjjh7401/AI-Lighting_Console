# t198 — 증거가 맥락에서 분리된다: 규모·처분·처방

카드: t198. 기전은 확정 상태로 인계받음(트랜스크립트가 세션 cwd 를 따라다니며 흔적을 안 남긴다). 이 레인이 잰 것은 (A) `.moai/reports/` 경로 인용의 규모, (B) `moai worktree done` vs 세션 종료 disposal 의 실제 효과, (C) 처방 셋의 값 비교.

## 0. 메타 사고 — 착수 전 clear-검증 오진 자체가 A 의 표본이다

착수 직전 리드가 "너는 clear 를 안 거쳤다"며 착수를 막았다(트랜스크립트 파일이 새로 안 생겼다는 근거). 레인이 같은 술어로 재측정하니 반대로 나왔다(구 파일 a47f511b 08:44 정지, 신 파일 45ee8eb9 08:50 성장 중, mtime 이 리드가 인용한 값과 바이트 동일이었으나 4분 낡은 값이었다). 리드가 재확인 후 정정: birth 시각으로 보면 회전은 08:46 에 이미 일어났고, 리드가 08:48:44 에 ls -lt 로 LX-SEQ 폴더만 봤을 때 새 파일이 아직 그 폴더에 없었다 — clear 직후 새 트랜스크립트가 태어난 위치(그 순간의 cwd, 즉 워크트리 쪽)에서 세션이 워크트리를 나온 뒤에야 LX-SEQ 로 옮겨온 것으로 추정(확정은 아님 — 이동은 흔적을 안 남겨 사후 재현 불가).

이 사고 자체가 (A) 의 셋째 갈래(증거 자체가 안 열린다)의 실물 표본이다: 리드가 인용한 경로(ls -lt 한 폴더)가 존재를 답하지 못한 것은 파일이 없어서가 아니라 그 순간 그 폴더에 없었기 때문이었다. 술어가 틀린 게 아니라 범위(어느 폴더를 볼지)가 틀렸다. 리드는 이 자리에서 이미 확정해 둔 지식("트랜스크립트는 cwd 를 따라다닌다")을 안 썼다 — 몰라서가 아니라 안 써서 틀렸다.

교정된 술어(카드의 처방 (3) 과 동일): 폴더가 아니라 세션 uuid 로 전 폴더를 find 하고 mtime/birth 를 현재 시각과 대조하라. 아래 3절에서 이 형태를 실제로 재사용해 값을 냈다.

주의: 대조군 한계 — 리드의 최초 대조군은 n=1(리드 자신의 세션)이었다. clear 가 항상 파일을 회전시키는지, 회전된 파일이 항상 즉시 올바른 폴더에 나타나는지는 이 카드에서 검증되지 않았다.

## B. moai worktree done vs 세션 disposal 비교

throwaway 워크트리(t198-disposal-test, main 과 diff 0)를 만들어 두 경로를 각각 쐈다.

ExitWorktree(action remove) — 최초 t198 진입 때 실행(작업 없음, 안전 확인 후) — 관측: 워크트리 디렉터리 제거. 브랜치는 남았다(WT-report-path-audit 스트레이 브랜치 발견, 재진입 시 git branch -m 충돌, 확인 후 수동 git branch -d).

moai worktree done 브랜치명(--delete-branch 미지정), t198-disposal-test 대상 L1(.claude/worktrees) 경로 — 관측: 성공. 워크트리 디렉터리 제거(git worktree list 에서 사라짐). 브랜치는 남았다(git branch -a 에 잔존, 수동 git branch -D 로 정리).

규약(lane-protocol.md)의 "moai worktree done 은 L2 트리에만 걸린다" 주장은 이 환경에서 반증된다. 실측: moai worktree done 은 L1(.claude/worktrees) 경로에도 정상 동작했다(exit 0, Worktree removed 출력). 부수 확인: 사용자 홈 아래 .moai/worktrees 디렉터리는 이 환경에 존재하지 않고, .moai 아래에도 별도 워크트리 레지스트리 파일이 없다(백업본 스킬 문서만 매치) — done 은 git 자체의 worktree 목록을 브랜치명으로 조회할 뿐, L1/L2 를 가르는 별도 등록부는 이 프로젝트에 실재하지 않는 것으로 보인다.

두 경로(ExitWorktree remove, moai worktree done)는 관측된 효과가 동일하다: 디렉터리 제거 + 브랜치 존속. 세션 종료 시 TUI 의 keep/remove 프롬프트 자체는 세션을 실제로 끝내야 재현되므로 이 레인에서 직접 재현하지 못했다(갭으로 남김) — ExitWorktree 가 그 프롬프트의 프로그램적 등가물일 가능성이 높다는 것이 근거 있는 추정이지, 확인된 사실은 아니다.

## C. 처방 셋 값 비교

처방 (1) git add -f 로 .moai/reports 카드폴더에 강제 커밋 — 겨냥: A 의 37건(리포트 파일 자체가 안 열림) — 실측 비용: pre-push ruff 대상 증가, UP031 및 E501 6건 — 출처: t194 레인 기존 실측(이 카드에서 재측정 안 함, 인용).

처방 (2) 인용 시 경로 대신 내용을 같이 싣기 — 겨냥: A·트랜스크립트 인용 양쪽 다 — 실측 비용: 문서 비대화(정량 미측정 — 이 카드에서는 실제 적용해 바이트 증가를 재지 않음) — 출처: t193 2회차 선례 인용만.

처방 (3) 경로 대신 세션 uuid 인용 후 find 로 해석 — 겨냥: 트랜스크립트 인용만(0절의 사고 유형) — A 의 37건에는 안 듣는다(그 37건은 세션 트랜스크립트가 아니라 .moai/reports 정적 파일이라 uuid 가 없다) — 실측 비용: 이번에 처음 실측. find 명령 1회 실행 결과 정확히 1건 매치, 모호성 없음. 비용은 명령 1회의 간접 단계 하나 — 출처: 이 카드에서 실측(0절).

### 권고 (판정은 리드 몫)

A 의 37건(SPEC 아티팩트가 plan-audit 리포트를 인용하는 깨진 경로)에는 처방 (1)이 유일하게 듣는다. 처방 (3)은 대상이 다르다(트랜스크립트 uuid 전용) — 카드가 셋을 같은 계열로 묶었지만 겨냥하는 파일 종류가 갈린다는 점을 규약에 반영 권고.

처방 (1)의 비용(ruff 6건)은 AUTOPATCH-001 13건처럼 인용이 몰린 자리엔 감내할 만하다고 판단되나, 정량적 손익 비교(ruff 6건 대 복구되는 인용 55건)는 리드 판정 영역.

처방 (3)은 비용이 가장 싸고(명령 1회, 이번 실측 모호성 0) 트랜스크립트류 인용(0절 사고, 규약 3.6 계열)에는 1순위로 채택 권고 — 단, 표본이 1건이라 반복 재현은 안 됨(residual risk).

처방 (2)는 두 문제 모두에 듣지만 비용을 이 카드에서 재지 못했다 — 다음 카드로 이연 권고(실제 인용 하나에 적용해 바이트 증가를 재는 실험).
