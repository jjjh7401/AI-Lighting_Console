## 1. 판정: **불통과**

범위 B(정확한 술어)에서 **중단 조건 ①이 걸렸다.** 판정 불가 3 ≥ 요청되지 않음 0.

이 문서는 그 결과를 완화하지 않는다. acceptance.md AC-UNREQ-005 가
「불통과가 정직하게 기록되면 합격」이라고 적은 대로, 아래는 불통과 기록이다.
M2·M3 은 착수하지 않는다 (spec.md C.4).

## 2. 두 범위가 **반대 판정**을 냈다

리드가 「둘 다 재고 따로 보고하라」고 한 것이 정확히 이걸 잡았다.

| | 범위 A (번호만) | 범위 B (번호 + 지시어) |
|---|---|---|
| 요청됨 | 16줄 / 10 시나리오 | 16줄 / 10 시나리오 |
| 요청되지 않음 | **6줄 / 3 시나리오** | **0** |
| 판정 불가 | 0 | **6줄 / 3 시나리오** |
| 조건 ① (판정불가 ≥ 요청되지않음) | 0 ≥ 3 → 안 걸림 | 3 ≥ 0 → **걸림** |
| 조건 ② (과업 유형 통째 덮음) | 0종 → 안 걸림 | 0종 → 안 걸림 |
| **판정** | **통과** | **불통과** |

분모: 코퍼스 21 시나리오 / 10 과업 유형 / 쓰기 명령 22줄 (쓰기가 있는 시나리오 13개).

### 왜 갈리는가 — 그리고 왜 A 의 「통과」가 가짜인가

갈리는 자리는 세 시나리오다: `group-create-1`("보컬 그룹으로 만들어줘" → `Store Group 3`),
`group-create-3`("그룹 하나로 묶어줘" → `Store Group 11`), `macro-create-2`.
셋 다 **사용자가 개체 종류는 말했지만 번호는 앱에 맡긴** 경우다.

- 범위 A 는 번호만 보므로 이 셋을 **요청되지 않음**(= 진짜 잡아야 할 것)으로 센다.
  그래서 비율이 좋아 보이고 통과가 나온다.
- 범위 B 는 위임을 알아보므로 **판정 불가**(= 잡으면 안 되는 것)로 센다.
  그래서 불통과가 나온다.

**술어가 정확해질수록 C 가 나빠 보인다.** A 의 통과는 술어가 위임을 구별하지 못해
오탐을 정탐으로 계상한 결과이지, C 가 싸다는 증거가 아니다.
이 성질은 spec.md G.1 이 이 SPEC 의 중심 위험으로 지목한 바로 그것이다.

## 3. 조건 ①이 이 코퍼스에서는 **구조적으로 평가 불가**다

측정하고 나서 알았다: **코퍼스 22개 쓰기 명령 중 진짜 요청되지 않은 쓰기는 0개다.**
전부 번호가 명시됐거나(16줄) 위임된 것(6줄)이다. 코퍼스는 설계상 정상 시나리오만 담는다
(`corpus.yaml` 머리말: "commands that clear the safety gate without approval").

조건 ①은 오탐:정탐 비율인데 **정탐이 구조적으로 0**이므로, 이 코퍼스에서 조건 ①은
「오탐이 하나라도 있는가」와 같은 말이 된다. 정확한 술어는 오탐을 정직하게 세므로
반드시 걸린다. 즉 **조건 ①은 이 데이터에서 C 를 평가하지 못한다.**

이것을 「그러니 조건 ①을 완화하자」로 읽으면 안 된다. 그건 숫자를 보고 임계를 무르게
바꾸는 것이고, D.5 가 막으려던 사후 조정 그 자체다. 여기서 보고하는 것은
**임계가 틀렸다**가 아니라 **데이터가 그 임계를 평가할 수 없다**이다. 둘은 다르다.

## 4. 조건 ②는 두 범위 모두 안 걸렸다 — 이건 C 에 유리한 실측이다

통째로 덮인 과업 유형 **0종 / 10종**. `group_create` 는 `group-create-2`(번호 명시)가,
`macro_create` 는 `macro-create-1`(번호 명시)이 섞여 있어 어느 유형도 전부 위임은 아니다.

즉 C 의 오탐 부담은 **3/21 시나리오이고 어떤 과업 유형도 통째로 잃지 않는다.**
갈래 B 가 `Store` 하나로 10/21 시나리오와 대표 과업 5종을 덮은 것과 대비된다.
조건 ②는 저장소가 이미 쓴 기준(「even 3/21 costs a whole task type」)이고, 그 기준으로는
C 가 B 보다 명확히 싸다.

## 5. 술어는 사고를 잡는다 — 코퍼스가 못 보여준 정탐

인공 대조군 2건(코퍼스 밖, n/21 집계에서 제외):

| 사례 | 지시문 | 명령 | 판정 |
|---|---|---|---|
| `synthetic-requested` | "프리셋 9.3으로 저장해줘" | `Store Preset 9.3` | 요청됨 ✓ |
| `synthetic-accident` | "시트 읽어서 뭐가 들었는지 알려줘" | `Store Preset 2.31` | **요청되지 않음** ✓ |

두 번째가 LXSEQ-003 M4 사고의 형태다. 술어가 그것을 잡는다.
다만 이건 **내가 만든 사례 1건**이지 코퍼스 데이터가 아니다. 정탐 근거로는 약하다.

## 6. 그래서 무엇을 판단해야 하는가 (M2 가 아니라 리드·감독의 몫)

M1 은 불통과이므로 내가 M2 로 넘어가지 않는다. 선택지는 둘이고, 성격이 다르다.

**(가) 불통과를 받아들이고 C 를 접는다.** 규칙대로다. 대신 사고를 막는 수단이
게이트 개정 A(M4) 하나만 남는다 — 그건 `Store Preset` 만 막고 다른 개체는 안 막는다.

**(나) 정탐이 있는 코퍼스로 다시 잰다.** 조건 ①이 평가 가능해지려면 요청되지 않은
쓰기 사례가 데이터에 있어야 한다. 이건 **새 사전등록**이지 임계 완화가 아니다 —
새 데이터셋과 새 임계를 측정 **전에** 다시 확정해야 하고, 그 설계를 내가 또 하면
G.2 의 편향이 그대로 반복된다. 설계자를 바꾸는 편이 낫다.

내 권고는 (나)이되 **설계는 내가 하지 않는 것**이다. 다만 이건 권고이지 판정이 아니다.
판정은 위에 적힌 대로 불통과다.

## 7. 미검증 (Gaps)

- **정탐 사례가 코퍼스에 0건.** §3 의 결론이 여기서 나온다. 이 한계를 모르고
  범위 A 의 「통과」를 인용하면 잘못된 결론에 도달한다.
- **위임 판정이 개체어 사전에 의존한다.** `OBJECT_WORDS` 8개(그룹/프리셋/큐/시퀀스/
  페이지/매크로/실행기/익스큐터). 사전에 없는 개체어를 쓴 지시문은 위임을 못 알아보고
  요청되지 않음으로 샌다. 코퍼스 21건에서는 문제가 안 났지만 실제 지시문에서는 다를 수 있다.
- **전량 스위트 파괴 수를 이 판정에 넣지 않았다.** C 는 룰셋 삽입이 아니라 응용 층
  변경이라 「항목을 넣고 돌린다」가 성립하지 않는다. M3 구현 없이는 A·B 와 같은
  세 번째 단위(테스트 파괴 수)를 낼 수 없고, M1 이 불통과라 M3 에 안 간다.
  **따라서 C 는 A·B 와 완전히 같은 단위로는 끝내 비교되지 않았다.** 두 단위
  (시나리오 수, 과업 유형 수)까지만 같다.
- **`Store Sequence 1 Cue 2` 같은 다중 대상 명령**은 첫 (종류, 번호) 쌍만 본다.
  코퍼스에는 해당 사례가 없었다.
