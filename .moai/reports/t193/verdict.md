    65:5. t182 unreadable_root 독스트링의 "예외 이름을 부르는 것은 거기 안 걸린다"는

갖고 있었다"고 적은 전제 자체가 원본과 안 맞는다.

결론(A): 이 표본은 붙여넣기 전송이 잘랐다는 증거로 못 쓴다. 오히려 규약
§3.6 이 경고하는 형태 — 근거를 대기 전에 원본을 다시 안 읽은 것과 더
닮았다. 두 서로 다른 위치의 내용이 "같은 자리(4번)"로 합쳐져 기억/재구성된
것이라면, 이건 전송 계기의 결함이 아니라 인용 재구성의 결함이다.

## 4. 이번 회차에 직접 잰 통제 팔 — 교차세션 메시지 채널

이 세션이 이번 카드를 받는 과정에서 리드로부터 SendMessage 로 긴 한국어+

본문을 그대로 대조했을 때 하이픈 플래그, 백틱 코드, 경로 표기 어느 것도

결론: 적어도 SendMessage(교차세션 메시지) 경로는, 카드가 지목한 잘림을

경로(사람이 렌더된 텍스트를 복사해 터미널에 붙여넣는 경로)와는 다른 채널이므로
대체 증거이지 대체 판정은 아니다 — 잘림이 사람의 클립보드/붙여넣기 단계에서만
나는 것이라면 이 팔은 애초에 안 걸릴 수 있다.

## 9. 갱신 — 실측 B 원문 확보 (리드 = t98 자신, 2차 회차)

리드가 t98 세션 본인이며, 손상본이 디스크가 아니라 **그 세션의 대화 컨텍스트**에
그대로 남아 있었다. 정본을 알 수 있는 자리만 골라 대조쌍으로 고정한다(리드
제공, 이 세션은 원문 접근 불가 — 리드의 관측을 그대로 인용하고 출처를 밝힌다):

    (1) moai todst done next unpick edit move drop undrop
        → moai todo list done …  에서 o·l·i 유실, "todo list" 가 "todst" 로 뭉침
    (2) done 은 dit 접두로              → edit 의 e 탈자
    (3) status  ueued 개수를            → queued 의 q 탈자
    (4) gh api rs/<headRefOid>/check-runs
        → repos/<owner>/<repo>/commits/ 가 "rs/" 로 대량 유실
    (5) 레인은   <pid> -dcwd -Fn 으로 정체 확인)
        → "lsof -p" 통째 유실, "-a -d cwd" 가 "-dcwd" 로 뭉침
    (6) sync=100— 셋 다/clear 대상이거나  → sync=10050 잘리고 다음 문장과 융합
    (7) 개수  | head 가붙은 출력을      → 공백 소실 + 중복 공백
    (8) "그 다음 큐에서 / 감독이 고른"     → 문장 미완결

### 9.1 카드의 물음 (1)(2)에 대한 답

- **한국어 산문은 멀쩡한데 ASCII 명령만 뭉개졌다** — 문자 의존 쪽에 무게가
  실리는 첫 신호다. 길이 의존은 여전히 안 갈린다(짧은 토큰 `q`, `e` 도 빠졌다).
- **유실이 행 단위가 아니라 문자 단위다**(`q` 하나, `e` 하나, `o`·`l`·`i`
  묶음). 그래서 손상된 명령이 **문법적으로 죽지 않고 실행되어 다른 값을
  답한다** — "잘림"보다 **탈자**가 정확한 이름이다. §4.0 표의 두 잘림 유형
  (하네스 상한 / `head`)과는 또 다른 셋째 형태로, **행 경계가 아니라 문자
  경계**에서 난다는 점이 갈림점이다.

### 9.2 여전히 못 가르는 것 (정직하게 남긴다)

- **손실 자리**(클립보드 / 터미널 bracketed paste / 하네스 입력 처리) —
  이 표본으로도 세 경로 중 어디인지 못 가른다.
- **"붙여넣기에서 났다" vs "애초에 그렇게 작성됐다"** — 엄밀히는 이것도
  이 표본만으로 완전히 못 가른다. 다만 (1)(3)(5)는 정본이 명백해 작성
  당시부터 그렇게 썼을 가능성은 낮다(예: "moai todst" 라고 처음부터 쓸
  이유가 없다) — 그 정도의 방증이지 확정은 아니다.
- 카드가 요청한 판정 셋(§5 표)은 **그대로 미측정**이다. 사람의 실제
  클립보드→터미널 붙여넣기 단계를 이 세션이 재현할 수단이 여전히 없다.

### 9.3 통제 팔 재평가

§4의 SendMessage 관측(하이픈·백틱 무사)은 여전히 다른 채널이라 판정은
아니지만, 이제 대비가 더 뚜렷하다: **SendMessage 경로는 이 회차까지
무사하고, 사람이 개입하는 붙여넣기 경로에서만 탈자가 관측됐다.** 이 대비
자체가 다음 회차가 어디를 먼저 봐야 하는지의 근거다.

### 9.4 판정 갱신

- 실측 A: **철회**(§2, 유지).
- 실측 B: **확보·고정함**(원문 8쌍, 위 §9 본문). 탈자가 실재한다는 것
  자체는 이제 이 표본으로 지지된다. 다만 손실 자리·작성 대 전송의 구분은
  여전히 미해결.
- 카드 제목/프레이밍 정정 제안: "잘림"이 아니라 "탈자(문자 단위 유실)".

## 10. 정정 — §3 의 「원문 미회수」는 범위 오류였다 (2회차, WT-paste-transport-b)

리드가 main `78f5415` 을 직접 열어 반증했다: `~/.claude/projects/-Users-studiox-Documents-Claude-Code-AI-Lighting-Console--claude-worktrees-t184/cd8100e9-533c-4a55-8978-fc6b6d12b7ba.jsonl` 13행에 `"type":"user"` 로 원문이 그대로 있다. 이 세션이 직접 열어 재확인했다(§10.1).

1. **당시 잰 것**은 `memory/*.md` 범위였고 0건 — 이 사실 자체는 그대로 참이다.
2. **그 0건은 부재의 증거가 아니었다.** 트랜스크립트 저장소(`~/.claude/projects/**/*.jsonl`)는
   `memory/` 밖에 있고, 애초에 그 범위로는 안 닿는 자리였다. 계기가 무엇을 세는지를
   먼저 묻지 않은 것 — 이 규약 §4.0 이 바로 그 형태다.
3. §3 의 "pruning 정책 때문일 수 있다" 가설은 **미측정이 아니라 불필요로 강등**한다.
   원문이 있으니 그 가설이 설명할 대상 자체가 없다.
4. §3, §9.2 는 **정정 대상이지 삭제 대상이 아니다** — 그 회차의 잰 범위 안에서는
   참이었던 기록이므로 지우지 않고 이 절로 정정한다(규약 §5).

리드가 밟은 함정도 같이 남긴다: 리드도 처음엔 primary 프로젝트 폴더 하나(53개
파일)만 grep 해 `todst` 0건을 얻었다 — 워크트리 세션은 프로젝트 폴더가 따로 파여
전체는 111개 폴더 875개 파일이다. **좁게 재고 넓게 결론낸 것**이고, 이 세션이
§2에서 반증한 실측 A와 같은 계열(근거를 대기 전에 원본/범위를 다시 안 읽음)이다.
그리고 `todst` 매치 4건 중 3건은 카드 본문을 읽은 세션들의 **오염**이었다(카드가
`todst` 를 인용하므로 재검색하면 카드 자신도 걸린다) — 매치 수를 증거 수로 읽지 않았다.

## 11. 발신 원본 대조 — 성립함. 「문자 단위 탈자」는 정정 대상이다

`grep -rl '칸반 리드 세션 재개' ~/.claude/projects/ --include='*.jsonl'` 은 16개 파일을
답했지만 그중 어디에도 `"type":"assistant"` 로 이 문구를 담은 자리가 없었다 —
즉 이 인계문은 세션 트랜스크립트 안에서 어시스턴트가 렌더한 흔적이 없다. 대신
카드 본문의 `applied lessons: project-lead-resume-20260831.md` 줄이 가리킨 그
메모리 파일 자체(115~148행)가 발신 원본이었다 — 그 세션(리드)이 이 파일의
"다음 세션 시작점" 블록을 사람이 복사해 t98 세션에 타이핑/붙여넣기로 냈다는 뜻이다
(수신 쪽 메타데이터 `promptSource=typed, origin.kind=human` 과도 맞는다).

**대조가 성립한다.** 두 텍스트를 나란히 놓고 읽었다(원본: memory 파일 115~148행,
손상본: §10.1). 결과는 §9 의 결론을 정정해야 한다.

### 11.1 정정 — 「문자 단위 탈자(q·e 한 글자)」가 아니라 「연속 구간 삭제」다

원본과 손상본을 직접 대조하면, 사라진 것은 낱글자가 아니라 **여러 글자로 된
연속된 구간**이고 그 구간의 양쪽 끝 글자가 우연히 이어 붙어 그럴듯한 새 단어처럼
보였을 뿐이다. 예:

    원문: "moai todo 동사는 아홉이다 — add list done"
    손상: "moai todst done"
    → "todo" 와 "list" 사이에서 "o 동사는 아홉이다 — add li" 전체(약 15자)가
      삭제되고, 남은 "tod" + "st" 가 붙어 "todst" 처럼 읽혔다. "o" 한 글자
      탈자가 아니라 15자 구간 삭제다.

    원문: "닫힘은 edit 접두로,"
    손상: "은 dit 접두로,"
    → "닫힘은 e" 구간이 삭제되고 "dit" 만 남았다. "e" 한 글자 탈자가 아니라
      "닫힘은 e" 전체가 삭제 구간이었다.

    원문: "status 는 닫힘의 지표가 아니다 — q" + "ueued"
    손상: "status  ueued"
    → "는 닫힘의 지표가 아니다 — q" 전체(약 17자)가 삭제됐다. "q" 하나가
      아니라 그 앞 문장 전부가 사라진 자리에 공백 두 칸만 남았다.

    원문: "레인은 소켓으로 불러라 (lsof -a -p <pid> -d cwd -Fn 으로 정체 확인)"
    손상: "레인은   <pid> -dcwd -Fn 으로 정체 확인)"
    → "소켓으로 불러라 (lsof -a -p " 전체(약 16자)가 삭제됐다.

    원문: "sync=10050 · plan=3402 · run=8397 — 셋 다"
    손상: "sync=100— 셋 다"
    → "50 · plan=3402 · run=8397 " 전체(약 24자)가 삭제됐다.

**공통 패턴**: 삭제 구간은 항상 여러 문자(관측된 범위 약 13~30자)로 된
연속 구간이었고, 매번 구간의 시작·끝이 우연히 실행 가능한 새 토큰을 만들었다
(그래서 "탈자"라는 이름이 그럴듯해 보였다). §9 의 "q·e 한 글자 탈자"는
**원문 없이 "정본이 무엇이었을까"를 추정한 결과였고, 실제 대조로는 성립하지
않는다.** 이 절로 §9.1 을 정정한다.

### 11.2 항목 (2)만 다른 형태다 — 「삭제」가 아니라 「다른 출처 내용으로 치환」

    원문 2): gh pr list --state open → 열린 것이 없어야 한다 (t182 는 닫혔다)
    손상 2): 🔴 gh api repos/jjjh7401/AI-Lighting_Console/commits/11f9d13/check-runs
             → 초록이면 t182 를 edit 으로 닫아라. #231 머지 커밋 CI 는 cancelled 였다
               (cancelled 는 통과도 실패도 아니다)

이건 원문의 부분 삭제로 설명이 안 된다 — 완전히 다른 문장이다. 그리고 이 문장은
이 카드(t193)의 배차 직전, 리드가 이 세션에 보낸 **다른 메시지**(11f9d13·#231·
cancelled CI 판정)의 내용과 사실상 같다. 즉 이 자리는 §11.1 의 "구간 삭제"와
같은 계기가 아니라 **다른 출처의 텍스트가 끼어든 것**으로 보인다 — 사람이 붙여넣기
직전/도중에 다른 내용을 참고해 그 자리를 직접 고쳐 썼을 가능성도 배제 못 한다.
**미측정으로 남긴다**: 이 자리가 전송 계기의 결함인지 사람의 편집인지는 이
표본만으로 못 가른다. 다만 §11.1 의 패턴(양쪽 글자가 이어 붙는 삭제)과는
형태가 다르다는 것만은 확실하다 — 같은 현상으로 묶으면 안 된다.

### 11.3 가설 — 바이트 폭 절단 (미확정, 다음 회차 검증 대상)

관측된 모든 삭제 구간이 **ASCII 로만** 이루어져 있고 한국어 산문 구간은 단 한
글자도 삭제되지 않았다(§9.1 의 관측은 이 대조로도 유지된다). UTF-8 에서 한글은
글자당 3바이트, ASCII 는 1바이트다 — 만약 손상 계기가 **바이트 폭 기준**으로
어떤 구간을 건너뛰거나 자른다면, 같은 바이트 폭이 한국어 구간에서는 훨씬 적은
글자 수만 건드리고(운이 나쁘면 0글자), ASCII 구간에서는 훨씬 많은 글자·단어를
삼킬 것이다 — 관측과 정확히 들어맞는다. **다만 이건 바이트 수 계산으로 뒷받침되는
가설이지, 실제 손상 계기(클립보드/터미널 렌더링/붙여넣기 처리)를 이 회차에서
직접 잡은 것은 아니다.** 다음 회차가 검증할 것: 각 삭제 구간의 정확한 바이트
길이를 재고 서로 비슷한 폭(±허용오차)인지 확인.

### 11.4 갱신된 미측정 (Gaps, 2회차)

- §11.3 의 바이트 폭 가설은 **미확정**이다 — 각 구간의 바이트 수를 재는 것이
  다음 회차의 첫 작업이어야 한다.
- §11.2 (항목 2의 치환)이 전송 계기인지 사람 편집인지는 이 표본만으로 못 가른다.
- 손실 자리(클립보드 / 터미널 bracketed paste / 하네스 입력 처리)는 **여전히**
  못 가른다 — 발신-수신 대조로는 "무엇이 다른가"는 잡히지만 "어느 단계에서
  달라졌는가"는 안 잡힌다. 사람의 실제 붙여넣기 재현 실험이 여전히 필요하다.
