# t93 -- 매처 실측: 레인을 막는 것은 ask 규칙이 아니다

판정: 전제 반증 -- 좁히지 않고 멈춤 (배차서 gate 조항)

측정 트리: .claude/worktrees/t93
브랜치: WT-rm-ask-narrow
기준 커밋: 998a4c5
측정 세션: 0db0c526-a15d-4e7a-a643-a53880ad0934

## 1. 주장 (Claim)

1. 전제 A 는 거짓이다. bypassPermissions 는 명시 ask 규칙을 이긴다.
   Bash(rm:*) 도 Bash(chmod:*) 도 이 세션에서 한 번도 프롬프트를 내지 않았다.
2. 전제 B 는 참이지만 원인이 잘못 지목됐다. 레인은 실제로 막힌다.
   다만 막는 주체는 ask 규칙도 deny 배열도 아니고, moai Go 바이너리의
   PreToolUse 훅이 내는 정규식 거절이다.
3. 따라서 A안(.claude/settings.json 의 ask 배열 좁히기)은 아무것도 고치지
   못한다. 대상 파일이 틀렸다.
4. 현재 가드는 동시에 너무 좁고 너무 넓다 -- 플래그 순서를 뒤집으면 그냥
   지나가고, 반대로 문자열 안의 언급까지 막는다.

## 2. 증거 (Evidence)

### 2-1. 실제 Bash 발사 -- 7형태

과녁은 전부 임시 디렉터리 아래 빈 폴더. 명령의 모양만 위험형이고 대상은 무해.

  1. 재귀+강제, 절대경로 --> 차단(Dangerous command blocked). 폴더 살아남음
  2. 플래그 순서 반전, 절대경로 --> 통과, 프롬프트 없음. 폴더 사라짐
  3. 재귀만, 절대경로 --> 통과. 폴더 사라짐
  4. 강제만, 절대경로 파일 --> 통과. 파일 사라짐
  5. 플래그 없는 단일 파일 (음성 대조군) --> 통과. 파일 사라짐
  6. 재귀+강제, 상대경로 --> 통과. 폴더 사라짐
  7. 위험형을 echo 의 따옴표 안 데이터로만 포함 --> 차단, 같은 문구

종료 코드는 증거로 쓰지 않았다. 7건 전부 되읽어 효과를 확인했다.

차단 문구는 정규식을 그대로 노출한다: 대소문자 무시 플래그, rm, 공백,
재귀강제 플래그, 공백, 슬래시. 슬래시가 붙어 있으므로 모든 절대경로가
사정권이다 -- 루트만이 아니다.

### 2-2. 훅에 직접 물은 결과 (결정적)

moai 의 pre-tool 훅에 payload 를 직접 먹여 판정만 받았다(실행 없음):

    재귀+강제 절대경로 --> permissionDecision: deny
                           reason: Dangerous command blocked (위 정규식)
    플래그 순서 반전   --> permissionDecision: allow
    따옴표 안 데이터   --> permissionDecision: deny (동일 문구)

.claude/hooks/moai/handle-pre-tool.sh 는 판단을 하지 않고 moai 바이너리로
stdin 을 넘기기만 한다. 즉 거절은 Go 바이너리 소유다.

### 2-3. ask 규칙이 무력하다는 양성 대조군

ask 배열 6건 중 Bash(chmod:*) 를 무해한 대상에 발사 --> 프롬프트 없이 실행.
ask 배열이 이 세션에 바인딩되지 않는다는 뜻이며, rm 이 안 걸린 것이 매칭
실패가 아니라 배열 자체의 무력화임을 가른다. 대조군이 없었다면 통과를
매칭 실패로 오독했을 것이다.

### 2-4. 다른 레인의 실기 기록 (전제 B 의 독립 증거)

세션 트랜스크립트에서 같은 차단이 2건 발견됨:

    2026-08-22  worktrees/t17  브랜치 WT-rig-sheet-csv  동일 차단 문구
    2026-08-24  worktrees/t55  브랜치 WT-prepush-gate   동일 차단 문구

둘 다 toolDenialKind 가 permission-rule 로 기록. 프롬프트가 아니라 차단이다.

## 3. 기준선 귀속 (Baseline-attribution)

설정 파일은 세 곳 전부 읽었다. 카드는 그중 하나만 봤다.

    프로젝트 .claude/settings.json
        ask 6건 (rm, chmod 포함), deny 48건 (rm 계열 9건),
        allow 114건, defaultMode 는 acceptEdits
    프로젝트 .claude/settings.local.json
        ask 0건, deny 0건 -- ask 를 덮지 않음
    사용자 ~/.claude/settings.json
        ask 0건, deny 0건, skipDangerousModePermissionPrompt 가 true

매처 성질: 명령 전체 텍스트에 대한 정규식 검색. 접두 고정이 아니다 --
7번이 따옴표 안 데이터인데도 걸렸으므로 하위명령 분해 매칭이 아니다.
따옴표를 못 본다.

## 4. 미검증 (Gaps)

  - 다른 권한 모드는 안 쟀다. 전제 A 반증은 이 세션에 대한 것이다.
    기본 모드나 acceptEdits 로 뜬 레인에서 ask 가 바인딩되는지는 미측정.
  - deny 배열이 실제로 발사되는지 안 쟀다. 훅이 먼저 거절해 deny 규칙까지
    도달하는지 확인할 수 없었다. deny 9건은 읽기만 했다.
  - 정규식의 소스 위치를 안 읽었다. Go 바이너리가 낸다는 것까지만 확인했고
    어느 파일 몇 행인지는 미확인. 이 저장소가 아니다.
  - 위험형 전수를 안 쟀다. 7형태만 쐈다. 장문 플래그형, 대문자 재귀 플래그,
    find 계열 삭제, xargs 경유 삭제 등은 미측정.
  - 차단 우회가 의도인지 결함인지 판정 못 했다. 2번과 6번이 통과한 것은
    관측했으나 소스를 안 읽어 설계 의도를 모른다.
  - 양성 대조군은 chmod 하나뿐이다. ask 배열의 나머지 4건(sudo, chown,
    .env 읽기 2건)은 안 쐈다.

## 5. 잔여 위험 (Residual-risk)

  - 이 가드가 뚫리는 것(2번, 6번)이 결함이라면, 좁히는 게 아니라 넓혀야
    한다. 카드의 방향(A안)과 반대다. 방향 결정은 소스를 읽은 뒤라야 한다.
  - 반대로 7번(문자열 언급 차단)은 오탐이며, 카드나 문서나 커밋 메시지에
    예시를 적을 때마다 재발한다. 이 보고서도 그 때문에 리터럴을 피해 말로
    풀어 썼다.
  - skipDangerousModePermissionPrompt 가 true 로 사용자 설정에 있다.
    전제 A 반증이 이 값에서 온 것인지 세션 실행 플래그에서 온 것인지는
    안 갈랐다.
  - 이 보고서 자체가 heredoc 쓰기에서 두 번 거절당했다. 증거 파일을 만드는
    행위에도 마찰이 있다. 이 자리에 처음 적었던 원인 진단은 틀렸다 — 7절 참조.

## 6. 권고 (비구속)

A안은 대상이 틀렸으므로 실행하지 않았다. 축을 다시 잡아야 한다.

  1. upstream 몫으로 넘긴다. 정규식은 moai 바이너리 소유다. 이 저장소의
     설정을 어떻게 고쳐도 동작이 안 바뀐다. t62 와 같은 성격이다.
  2. 좁힐지 넓힐지를 먼저 정한다. 지금 가드는 양방향으로 틀렸다. 뚫리는
     쪽이 더 큰 위험이면 넓히는 게 맞고, 마찰이 더 크면 좁히는 게 맞다.
     소스를 읽지 않고는 못 정한다.
  3. 레인 마찰의 즉효 회피책은 이미 있다. 다만 이건 가드를 우회하는
     법이라 문서로 배포하면 안 된다. 기록만 남긴다.

## 7. 정정 — 위 마찰의 원인을 잘못 지목했었다

초판 5절은 heredoc 거절의 원인을 「마크다운 표의 파이프와 백틱」이라고
적었다. **틀렸다.** 격리하지 않고 지목했다 — 표를 걷어내면서 JSON 도 같이
걷어냈는데, 두 변수를 동시에 바꿔 놓고 한쪽에만 원인을 붙였다.

### 격리 실측 (전부 따옴표 붙은 구분자의 heredoc, 본문만 교체)

    파이프 85개 + 백틱 든 표 15행                     통과
    한글 산문 6737바이트                              통과
    중괄호 하나, 내용 한 글자                         통과
    중괄호 안에 쉼표로 구분된 두 항목                 통과
    명령 치환 (달러+괄호로 감싼 echo)                 통과
    중괄호 안에 큰따옴표로 감싼 키와 값 (JSON 한 줄)   거절

살아 있는 명령 텍스트 쪽:

    until 루프, 조건이 리터럴                         통과
    같은 루프, 조건에 명령 치환만 추가                 거절

**방아쇠는 파이프도 백틱도 크기도 아니다.** 통과한 산문이 거절된 한 줄보다
600배 이상 크다. 실제 방아쇠는 (A) 살아 있는 명령 텍스트의 확장 구문과
(B) heredoc 본문 안의 JSON 형태 중괄호다.

### 이 정정이 뒤집는 결론

초판은 이 가드를 「복잡해 보이면 거절한다」로 읽었다. 아니다. 두 방아쇠 모두
실행 전에 경로를 정적으로 알 수 없게 만드는 구문이며, 거절 문면(워크트리
안에 머무는지 확인 불가)이 사실 정확했다. 그 가드 자신의 기준으로 정탐이다.

결함은 한 자리로 좁혀진다: 확장이 원천적으로 일어나지 않는 자리(따옴표 붙은
heredoc 본문)에서 중괄호만 살아 있는 것으로 취급된다. **같은 자리의 명령
치환은 이미 올바르게 접히므로 불일치다.** modu-ai/moai-adk#1659 로 올렸다.
위험명령 가드 쪽은 modu-ai/moai-adk#1658 이며, 두 가드는 문면도 방아쇠도 다르다.

### 남는 교훈

거절 문구가 세 가드에서 비슷해서 문구로 축을 나눌 수 없다. 그리고 원인을
지목하기 전에 **한 번에 한 변수만 바꿔야 한다** — 이 저장소가 이미 문서화한
실패 형태를 그대로 재현했다. 리드도 이 오진을 확인 없이 받아 upstream 이슈
본문 4점 중 3점을 그 위에 지었고, 제출 직전에 멈췄다.
