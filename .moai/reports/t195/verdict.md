## 2. 증거 (Evidence)

### F2 — 이동하면 자기 id 를 단 채 언다 (재현)

**예측을 이동 전에 등록했다.** t208 트리에서 `captured_at 13:37:05` / 내 id 를
읽어두고, 「옮긴 뒤에도 내 id 를 단 채 멈춰 있으면 기전 확정」이라고 적은 뒤 옮겼다.

이동 경로: `t208 워크트리` → `ExitWorktree` (launch dir 경유) → `EnterWorktree(t195)`

`13:41:39` 에 세 경로를 동시에 읽은 결과 — **셋 다 내 session_id 다**:

| 경로 | `session_id` | `writer_pid` | `captured_at` | `raw_pct` | 낡음 |
|---|---|---|---|---|---|
| `.claude/worktrees/t208/…` | `f7648b4a…` **(내 것)** | 57148 | 13:37:29 | **22** | **4분 10초, 정지** |
| `.moai/state/…` (primary) | `f7648b4a…` **(내 것)** | 58674 | 13:37:56 | **22** | **3분 43초, 정지** |
| `.claude/worktrees/t195/…` (현재) | `f7648b4a…` **(내 것)** | 66181 | 13:40:33 | **24** | 66초, 갱신 중 |

🔴 **지금 이 순간 §9 를 문면 그대로 따르면 틀린 값을 쓴다.** primary 를 읽고
`session_id` 를 대조하면 **내 것과 일치한다** — 검문 통과. 그런데 그 값 `22` 는
정지한 값이고 실제는 `24` 다. 「남의 값이라 버려라」로는 이 형태를 못 거른다.
원인이 「남이 썼다」가 아니라 **「내가 쓰다 말았다」**라서다.

그리고 이 구멍은 **확신을 올린다** — id 가 내 것이니 오히려 더 믿게 된다.

### F2 를 남이 밟은 흔적 — 나 말고도 열 세션

전수(88개)에서 `session_id` 별 파일 수:

- 26개 세션이 88개 파일을 들고 있다
- 그중 **git 배포분 둘**(F5)을 빼면 24개 세션 / 46개 파일
- **10개 세션이 사본을 둘 이상** 들고 있다 — 전부 F2 흔적이다

가장 선명한 것(리드 사례와 같은 팔 2, 즉 primary→워크트리 이동):

    2c69ef0a…  primary            13:13:35  raw_pct 21   ← 얼어붙음
    2c69ef0a…  worktrees/t205     13:13:25  raw_pct 21   ← 얼어붙음
    2c69ef0a…  worktrees/t187     13:37:05  raw_pct 39   ← 갱신 중

같은 세션의 같은 시각 값이 **21 과 39** 로 갈린다. primary 를 읽은 사람은
「내 id 니까」로 **21** 을 쓰고, 실제는 39 다. 18포인트 차이고, 21 은 임계 근처도
아닌 값으로 읽힌다.

### F3 — 턴이 도는 동안엔 갱신이 없다

한 턴 안에서 75초를 대기시키고 앞뒤로 `captured_at` 을 읽었다:

    13:39:09   captured_at = 13:38:08
    (75초 대기, 같은 턴)
    13:40:24   captured_at = 13:38:08     ← 그대로

턴 경계에서만 갱신된다. 즉 **긴 턴 하나가 도는 동안 값은 항상 낡아 있다** —
그리고 컨텍스트가 가장 빨리 자라는 구간이 바로 긴 턴이다. F2 와 달리 이쪽은
낡음이 턴 길이로 **유계**지만, 서브에이전트 팬아웃이나 대형 테스트가 도는 턴이면
분 단위가 된다.

### F4 — `writer_pid` 는 판별자가 못 된다

같은 세션이 60초 안에 남긴 기록들의 `writer_pid`: `51929 → 56221 → 57148 → 58674
→ 59393 → 66181` — **매번 다르다.** 그리고 `ps` 로 확인하니:

    ps -o pid=,comm= -p 57148 -p 58674 -p 59393 -p 56221 -p 51929
    rc=1   (다섯 개 전부 없음)

기록 시점에서 2분밖에 안 지난 `59393` 도 이미 죽어 있다. 즉 `writer_pid` 에
liveness 프로브를 걸면 **가장 신선한 기록에도 「죽음」이 나온다.**

⚠️ 이 값이 무엇의 pid 인지는 **안 쟀다.** 렌더 보조 프로세스일 것이라는 건 추론이다.
잰 것은 「매 기록마다 다르고, 2분 된 것도 살아 있지 않다」까지다.

이건 상위 규약 `context-window-management.md` § Detection Heuristics 의 문구와
어긋난다 — 거기서는 세션 id 가 비었을 때 `writer_pid` 를 판별자로 쓰라고 적는다.

### F5 — 파일 둘이 git 에 커밋돼 있다

체크아웃이 배달하는 값이라 **앞으로 만들 모든 워크트리에도 따라간다.**
⚠️ 다만 이 경로를 실제로 읽는 소비자가 있는지는 **안 쟀다** — 존재는 확정,
도달은 미측정이다.

### F6 (부수) — 세션 정체 파일 둘이 11일째 정지

## 4. 미검증 (Gaps)

  경유하면서 결과적으로 팔 2 와 같은 상태(primary 가 내 id 로 얼어붙음)를
  만들었고**, 그와 별개로 **남의 세션 `2c69ef0a…` 에서 팔 2 를 실물로 관측했다.**
  구성한 대조군이 아니라 **관측된 사례**다 — 더 강한 증거지만, 그 세션의 이동
  경로를 직접 본 것은 아니다.
- **왜 launch dir 경유가 primary 에 썼는지 안 쟀다.** launch dir 은
  `/Users/studiox/orca/workspaces/AI-Lighting_Console/LX-SEQ` 이고 그 자체가
  워크트리인데(`git-common-dir` 이 primary `.git`), 거기엔 **다른 세션의 파일**이
  따로 있었다(`ce528e21…`, raw_pct 52, 신선). 경로 결정 규칙을 안 읽었다.
- **`writer_pid` 가 무엇의 pid 인지 안 쟀다** (F4 참조).
- **F5 의 커밋된 파일을 읽는 소비자가 있는지 안 쟀다.**
- **F6 파일이 비교 기준으로 쓰이는지 안 쟀다.**
- **생산자 코드를 안 읽었다.** `moai` 는 이 저장소 소스가 아니라 설치된
  `moai-adk 3.1.2` 다. 기전은 전부 **행동 관측**이고 코드 확인이 아니다.
- **임계값을 안 정했다** — 카드의 잴 것 (2). 처방은 리드 몫이라 후보만 6절에 적는다.

## 5. 잔여 위험 (Residual-risk)

- **관측한 것이 우연일 수 있는 자리**: F2 의 「정지」는 4분 관측이다. 더 오래
  두면 다시 쓰일 가능성을 배제하지 못한다 — 다만 전수에서 **19일 된 사본**과
  **8일 전 세션의 사본들**이 그대로인 것이 반증 부담을 옮긴다.
- **F3 의 유계성**: 「턴 길이만큼」은 이번 턴들에서만 잰 값이다. 턴이 아닌
  다른 갱신 계기(백그라운드 렌더 등)가 있다면 더 짧을 수 있다.
- **F5 는 커질 수 있다**: 새 워크트리가 늘 때마다 배달본이 늘어난다. 오늘
  32곳 + 10곳이지만 이 수는 워크트리 수를 따라간다.
- **이 보고 자체가 F3 을 밟는다**: 여기 적은 `raw_pct 24` 는 이 턴이 시작될 때의
  값이고, 이 턴이 끝나는 시점에는 이미 낡았다.

## 6. 처방 후보 (판정은 리드 — 여기서 고르지 않았다)

축이 넷으로 갈린다. 이번 측정이 각 축에 주는 것만 적는다.

**축 A — §9 에 「`session_id` 일치는 신선도의 증거가 아니다」를 넣는다**
F2 가 이 축을 지지한다. 지금 §9 는 id 일치를 신뢰의 근거로 쓰고, 그 근거가
가장 위험한 형태(내가 쓰다 만 사본)에서 **정확히 반대로** 작동한다.

**축 B — `captured_at` 을 함께 읽고 보고에 함께 적는다 (임계 없음)**
낡음을 막지는 못하지만 **관측 가능해진다.** 임계를 정하지 않아도 되는 게 장점이다 —
F3 때문에 「신선한 값」이라는 상태가 애초에 존재하지 않는다(항상 최소 한 턴 낡았다).
비용: 보고 한 줄.

**축 C — 임계를 정한다 (예: N분 넘으면 버린다)**
F3 이 이 축을 어렵게 만든다. 턴 길이가 가변이라 임계가 짧으면 정상 값도 버리고,
길면 F2 의 정지본을 통과시킨다. **F2 의 낡음은 무한대라 어떤 임계로도 걸리지만**,
그러려면 임계가 「턴 길이보다 크고 무한대보다 작은」 구간에 있어야 하고 그 구간을
이번에 재지 않았다.

**축 D — 카드 수 축으로 간다**
카드의 잴 것 (3) 확인: 카드 수는 세션이 자기 전사에서 세는 값이라 **이 파일군에
전혀 의존하지 않는다.** F1~F5 어느 것도 카드 수를 오염시키지 않는다.
⚠️ 다만 이 축도 검증 불가라는 §9 자신의 지적(자기보고)은 그대로 남는다.

**경로를 고정하는 축(파일을 하나로)** 은 생산자가 `moai-adk` 이라 이 저장소에서
할 수 없다. F5 의 커밋된 두 파일을 지우는 것은 이 저장소에서 가능하지만,
소비자를 안 쟀으므로(4절) **이번 회차의 근거로는 제안하지 않는다.**

## 6.5. 추가 측정 — F5 의 뿌리를 찾았다 (gap 하나 닫음)

> 🔴 **이 절의 뿌리 진단은 절반 틀렸다 — 6.6 에서 정정했다.** 계기(`git check-ignore`)를
> 잘못 읽었다. 6.5 를 6.6 없이 인용하지 마라.

§7 의 「한 명령이면 답이 나는 것은 지금 재라」에 따라 4절 gap 중 둘을 이어서 쟀다.

**생산자 문면** — `moai` 는 이 저장소 소스가 아니라 설치된 36MB 바이너리
(`~/.local/bin/moai`, 2026-08-21)라 코드를 못 읽는다. 대신 문자열을 뽑았다:

    strings ~/.local/bin/moai | grep -i context-usage

나온 것 둘:

    `<projectDir>/.moai/state/context-usage.json` on every render.
    | `state/` | Runtime state snapshots, e.g. context-usage (gitignored

🔴 **설계상 이 파일은 gitignore 대상이다.** 즉 F5 의 커밋본 둘은 의도된 배포가
아니라 **누락이다.**

**왜 새어 나갔나** — 한 명령으로 확정됐다:

    git check-ignore -v docs/curriculum/.moai/state/context-usage.json \
                        .moai/reports/t181/probes/.moai/state/context-usage.json \
                        .moai/state/context-usage.json

세 경로 중 **하나만** 규칙에 걸린다:

    .gitignore:203:.moai/state/     .moai/state/context-usage.json

`.gitignore` 203행의 `.moai/state/` 는 **경로 구분자를 품고 있어 저장소 루트에
고정된다.** 그래서 루트의 `.moai/state/` 만 막고, 중첩된
`docs/curriculum/.moai/state/` 와 `.moai/reports/t181/probes/.moai/state/` 는
**규칙 밖이다.** 다른 `moai/state` 규칙은 `.gitignore` 에 없다(`grep -n` 확인, 1건).

즉 F5 는 「상태 파일을 왜 커밋했나」가 아니라 **「무시 규칙이 루트 고정이라 중첩
사본을 안 덮는다」**다. 세션이 중첩 디렉터리에서 렌더할 때마다(F1) 규칙 밖에
새 상태 파일이 생기고, 그것이 커밋 후보로 올라온다.

⚠️ 여전히 **안 쟀다**: 이 커밋본을 실제로 읽는 소비자가 있는지. 경로 결정이
`<projectDir>` 기준이라는 것까지는 문면으로 확인했지만, `<projectDir>` 이 중첩
디렉터리로 해석되는 조건은 안 쟀다.

주장이라 지우지 않고 고친다.

### 무엇이 틀렸나

6.5 는 커밋된 파일 **둘 다** 「`.gitignore` 규칙이 루트 고정이라 안 덮인다」로
설명했다. **둘 중 하나만 맞다.**

### 왜 틀렸나 — `git check-ignore` 의 침묵은 원인이 둘이다

`git check-ignore` 는 기본적으로 **추적 중인 파일을 출력에서 제외한다.** 그래서
침묵의 뜻이 갈린다:

- 「어떤 규칙도 안 맞는다」 (내가 읽은 뜻)
- 「규칙은 맞지만 이미 추적 중이라 안 보여준다」 (실제로 섞여 있던 뜻)

`--no-index` 를 붙이면 추적 여부와 무관하게 규칙만 본다. 붙여서 다시 재니
**두 파일이 갈라졌다**:

    git check-ignore -v --no-index .moai/reports/t181/probes/.moai/state/context-usage.json
    .gitignore:247:.moai/reports/    ← 규칙에 걸린다

    git check-ignore -v --no-index docs/curriculum/.moai/state/context-usage.json
    rc=1                             ← 어떤 규칙에도 안 걸린다

### 정정된 F5

| 파일 | 규칙에 걸리나 (`--no-index`) | 왜 추적되나 |
|---|---|---|
| `docs/curriculum/.moai/state/…` | **안 걸린다** | 🔴 **진짜 새어 나간 것.** `.gitignore:203` 의 `.moai/state/` 가 루트 고정이라 중첩 사본을 안 덮는다 — 6.5 의 진단이 **이 파일에는 맞다** |
| `.moai/reports/t181/probes/.moai/state/…` | **걸린다** (`:247 .moai/reports/`) | 규칙은 정상 작동했고, **사람이 `-f` 로 강제 추가**했다. 이 저장소는 리포트를 같은 방식으로 다수 추적한다 — 관행이지 결함이 아니다 (수치는 아래) |

**리포트 추적 수 — 트리·커밋을 붙여야 재현된다.** 같은 명령이 트리마다 다른 수를
답한다. 이 항목의 결론(「관행이다」)은 어느 수로도 서지만, 수만 적으면 다음 사람이
재현하지 못한다.

    git ls-tree -r --name-only 12846e9 .moai/reports/ | wc -l   → 228   (base, origin/main)
    git ls-files .moai/reports/ | wc -l                          → 229   (t195 트리 @ 318da7f
                                                                          — 이 verdict 자신이 1 늘렸다)

리드는 같은 명령으로 **162** 를 얻었다 — 그 워크트리가 `b26660a` 로 base 보다
낡아서다. 세 수는 모순이 아니라 **서로 다른 트리의 값**이고, 저장소가 자라는 동안
계속 갈린다. 「228」만 적었던 것은 출처 없는 수였고, 여기서 고친다.

즉 **새어 나간 파일은 둘이 아니라 하나다.** 나머지 하나는 이 저장소가 리포트를
싣는 정상 경로를 탔을 뿐이다.

배달 규모는 안 바뀐다(32곳 / 10곳) — 두 파일 다 커밋돼 있고 모든 워크트리에
따라가는 것은 관측된 그대로다. 바뀐 것은 **원인 귀속**이다.

### 이 정정을 촉발한 것

리드가 「`-f` 가 필요했던 것도 기록해라 — 그 자체가 F5 의 증상이다」라고 했다.
**그 framing 이 맞는지 재려다가 내 진단이 틀린 것을 찾았다.** `-f` 는 F5 의
증상이 아니다 — 규칙이 제대로 걸었는데 사람이 의도적으로 넘긴 것이고, F5 는
규칙이 아예 안 걸린 것이다. **방향이 반대다.**

### 남는 계기 교훈

`git check-ignore` 의 **침묵을 「규칙 밖」으로 읽지 마라.** 추적 중인 파일에도
침묵한다. 무시 규칙을 물을 때는 `--no-index` 를, 추적 여부를 물을 때는
`git ls-files` 를 써라 — **두 질문이 다르고, 한 명령이 둘 다 답하지 않는다.**
이번엔 그 둘을 한 출력에서 읽으려다 틀렸다.
