## 2. FAIL 항목

### F1 [FAIL] 시트는 89큐가 아니라 **18큐**다 — SPEC 전체가 행과 큐를 혼동한다

**측정**: 고유 `Q#` **18개** / 데이터 행 89개. 한 큐가 최대 **10행**을 갖는다.

```
Q# 별 행 수 분포 — 1행:1큐 · 2행:1큐 · 3행:4큐 · 4행:4큐 · 5행:1큐
                   6행:1큐 · 7행:3큐 · 8행:2큐 · 10행:1큐     합 18큐 / 89행
표본: Q010,BACK / Q010,WASH-U / Q010,HAZE   <- 한 큐 안의 세 그룹
```

시트의 단위는 **「1행 = 한 큐 안의 한 그룹 상태」**이지 「1행 = 1큐」가 아니다.

**걸리는 자리**:
- §2.1 「**89개 큐**가 번호와 이름으로 되읽힌다」 — 되읽으면 18이 나온다. 수용 기준으로 못 쓴다
- AC-LXSEQ4-013 「큐 N개의 슬롯 번호와 이름」 — N 의 기대값이 틀려 있다
- §B 「시퀀스 하나가 저장되고 그 아래 **큐들이** 올라가며」
- 제목 「cue-ex 시트 **89행**을 콘솔 큐로」 — 행 수 자체는 맞지만 큐 수를 암시한다

**분류 (A) 우리 문서 결함.** 근거: 정본 CSV 전수, 고유 `Q#` 18. 콘솔·감독 의도와 무관하다.

### F2 [FAIL] AC-004(행 제외)와 AC-007(부분 투입 금지)이 큐 단위에서 정면 충돌한다

                     -> 18큐 중 10큐(56%)가 반쪽으로 올라간다. 소멸하는 큐 0개.

AC-LXSEQ4-007 본문: 「투입 전 검사에서 한 행이라도 해소되지 않으면 **아무것도 보내지 않는다.**
부분 투입이 없다. … 큐는 순서가 의미를 지니므로 부분 투입이 더 나쁘다.」

두 문장은 **같은 시트에 동시에 적용될 수 없다.** AC-004 를 그대로 실행하면 10개 큐가

(c) 하나라도 걸리면 0건(-> 10/18 이 걸리므로 사실상 전량 거절).

어느 갈래든 **큐 수 기준으로 다시 세야** plan.md M1 의 「제외가 과반이면 멈추고 보고」가
의미를 갖는다. 지금 문면대로 행으로 세면 19/89 = 21% 라 안 걸리고,
큐로 세면 10/18 = 56% 라 **즉시 걸린다.** 같은 시트에서 정반대 결론이 나온다.

**분류 (A).** 근거: 두 AC 의 문면과 큐별 실측이 양립 불가하다.

### F6 [FAIL] FX 범위 제외가 틀렸다 — 근거 둘 다, 그리고 결론도

감사 도중 감독 답 둘이 도착해(리드 경유) 이 항목의 등급이 WARN 에서 FAIL 로 올라갔다.
감독 답은 **내가 직접 관측하지 않았다** — 리드가 전한 문면을 그대로 인용한다.

> ① 「FX열은 별도로 관리하고 시퀀스나 큐를 만들 때 사용.」
> ② 「FX를 만드는 기능도 이미 앱에서 만들었고 테스트도 진행했어. 다시 만들지 말고
>    기능이 있는지 먼저 살펴봐.」

`spec.md` §6 이 FX 제외에 근거 둘을 댔다. **둘 다 갈렸다.**

**근거 ① 「이 시트의 FX 셀은 전부 비어 있다」 -> 거짓.** 내 독립 측정(정본 CSV, awk):

```
FX 계열 4열(FX·FX-Rate·FX-Phase·FX-Width) 비어있지 않은 셀   115
FX 가 든 행                                                  47 / 89 (52.8%)
FX 가 든 큐                                                  16 / 18 (88.9%)
비교: SPEC 이 확정 입력으로 잡은 COL 은 48셀 — FX 가 2.4배 크다
```

세 계기가 독립으로 같은 값을 냈다(plan 레인 pre-audit · 리드 · 나).
**큐 단위 88.9% 는 이 회차에 처음 나온 값이다** — 행 단위 52.8% 보다 무겁다.
이대로 구현하면 **18큐 중 16큐가 이펙트 없이 선다.**

**근거 ② 「3단계 이펙트 경로가 별도이고」 -> 전제는 참, 결론이 안 따라온다.**
별도로 관리되는 것은 맞다. 그런데 감독 답 ①이 「**시퀀스나 큐를 만들 때 사용**」이라고 한다 —
**별도 관리와 큐 참조는 배타가 아니다.** `COL.01` 이 별도 프리셋 풀의 색을 가리키면서
큐에 실리는 것과 **같은 구조**다. 「3단계 소관이니 4단계에서 빼도 된다」는 추론이 성립하지 않는다.

**따라서 `FX` 는 4단계 범위 안이다.**

**세 층 전부에 등재돼 있다.** 내부 함수가 아니라 모델이 부를 수 있는 정식 도구다.

이것이 이 결함에서 가장 아픈 자리다:
**`spec.md` §3 이 「등재 도구 37종 전수에 `import_lxseq_cues` 가 없다」고 적는다.**
37종을 **전수로 훑으면서** `find_fx`·`instantiate_fx`·`compose_fx` 를 지나쳤다.
없는 것을 찾으러 목록을 열었고, 있는 것을 못 봤다. **능력이 눈앞의 목록 안에 있었다.**

#### F6-b 처방의 크기 — 만드는 것이 아니라 연결이다

「FX 를 범위에 넣는다」가 **「FX 지원을 새로 만들어라」로 읽히면 틀린다.**
정확히는 **`FX.01~FX.08` 참조를 기존 `find_fx`/`instantiate_fx` 로 잇는 배선이 SPEC 에 없다**이다.
새 이펙트 엔진이 아니라 **참조 해석 한 겹**이다. 이 구분이 처방의 크기를 완전히 바꾼다.

#### F6-c 계약 적합성 — 리드가 확인을 요청한 축. **기본 목적지로는 안 맞는다**

`completed` 라도 계약이 안 맞으면 배선이 안 된다. `instantiate_fx` 등재 설명을 직독했다:

> It creates ONE sequence with ONE cue, and assigns an executor only if you passed one.
> **It never overwrites an existing sequence.**

**기본 목적지로는 4단계에 못 쓴다.** FX 참조 30건을 그대로 부르면 **시퀀스가 30개 생긴다** —
SPEC-004 가 원하는 것은 시퀀스 **1개** + 큐 18개다.

그런데 같은 설명이 대안을 준다:

> pass destination 「preset」 EXPLICITLY for the operator flow (a labeled preset),
> or omit it for a sequence + cue (the parameter default)

그 경로가 코드에 실재한다: `_fx_preset_destination`(:5814) · `_deliver_fx_plan`(:5894).

**그래서 배선의 형태는 이것이어야 한다:**

```
FX.NN  ->  find_fx (이름으로 fx_id)  ->  instantiate_fx(destination=preset)  ->  라벨 붙은 FX 프리셋
                                                                                        ^
                                                        큐가 그 프리셋을 참조 (COL 과 같은 구조)
```

감독 답 ①의 「별도로 관리하고 큐를 만들 때 사용」과 정확히 맞는다.

🔴 **다만 빠진 고리가 하나 있다.** `FX.01~FX.08` 이라는 어휘가 **코드 어디에도 없다**:

```
grep -rn "FX\.0" server/     ->  0건 (__pycache__ 제외)
```

`find_fx` 는 **이름**으로 찾는다. 시트의 `FX.01` 이 fx 라이브러리 항목의 이름인지,
콘솔 FX 프리셋 풀의 슬롯 번호인지, 조명감독의 자체 명명인지가 **미정**이다.
`COL.01` 이 어떻게 풀리는지와 나란히 놓고 정해야 한다. **(C) 감독 확인.**

부수 **(C)**: `FX` 열 값이 두 성질로 섞여 있다. 내 측정 —

```
OFF     17건   <- 참조가 아니라 상태 명령으로 보인다
FX.01 8 · FX.08 5 · FX.03 5 · FX.05 4 · FX.02 4 · FX.04 2 · FX.07 1 · FX.06 1   (참조 30건)
```

감독 답 ①을 보면 `OFF` 는 「이 큐에서 이펙트 안 씀」으로 읽는 것이 자연스럽지만
**아직 확정이 아니다.** 파서가 참조와 상태 명령을 같은 열에서 갈라야 한다.

**분류 (A) 우리 문서 결함.** 근거: 근거 ①은 실측 115셀로 반증, 근거 ②는 감독 답으로 반증,
능력 부재 가정은 등재 3층 실측으로 반증.

**메모(측정 규율)**: 리드가 인용한 `_fx_preset_destination` :5768 · `_deliver_fx_plan` :5848 은
실측과 각각 **46행 어긋난다**(:5814 · :5894). 결론에는 영향이 없지만, 인용 줄번호는
이 감사가 계속 밟은 자리라 적어 둔다.

## 3. 🔴 「없다」로 단정하고 그 위에 결정을 얹는 형태 — 이 감사의 가장 이전 가능한 산출

리드가 오늘만 **네 번째**라고 지목했다. 셋은 리드의 관측이고 넷째는 내가 실측했다.

| # | 단정 | 열어 보니 |
|:--:|---|---|
| 1 | 픽스처 타입 54종 「없다」 | 상태 셋을 뭉갠 것일 수 있다 (리드, 측정 중) |
| 2 | 앱 능력 「안 열렸다」 | 3단계까지 실기 도달해 있었다 (리드) |
| 3 | 큐 확인 수단 「불가」 | `cue_monitor._cue_items` 가 이미 있었고 LIVE-VERIFIED (**이 SPEC 이 스스로 반증**) |
| 4 | FX 「범위 밖」 | 만드는 기능이 `completed` SPEC 둘 + 등재 도구 3종으로 있었다 (**내 실측**) |

**넷 다 「없다/안 된다」로 단정하고 그 위에 결정을 얹었고, 넷 다 열어 보니 있었다.**

3번과 4번이 **같은 SPEC 안에서 반대 방향으로** 일어난 것이 이 감사의 핵심 관찰이다.
이 SPEC 은 3번에서 「저장소가 이미 갖고 있다 — 짓기 전에 찾아라」를 실제로 수행해
카드 전제를 반증했다. **그 성공을 FX 에는 적용하지 않았다.**

그리고 형태가 한 겹 더 깊다. `spec.md` §8 이 「`FX` 4열이 전부 비어 있는지 안 셌다」를
**정직하게 고백**했다. 하지만 **「FX 기능이 이미 있는지 안 찾아봤다」는 고백은 없다** —
없다고 가정한 것을 **가정인 줄도 몰랐다.** 안 잰 것은 적을 수 있지만,
안 물은 것은 적히지 않는다.

**교훈 둘, 이름 붙여 남긴다:**

1. **정직한 gap 절은 결정의 근거가 될 수 없다.** §8 의 「안 셌다」가 §6 의 범위 결정을
   사실상 떠받쳤다. 미측정을 적어 두는 것과 미측정 위에 결정을 세우는 것은 다른 일이다.
   문면은 정직했고 **결정이 그 위에 섰다.**
2. **「저장소가 이미 갖고 있는가」를 안 물은 것이 이 SPEC 의 구조적 결함이다.**
   범위에서 무엇을 뺄 때는 「이 시트에 값이 있나」와 **「이 능력이 이미 있나」를 따로 물어야 한다.**
   전자만 물으면 능력이 있어도 안 보인다 — 그리고 이 SPEC 은 전자조차 안 재고 뺐다.

## 4. AC-013 되읽기 한계 서술의 정확성 — 리드 첫째 물음

**결론: 서술은 정확하다. 과장도 축소도 아니다.** 다만 **불완전**하다.

`_cue_items`(:145-162) 직독. 함수는 자식마다 `no` 와 `name` 두 키를 넣고,
`cueNo` 가 정수일 때만 `cue_no` 를 더한다. 값 필드는 어디에도 없다.

| SPEC 서술 | 코드 | 판정 |
|---|---|:--:|
| 「슬롯 번호·이름·큐 번호만 싣는다」 | 세 키가 전부 | **정확** |
| 「큐 내용(어느 그룹에 어떤 값이 실렸는지)은 이 경로로 안 온다」 | 값 필드 없음 | **정확** |
| 「`cue_no` 는 응답기 1.5.0+ 에서만」 | docstring :146-148 이 그대로 적는다 | **정확** |
| 「그 아래면 슬롯 번호만 오고 이 SPEC 은 그 경우에도 성립해야 한다」 | `isinstance` 실패 시 키 자체가 없다 | **정확** |

**빠진 것 둘** (축소는 아니고, 이 SPEC 이 안 쓴 여지다):

1. `build_executor_cue_progress` 는 `_cue_items` 보다 **더 준다** — `sequence_name`(:234)과
   `current_cue`(:236, `_read_current_cue` 가 시퀀스 핸들의 `CurrentCue` 를 읽는다).
   재생 위치는 내용은 아니지만 되읽기 재료다. SPEC 은 이 둘을 안 적었다
2. F3 의 도달 문제 — 정확한 서술이지만 **닿을 수 없는 함수**에 대한 서술이다

## 5. AC-004 복귀 경로 — 리드 둘째 물음. **없다, 그리고 걱정보다 나쁘다**

리드가 「없다를 먼저 가정하고 찾아라」고 했다. 셋을 찾았고 **셋 다 경로가 아니다.**

| 자리 | 문면 | 왜 경로가 아닌가 |
|---|---|---|
| spec.md §9 | 「감독 답이 온 뒤 POS·LED-W·BM 을 확정 입력으로 승격」 | 절 제목이 「후속 후보 — **카드로 만들지 않는다**」다. 계기가 명시적으로 없다 |
| acceptance.md §D | 「답이 오면 AC-004 가 바뀐다」 | **누가** 바꾸는지 없다 |
| plan.md M0 #4 | run 단계가 「감독 답이 왔는가」를 재고 「왔으면 §4.2 가 바뀐다」 | 🔴 **run 단계는 이것을 할 수 없다** |

🔴 셋째가 결정적이다. 소유권 규칙상 run 단계(`manager-develop`)는
`spec.md`/`plan.md`/`acceptance.md` **본문을 수정할 수 없고**, 필요하면 blocker report 를 내고
오케스트레이터가 `manager-spec` 에 재위임해야 한다
(`.claude/rules/moai/development/spec-frontmatter-schema.md` § Forbidden ownership crossings).
**plan.md 가 run 단계에 구조적으로 금지된 행위를 지시한다.**

게다가 SPEC 이 `completed` 로 닫힌 뒤라면 `completed -> in-progress (amendment)` 전이
(`amendment_of:` + HISTORY `## Amendments`)까지 필요하다.

**결과**: 감독 답이 도착해도 그것을 받아 SPEC 을 되돌릴 **주체·계기·산출물이 하나도 없다.**
답을 받아 놓고 SPEC 을 다시 쓰게 된다 — 리드의 우려가 그대로 성립한다.

**그리고 이것은 가설이 아니다.** 감사 도중 **FX 에 대한 감독 답이 실제로 도착했고**,
그 답을 받아 SPEC 을 고칠 경로가 없어서 이 판정문이 그 자리를 대신하고 있다.
POS·LED-W·BM 답이 왔을 때도 똑같을 것이다.

부수 결함: AC-004 는 제외 수와 사유를 「산출물」에 실으라고만 하고 **그 산출물이 어디
남는지 경로가 없다.** 기록이 휘발되면 답이 왔을 때 대조할 대상도 없다.

**처방 방향(제안 — 결정은 감독·리드)**: 제외 행을 고정 경로 파일로 남기고
(예: `.moai/specs/SPEC-COPILOT-LXSEQ-004/held-rows.md`), 복귀를 후속 SPEC 의 **착수 조건**으로
명시하거나, §9 에서 「카드로 만들지 않는다」를 걷어내고 복귀 카드를 세운다.

## 6. WARN 항목

### F7 [WARN] `Dim` 빈칸 13행의 의미가 미정 — 같은 함정을 한 열에서만 봤다

**측정**: `Dim` 빈칸 **13/89행** · 숫자 아닌 값 **0건** · `DIM.` 토큰 0회.

AC-LXSEQ4-006 은 페이드에 대해 명시적으로 못 박는다:

> `0.0` 과 빈칸을 **다르게** 다룬다 — `0.0` 은 「0초」이고 빈칸은 「지정 없음」이다.
> 검사가 둘을 갈라 단언한다.

**AC-LXSEQ4-003 은 `Dim` 에 대해 같은 구분을 하지 않는다.** 「`55` 가 0-100 숫자로 해석된다」와
「`DIM.01` 같은 참조가 오면 거부」뿐이다. 빈칸 13행이 「0%」인지 「이 큐에서 이 그룹은 건드리지
않음」인지 정해져 있지 않다 — **조명에서 이 둘은 정반대 결과다**(끈다 vs 그대로 둔다).

**분류 (C) 문서 의도 미확인.** 시트만으로 안 갈린다.

### F8 [WARN] 되읽기 0건을 부재로 읽는 위험에 AC 가 없다

SPEC §2.1 은 t87·t105 를 **인용한다** — 「이름만 답한다, 값은 미판독」·「값 판독 채널은
존재를 답하고 값은 안 준다」. 그런데 그 계열의 다른 절반을 AC 로 안 옮겼다.

이 저장소가 인접 채널에서 이미 만난 형태: **내용이 있는 객체도 빈 목록을 답할 수 있다.**
`_cue_items` 가 빈 목록을 돌려주면 산출물에 「0큐」로 적히는데,
그것이 「투입 실패」인지 「채널이 안 보여준 것」인지 가르는 AC 가 없다.

AC-LXSEQ4-012 는 사유 문자열 분리를 요구하지만 그 넷은 전부 **투입 전** 거절 갈래다
(열 집합 어긋남 · 그룹 이름 없음 · 미확정 입력 · 점유 슬롯). **되읽기 0건은 그 목록에 없다.**
F3 과 겹치면 특히 위험하다 — 실행기 미배정 때문에 0이 나오는데 「투입 실패」로 읽힌다.

**분류 (A).** 근거: 저장소가 이미 기록한 실패 형태이고 SPEC 이 인용까지 했다.

### F9 [WARN] 검증가능성이 기준선 대비 후퇴했다

리드 지시대로 SPEC-COPILOT-LXSEQ-003 과 기계적으로 대조했다.

## 7. plan 레인이 자기 감사로는 못 봤을 축 (리드 요청 항목)

plan 레인은 「자기 감사는 내가 애초에 안 떠올린 축을 못 찾는다」고 스스로 적었다. 여섯이다.

1. **행 ↔ 큐 축** (F1·F2) — 가장 큰 것. 시트를 「행」으로 읽는 프레임 안에서는
   AC-004 와 AC-007 이 서로 모순으로 보이지 않는다. 프레임 밖에서만 보인다
2. **호출 사슬 축** (F3) — `_cue_items` 를 직독해 반환을 정확히 서술했지만, **누가 그것을
   부르는지**는 다른 물음이다. 「함수가 무엇을 주나」와 「그 함수에 닿을 수 있나」의 구분
3. **형제 대조 축** (F4) — 「새 도구를 만든다」에 집중하면 「기존 도구가 무엇을 지키나」를
   옆으로 재지 않게 된다. 안전 게이트는 그 대조에서만 드러난다
4. **소유권 축** (§5) — plan.md 가 run 단계에 지시한 행위가 run 단계에 **허용되는지**는
   SPEC 밖 규칙이다. SPEC 안만 보면 완결돼 보인다
5. **기존 능력 축** (F6) — 「이 능력이 이미 있나」를 물어야 보인다. §3 이 도구 37종을
   전수로 훑으면서 FX 도구 셋을 지나쳤다 — **찾는 것이 정해져 있으면 있는 것이 안 보인다**
6. **저장소 학습 축** (F8) — t87·t105 를 인용까지 하고도 AC 로 안 옮겼다.
   인용은 정직했고 **반영이 없었다**

## 9. 구현 진입 전에 고칠 것 (FAIL 해소 조건)

1. **F1** — 「큐」와 「행」을 문면에서 분리한다. 18큐 / 89행을 §2.1 · AC-013 · §B 에 반영
2. **F2** — 제외의 **단위**를 정한다(큐 통째 / 그룹만 / 전량 거절 중 하나). AC-004 와 AC-007 을
   같은 단위로 다시 쓴다. plan.md M1 의 「과반이면 멈춘다」도 큐 기준으로 다시 센다
   (행 기준 21% -> 큐 기준 56%, 정반대 결론)
3. **F3** — 되읽기 경로를 `query_state("DataPool/Sequences/<no>")` 직접 호출로 다시 적거나,
   시퀀스를 실행기에 배정하는 단계를 범위에 넣는다. AC-001 의 지목을 고친다
4. **F4** — AC-010 에 `action: preview|apply` 기본 preview · `additionalProperties: False` ·
   바이트 입수 경로(경로 인자 금지)를 넣는다. `registry.py` 행을 덮는 AC 를 더한다
5. **F5** — 큐 이름 규칙과 유일성을 AC 로 세운다. 유일한 확인 수단이 AC 밖에 있으면 안 된다
6. **F6** — `FX` 4열을 범위에 넣는다. **새로 만들지 말고 잇는다** —
   `find_fx` -> `instantiate_fx(destination=preset)` -> 큐가 그 프리셋 참조.
   §4.1 표에서 FX 를 「이번 범위 밖」에서 옮기고, §6 의 두 근거를 삭제한다.
   `FX.01~08` 의 해석(F6-c)과 `OFF` 의 의미는 감독 답을 받고 확정한다

WARN 셋(F7~F9)은 진입을 막지 않지만, **F9 는 이 SPEC 이 실기 0회로 쓰였다는 점에서
가볍지 않다** — AC 문면이 유일한 계약이다.

- **실기 0회.** 콘솔에 접촉하지 않았다. 응답기 버전 · 쇼 지문 · `DataPool/Sequences` 빈 슬롯 ·
  `FX.01~08` 이 콘솔 풀에 실재하는지 — 전부 안 쟀다. **M0 의 몫이고 (B) 축이다**
- **`find_fx`/`instantiate_fx`/`compose_fx` 의 본문을 안 읽었다.** 등재 3층과 등재 설명만 읽었다.
  F6-c 의 계약 판정은 **등재 설명 문면 근거**이고 실행 확인이 아니다
- **`server/fx/` 의 loader·matching·schema 를 안 읽었다.** 라이브러리 3종의 항목 이름이
  `FX.01` 형태와 맞는지 안 봤다 — F6-c 의 (C) 가 그 미측정 위에 서 있다는 뜻이다
- **FXGEN-001·FXLIB-001 의 인수 기준을 안 열었다.** frontmatter status 만 읽었다.
  리드가 「계약이 재사용 가능한지 보라」고 했고, 나는 **등재 설명으로만** 답했다 —
  두 SPEC 의 AC 대조는 **안 한 것이 맞다**
- **t71 카드 본문을 안 읽었다.** 큐에 살아 있다는 것만 확인했다(대조군 t70·t203 동반)
- **`_read_current_cue` 의 실동작을 안 쟀다.** 코드만 읽었다
- **뮤테이션 0건.** 코드 변경이 없어 걸 대상이 없다. 대신 인용을 전수로 열었다
- **SPEC-001·002 와는 대조하지 않았다.** 리드가 지정한 기준선은 003 하나다
- **감독 답 둘을 직접 관측하지 않았다.** 리드가 전한 문면을 인용했다. 내가 실측한 것은
  그 답이 가리키는 **코드 쪽 사실**(등재 3층 · completed SPEC 둘 · `server/fx/`)이다
- **`pre-audit-finding.md` 의 값을 릴레이하지 않고 전부 재측정했다.** 일치했다 —
  그러나 일치는 내 측정의 결과이지 근거가 아니다
