## 1. 카드가 안 쟀다고 적은 값 — 경로 비율

`MEMORY.md` = 24,997B (2026-08-31). 성분 분해:

| 성분 | 바이트 | 비중 |
|---|---:|---:|

| 표시 텍스트 | 5,756 | 23.0% |
| 경로 | 4,912 | **19.7%** |
| 링크 없는 줄(머리말·소제목) | 707 | 2.8% |
| 링크 문법 `[` `]` `(` `)` | 492 | 2.0% |
| 합 | 24,998 | 100.0% |

⚠️ 합이 24,998 로 1 크다. 계기가 줄마다 개행 1B 를 더하는데 파일 끝 개행이 한 번 중복 계산된다.
오차 1B(0.004%)이고 방향이 고정이라 비율 결론에 안 걸린다 — 숨기지 않고 적는다.

🔴 **카드가 겨눈 것은 셋째로 큰 성분이다.** 옵션 (1)(2)를 다 해도 상한은 18.2% 다.

## 2. 형태 비율 — 리드가 요구한 첫 걸음

|---|---:|---:|---|

🔴 **카드가 일반화한 표본(형제 붙임)은 항목의 6.6% 를 대표한다.** 바이트로는 더 작다 —
형제 줄 전체가 1,695B 로 파일의 6.8% 이고, 자기 줄이 22,596B 로 **90.4%** 다.

🔴 **인라인 참조 2건은 항목이 아니라 본문이다.** 경로 73B(전체 경로의 1.5%)를 차지하는데,
파일명 규약을 바꿔도 이 둘은 산문 안에 박혀 있어 같이 못 줄인다. 기계 분류는 이걸 「형제 항목」으로 셌다.

## 3. 카드와 리드의 표본이 왜 그렇게 보였나

| 주장 | 출처 | 전수 실측 | 판정 |
|---|---|---|---|
| 표시 4B · 경로 34B | 카드(t182 표본 1건) | 표시 평균 46.8B · 경로 평균 39.9B | **역전** |
| 형제 붙임 약 66B | 리드(표본 1건) | 평균 60B · 중앙 49B | 근사 |
| 형제 붙임의 절반이 경로 | 리드(표본 1건) | 항목 조각 기준 **61.8%** / 형제 줄 기준 **35.0%** | 분모에 따라 갈림 |
| 새 줄 330~390B | 리드(표본 1건) | 평균 211B · 중앙 191B · 최대 453B | 상위 구간 |

**표시가 경로보다 크다**(5,756 > 4,912)는 카드 전제의 정반대다. 이유는 형태에 있다 —
형제 붙임은 라벨을 짧게 쓰고(`[t182]` 4B), 자기 줄은 서술형 제목을 쓴다(최대 97B).
즉 **카드 표본의 「표시 4B」는 형제 붙임 형태의 성질이지 색인의 성질이 아니다.**

🔴 **분모 둘이 62% 와 35% 로 갈린다.** 「형제 붙임 1건을 더 붙이는 한계비용」을 물으면 조각이 분모라 62%,
「형제 줄이 파일에서 먹는 자리」를 물으면 줄이 분모라 35% 다. 둘 다 참이고 답하는 질문이 다르다.

표적 크기가 13,131B 대 4,912B 라, 같은 절약을 내는 데 본문 쪽이 **훨씬 낮은 압축률**로 된다.

🔴 **넷째 옵션이 카드 목록에 없었다.** 표시 텍스트는 5,756B(23.0%)로 경로보다 큰데,
경로와 달리 **줄여도 탐색이 안 깨진다**(링크는 여전히 해석된다). 카드가 이 축을 안 봤다.

## 7. 안 잰 것

- 🔴 **파일명을 줄였을 때 잃는 것을 안 쟀다.** 카드가 물은 「어느 쪽이 비싼지」의 나머지 반쪽이다.
  이름에서 날짜·역할이 빠지면 파일을 찾기 어려워지는데, 그 비용은 바이트로 안 나온다.
  **그래서 이 보고서는 (1)을 하지 말라고 말하지 않는다 — 표적이 셋째로 작다고만 말한다.**
- **본문의 압축 가능량을 안 쟀다.** 위 표의 「15% 압축」은 실측이 아니라 산술 예시다. t173 소관.
- **표시 텍스트의 압축 가능량도 안 쟀다.** 넷째 옵션은 표적 크기만 재고 실현 가능량은 안 쟀다.
- **시점 1건이다.** 색인은 세션마다 자라고 잠금 없이 동시에 쓰인다(t178) — 이 24,997B 는
  이 순간의 값이다. 인용할 때 날짜를 떼지 마라.
- **인라인 참조는 2건만 확인했다.** 다중 링크 줄 6개는 전수로 열었지만, 자기 줄 107개 안에
  숨은 인라인 참조는 정의상 없다(링크 1개 = 그 항목 자신). 이건 구조로 보장된다.

### 10.1 정정 — 위 §10 의 예측은 절반만 맞았다 (push 에서 반증됨)

§10 에 「프로브를 규칙에 맞게 다시 썼다」고 적고 push 했더니 **pre-push 게이트가 막았다.**
지우지 않고 고지한다 — 틀리게 주장했다는 사실이 감사 기록이다(규약 §5).

```
FAILED server/tests/test_overlap_preserve.py::TestTouchedFilesPassLint::test_ruff_format_reports_no_change
  Would reformat: .moai/reports/t191/probes/index_budget.py
  1 file would be reformatted, 411 files already formatted
```

🔴 **ruff 축이 둘인데 나는 하나만 읽었다.**

| 축 | 명령 | 내 예측 | 실제 |
|---|---|---|---|
| 린트 | `uv run ruff check` | 통과 | **통과** (`All checks passed!`) — UP031·E501 회피는 유효했다 |
| 포매터 | `uv run ruff format --check` | (안 봤다) | **실패** — 게이트가 막음 |

`pyproject.toml` 의 `[tool.ruff.lint] select` 를 읽고 「규칙을 다 봤다」고 여겼는데,
게이트가 강제하는 것은 `[tool.ruff.lint]` 뿐 아니라 **포매터 축**이기도 하다.
설정 파일에 `[tool.ruff.format]` 절이 바로 아래 있었는데 린트 절만 읽고 멈췄다.

🔴 **계기 오류가 하나 더 있었다.** `which ruff` 가 not found 를 답하길래 「이 트리에서 못 돌린다,
push 가 최종 판정이다」로 §10 에 적었다. **틀렸다** — 이 트리에 `.venv` 가 있고 `uv run ruff` 로 돈다.
우주를 PATH 로 잡았는데 실제 우주는 프로젝트 venv 였다. 오늘 이 세션에서 **같은 형태의 두 번째**다
(첫 번째: 규약 파일을 primary 절대경로로 물어 「없다」를 얻음 → 실제로는 primary 가 다른 브랜치에 주차).
**둘 다 술어는 맞았고 우주가 틀렸다.**

📏 수정 후 검산: `uv run ruff format` 이 5줄을 1줄로 접었고(리스트 컴프리헨션),
프로브 출력은 **바이트 동일**(`diff` 무차이)이라 포매터가 동작을 안 바꿨다.
