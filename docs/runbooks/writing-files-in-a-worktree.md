# 워크트리에서 파일 쓰기 — 어느 형태가 통과하는가

다른 워크트리에서 `EnterWorktree` 로 **이동해 들어간** 세션에서는 `Write` · `Edit` 도구가
막힌다(카드 t14 ①, 재현 6회 · 경계는 t33 이 대조군 7건으로 고정). 그러면 Bash 가 유일한
쓰기 수단이 되는데, **Bash 도 형태에 따라 거부된다.** 어느 형태가 통과하는지
몰라서 매번 시행착오를 겪었고, 그 과정에서 사고가 두 번 났다 — JSON 하나가 깨졌고
(t13) 문서에 오타가 들어갔다(t21).

이 문서는 그 형태를 실측으로 고정한다. 추측하지 말고 표를 보라.

## 먼저 — 이 마찰을 통째로 피하는 길이 있다 (t33, 2026-08-23)

아래 표는 **`EnterWorktree` 로 형제 워크트리에서 이동해 들어간 세션**에서 참이다. 그런데
**워크트리 안에서 세션을 시작하면 `Write` · `Edit` 이 그대로 동작한다.**

```
세션이 워크트리 t33 안에서 시작 → 워크트리 안에 Write   ✅ 통과
세션이 형제 워크트리에서 시작 후 EnterWorktree → 같은 경로에 Write   ❌ 거부
```

막히는 이유는 워크트리라서가 아니라 **거기서 시작하지 않아서**다. 프로젝트 루트는 세션이
시작된 디렉터리에 고정되고 `EnterWorktree` 는 cwd 만 옮긴다. 이 저장소에서는 세션 시작
지점(`orca/…/LX-SEQ`)과 카드 워크트리(`.claude/worktrees/<id>`)가 **같은 저장소의 형제
워크트리**라, 카드 워크트리는 프로젝트 루트 밖이 된다.

`claude --add-dir` 로는 풀리지 않는다 — 실측 거부(U-8 대조군 6).

**따라서 아래 Bash 우회는 「이동해 들어간 세션」의 대처법이다.** 워크트리를 세션의 시작
지점으로 삼을 수 있으면 이 문서 전체가 필요 없다. 근거와 대조군 7건: `docs/upstream/moai-harness-findings-20260822.md` U-8.

## 적용 범위 — 이 규칙이 참인 조건

아래 표와 규칙은 **`EnterWorktree` 로 들어간 격리 세션 안에서만** 참이다. 그 밖에서는
무의미하다 — 규칙 3(`cat` heredoc 으로 파일 쓰지 않기)이 특히 그렇다.

거부 메시지 자체가 조건을 말한다.

```
This session is isolated in the worktree /…/.claude/worktrees/t14, but this
command is too complex to verify that it stays inside the worktree.
```

범용 Bash 가드가 아니라 **워크트리 세션 가드**이고, `EnterWorktree` 세션에서만 무장한다.

리드 세션 실측(2026-08-23): 파일시스템상 워크트리 안에 있으나 `ExitWorktree` 로 나온
세션에서는 아래 G(중괄호 리터럴)가 **통과했다.** 같은 명령이 격리 세션에서는 거부된다.
즉 트리거는 워크트리에 있느냐가 아니라 격리 세션이냐다.

그러면 인과가 정리된다. 가드는 명령의 대상 경로가 워크트리 안에 머무는지 **정적으로 검증**하려 한다. 중괄호(확장 가능)와 셸 리다이렉트(대상이 실행 시점에 정해짐)는 둘 다 그 정적 분석을 무력화하므로 각각 독립적으로 거부를 부른다. heredoc 자체는 무관하다.

**이 조건을 모르고 격리 세션 밖에서 시험하면 통과한다.** 그때 이 문서를 못 믿게 되는 것이 실제 위험이라 맨 앞에 적는다.

## 실측 표

대조군으로 변수를 하나씩만 바꿔 쟀다(카드 t14, 워크트리 `t14`, `596f6fd`).

| # | 형태 | 결과 |
|---|---|---|
| A | `cat <<EOF > /tmp/f.txt` · 중괄호 없음 | ❌ 거부 |
| B | `cat <<EOF > f.txt` · 워크트리 안 · 중괄호 없음 | ❌ 거부 |
| C | `python3 - <<PY` · 중괄호 리터럴 + f-string | ❌ 거부 |
| D | `python3 - <<PY` · 중괄호 없음 · 파이썬이 파일 씀 | ✅ 통과 |
| E | `cat <<EOF` · 리다이렉트 없음 | ✅ 통과 |
| F | `python3 - <<PY` · `dict()` 호출 | ✅ 통과 |
| G | `python3 - <<PY` · `{"a": 1}` 리터럴 하나만 | ❌ 거부 |
| — | `printf %s\n ... > f.txt` · 중괄호 포함 | ✅ 통과 |

F 와 G 는 **한 글자만 다르다** — `dict(a=1)` 대 `{"a": 1}`. 결과가 반대다.

## 규칙 셋

거부 조건은 둘이고 서로 독립이다. heredoc 이 있고, **그 안에 중괄호가 있거나**, 명령에
**셸 리다이렉트가 붙으면** 거부된다. heredoc 자체는 문제가 아니다(E 가 통과한다).

1. **기본은 printf 다.**
   `printf %s\n 한 줄 또 한 줄 > 파일` — 각 행을 작은따옴표로 감싼 인자로 넘긴다.
   중괄호가 있어도 통과한다(t13 에서 `package.json` 을 이 방식으로 다시 썼다).
   **함정**: 내용에 작은따옴표가 있으면 못 쓴다. 백슬래시-따옴표를 넣으려면
   `\"` 로 적는다 — `\\"` 로 적으면 백슬래시 둘이 나가 JSON 이 깨진다(t13 사고).

2. **내용에 작은따옴표가 있거나 구조를 다뤄야 하면 python3 heredoc 이다.**
   단 두 가지를 지킨다.
   - 중괄호 리터럴을 쓰지 않는다. `dict()` · `set()` · `list()` 를 쓴다.
   - 셸 리다이렉트를 붙이지 않는다. 파일은 `Path(...).write_text(...)` 로 쓴다.

3. **`cat` heredoc 으로 파일을 쓰지 않는다.** 리다이렉트가 붙는 순간 거부된다.
   출력만 볼 때는 써도 된다.

## 쓴 다음에 반드시 확인한다

우회는 매번 **다른 방식으로** 실패한다. 그래서 쓰기 자체보다 확인이 중요하다. 형태별로
확인 명령이 다르다.

| 쓴 것 | 확인 |
|---|---|
| JSON | `python3 -c "import json;json.load(open(PATH))"` |
| 파이썬 | `python3 -c "import ast;ast.parse(open(PATH).read())"` |
| 파일 전체를 다시 쓴 경우 | `git diff PATH` — 의도한 줄만 바뀌었는지 |
| 셸 인용을 escape 한 경우 | `grep -n` 로 그 문자를 전수 조회 |

마지막 행이 t21 에서 실제로 값을 했다. 인용부호 escape 가 따옴표 두 개를 남겼는데
`grep -n` 전수 조회로 잡았다. 눈으로 읽어서는 못 봤을 것이다.
