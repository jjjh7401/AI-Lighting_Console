# M1 — 왜 조명감독이 바이브 코딩을 해야 하는가 · 🟢 2h

💬 **한 줄로 말하면**
> 내가 매번 손으로 하는 지겨운 작업이 있는데, **아무도 그걸 자동으로 해주는 프로그램을 안 만들어 준다.**
> 예전엔 그래서 포기했는데, 지금은 **AI에게 시켜서 내가 만들 수 있다.**

🔑 **처음 나오는 말**: 바이브 코딩 · AI 모델

---

## M1-1. 왜 그 프로그램은 세상에 없나

세 가지 이유가 있고, **셋 다 "그래서 네가 만들어야 한다"로 끝난다.**

| 이유 | 무슨 뜻인가 | 그래서 |
|---|---|---|
| **사려는 사람이 너무 적다** | 그 기능이 필요한 사람이 전 세계에 수십 명일 수도 있다 | 회사가 팔 물건으로 안 만든다 |
| **현장마다 다 다르다** | 같은 콘솔을 써도 극장마다 장비도 방식도 다르다 | 하나 만들어 다 팔 수가 없다 |
| **프로그래머는 조명을 모른다** | 뭘 원하는지 설명하는 데만 며칠 걸린다 | 돈은 많이 들고 결과는 어긋난다 |

💡 **쉬운 말로**
> 시장이 작아서 안 만들고, 다 달라서 못 만들고, 설명이 어려워서 안 된다.
> 그런데 **당신은** 팔 걱정이 없고, 당신 현장만 알면 되고, 설명할 필요가 없다 — **이미 알고 있으니까.**

---

## M1-2. 무엇이 바뀌었나

예전에 프로그램을 만들려면 **두 가지**가 다 필요했다.

```
   예전
   ┌─────────────┐   ┌──────────────┐   ┌──────┐
   │ 조명을 안다  │ + │ 코드를 쓸 줄 안다 │ = │ 프로그램 │
   └─────────────┘   └──────────────┘   └──────┘
                            ↑
                    여기서 대부분 막혔다

   지금
   ┌─────────────┐   ┌──────────────┐   ┌──────┐
   │ 조명을 안다  │ + │ AI를 부릴 줄 안다 │ = │ 프로그램 │
   └─────────────┘   └──────────────┘   └──────┘
          ↑
   이제 이게 더 귀하다
```

💡 **쉬운 말로**
> AI는 코드를 쓸 줄 안다. 그런데 **당신 극장의 장비 배치도, 무엇이 위험한지도 모른다.**
> 그건 당신만 안다. 그래서 이제 **조명을 아는 게 강점**이 된다.

🎓 **학생에게**: 아직 현장 경험이 적어도 괜찮다. **배우는 중인 것 자체가 자산**이다 — 학교 실습실에서 반복되는 작업도 훌륭한 소재다.

---

## M1-3. 조명 하는 사람은 이미 절반을 배웠다

AI를 부리는 데 필요한 능력의 대부분을, 조명 배우는 사람은 이미 훈련받고 있다.

| 조명에서 하는 일 | AI를 부릴 때 하는 일 |
|---|---|
| 큐 순서를 짠다 *(큐 = 저장해 둔 조명 장면 하나)* | 작업 순서를 짠다 |
| 포커싱 시키고 결과를 눈으로 본다 | 시키고 결과를 확인한다 |
| 안 밝으면 **채널 → 밝기 → 패치** 순으로 본다 | 안 되면 원인을 단계별로 찾는다 |
| 리허설 없이 본공연 안 간다 | 확인 없이 실제 적용 안 한다 |
| 실수하면 공연이 멈춘다는 감각 | **되돌릴 수 없는 일**을 구분한다 |

> **새로 배울 건 코딩이 아니다. 이 습관을 컴퓨터에게도 쓰는 방법이다.**

## M1-5. 실습 — 내 작업 꺼내기

각자 **매번 손으로 하는데 지겨운 작업 1개**를 아래 양식으로 적는다.
이 종이는 마지막까지 보관하고 **수료 프로젝트의 씨앗**이 된다.

```
무슨 작업 :
얼마나 자주 :
한 번에 몇 분 :
지금 어떻게 하나 :
틀리면 무슨 일이 나나 :
```

🎓 **학생 트랙 대안**: 실습실 장비 점검, 동아리 공연 준비, 과제 제출용 자료 정리 — 조명이 아니어도 된다.

# M2 — 무엇으로 만드나: AI 모델과 도구 선택 · 🟢🔵 3h

💬 **한 줄로 말하면**
> AI가 여러 종류인데, **어디에 뭘 쓰는지**가 다르다.
> 특히 **"내가 만들 때 쓰는 AI"와 "만든 프로그램 안에서 도는 AI"는 다른 것**이다. 이것부터 구분한다.

🔑 **처음 나오는 말**: 터미널 · CLI · 컨텍스트 · 토큰 · MCP · API · 프로바이더 추상화

## M2-1. 가장 많이 헷갈리는 것부터

💡 **쉬운 말로**
> **요리사와 레시피**를 생각하면 된다.
> - 내가 **레시피를 쓸 때** 도와주는 사람 → ① 개발 도구
> - 손님이 주문하면 **주방에서 실제로 요리하는** 사람 → ② 런타임 모델
>
> 둘은 다른 사람이어도 된다.

```
   ┌───────────────────────────────────────────────────┐
   │ ① 개발 도구 — 내가 "프로그램을 만들 때" 쓰는 것      │
   │    Claude Code · Codex CLI · Antigravity CLI ·     │
   │    Cursor                                          │
   │    → 내 컴퓨터의 파일을 읽고 쓰고, 명령을 실행한다  │
   └───────────────────────────────────────────────────┘
                        ↓  이걸로 만들어낸다
   ┌───────────────────────────────────────────────────┐
   │ ② 런타임 모델 — 내가 만든 "프로그램 안에서 도는" 것 │
   │    Claude API · Gemini API                         │
   │    → 사용자의 한국어 지시를 콘솔 명령으로 바꾼다    │
   └───────────────────────────────────────────────────┘
```

**이 프로젝트도 둘이 다르다.** 만들 때는 Claude Code를 썼지만, 프로그램 안에서는 **AI를 갈아끼울 수 있게** 만들어서 Anthropic과 Google 둘 다 쓸 수 있다.

## M2-2. 개발 도구 고르는 기준 6가지

💬 **한 줄로 말하면**: **제품 이름을 외우지 말고 기준을 외운다.** 이름은 사라지고 기준은 남는다.

| # | 기준 | 쉬운 말로 | 이게 없으면 |
|---|---|---|---|
| 1 | **파일을 직접 다루나** | 내 컴퓨터 파일을 열고 고칠 수 있나 | 복사·붙여넣기 노동이 된다 |
| 2 | **혼자 계속 일하나** | 한 번 시키면 여러 단계를 스스로 이어서 하나 | 매 단계 내가 붙어 있어야 한다 |
| 3 | **얼마나 기억하나** | 앞에 한 말을 얼마나 오래 들고 있나 | 앞을 잊고 같은 실수를 반복한다 |
| 4 | **규칙을 심을 수 있나** | "우리 현장에선 이렇게 한다"를 가르칠 수 있나 | **안전 규칙을 기계로 못 지키게 한다** |
| 5 | **다른 프로그램과 이어지나** | 콘솔·도면 프로그램과 연결되나 | 혼자 뚝 떨어진 섬이 된다 |
| 6 | **돈이 얼마나 드나** | 정액인가 쓴 만큼인가, 한도가 있나 | 예상 못 한 요금이 나온다 |

> **기준 3의 "기억"**을 컴퓨터 용어로 **컨텍스트**라 한다. 사람으로 치면 지금 머릿속에 들고 있는 내용이다. 한계가 있어서 넘치면 앞부분을 잊는다.

## M2-3. 도구 지형 — 2026-08-07 조사 기준

> 표의 모든 항목은 각 제품의 **공식 문서에서 직접 확인**했다.
> 공식 문서에 없던 항목은 **"문서 미기재"**로 남겼다 — **짐작으로 채우지 않았다.**
> 출처는 §M2-8. **강의 전 반드시 재확인할 것.**

### 세 가지 종류

| 종류 | 대표 | 어떤 건가 |
|---|---|---|
| **터미널에서 도는 것** | Claude Code · Codex CLI · Antigravity CLI | 글자로 명령하는 창에서 실행. 파일과 명령을 직접 다룬다 |
| **편집기 안에서 도는 것** | Cursor 등 | 코드 편집 프로그램 안에서 동작. 코드를 눈으로 보며 작업 |
| **웹 채팅** | 각 회사의 웹 화면 | 설치 불필요. 단, **내 컴퓨터 파일을 못 만져서 도구 제작엔 부적합** |

**조명 도구를 만들려면 첫 번째(터미널)가 맞다.** 콘솔과 통신하는 코드, 콘솔에 넣을 파일, 규칙집, 점검표를 **동시에 다뤄야** 하는데 그게 전부 파일 작업이기 때문이다.

### 터미널 도구 3종 비교

> 🔵 **심화 표** — 학생 트랙은 "다 비슷한데 Claude Code가 규칙·역할 나누기가 세다" 정도만 알면 된다.

| 항목 | **Claude Code** (Anthropic) | **Codex CLI** (OpenAI) | **Antigravity CLI** (Google) |
|---|---|---|---|
| 공개 여부 | 비공개 · 구독 | **소스 공개(Apache-2.0)** | 비공개 |
| 쓸 수 있는 곳 | 터미널 · VS Code · JetBrains · 데스크톱 앱 · 웹/모바일 | 터미널 · VS Code/Cursor/Windsurf · 데스크톱 모드 | 터미널 (데스크톱 앱과 엔진 공유) |
| **역할 나누기**(서브에이전트) | ✅ 각자 기억 따로 · **권한 제한 가능** · 역할별 AI 지정 | 문서 미기재 | ✅ 동시에 여러 개 |
| **자동 검사**(훅) | ✅ | 문서 미기재 | ✅ |
| **지식 묶음**(스킬) | ✅ | 문서 미기재 | ✅ |
| **규칙 파일** | `CLAUDE.md` + 자동 기억 | `AGENTS.md` | Rules |
| **묶음 배포**(플러그인) | ✅ | 문서 미기재 | ✅ |
| **외부 연결**(MCP) | ✅ | ✅ | ✅ |
| **울타리·승인**(샌드박스) | ✅ | ✅ | ✅ OS 기본 기능 사용 |
| **예약 실행** | ✅ 클라우드·데스크톱·반복 | 문서 미기재 | 문서 미기재 |
| 쓰는 AI | Claude 5 계열 | `gpt-5.6-sol` | 문서 미기재 |
| 어떻게 쓰나 | Claude 구독 또는 개발자 계정 | ChatGPT 요금제 또는 개발자 키 | 문서 미기재 |

💡 **"문서 미기재"를 어떻게 읽나**
> **그 기능이 없다는 뜻이 아니다.** 공식 문서에서 **확인이 안 됐다**는 뜻이다.
> 이 구분이 이 과정 전체에서 가장 중요한 태도다 — **확인 안 된 걸 확인된 것처럼 적지 않는다.**

### 편집기형 — Cursor

공식 문서에서 확인된 것: **Agent 모드 · 규칙 파일 · MCP · 스킬 · 훅 · CLI**.
터미널형과 같은 기능을 갖추고 있어서, **코드를 눈으로 보며 작업하는 게 편한 사람**에겐 좋은 선택지다.

### ⚠️ Gemini CLI는 개인 사용자에게 이미 끝났다 (2026-06-18)

**무슨 일이 있었나**: 2026-06-18부터 Gemini CLI는 **개인 계정의 요청을 더 이상 처리하지 않는다**(공식 공지).

- **대신 쓸 것**: Antigravity CLI — 설치하면 기존 설정을 자동으로 옮겨 준다
- **영향 없는 사람**: 기업용 라이선스 사용자, 개발자 키 사용자
- 같은 날 관련 편집기 확장 프로그램도 개인 대상 서비스를 중단했다

💡 **이 사건이 M2에서 가장 중요한 교재다**
> 반년 전까지 **"무료로 쓸 수 있는 유일한 터미널 AI"**로 여기저기서 추천되던 도구가, **한 달 예고하고 사라졌다.**
>
> 그래서 두 가지를 배운다:
> 1. **제품 이름 말고 기준을 외운다** — 이름은 사라지고 기준은 남는다
> 2. **갈아탈 수 있게 만들어 둔다** — 남의 회사 결정이 내 프로그램을 죽이지 못하게

## M2-4. 프로그램 안에서 돌 AI 고르기

💬 **한 줄로 말하면**: 만든 프로그램 안에서 돌 AI는 **기준이 다르다.** 빠르고 싸고 정확해야 한다.

| # | 기준 | 이 프로젝트의 목표치 |
|---|---|---|
| 1 | 시킨 대로 정확히 명령을 만드나 | 문법 틀리는 비율 **5% 미만** |
| 2 | 얼마나 빠른가 | 지시부터 실행까지 **10초 미만** |
| 3 | 얼마나 싼가 | 위 둘을 통과하는 것 중 싼 쪽 |
| 4 | 같은 내용을 매번 다시 안 보내도 되나 | 규칙집 고정 부분은 재사용 |

### 갈아끼울 수 있게 만들었다

💡 **쉬운 말로 — 전구 소켓**
> **E26 소켓**을 생각하면 된다. 소켓 규격만 맞으면 **어느 회사 전구든 끼워진다.**
> 전구를 바꾸려고 등기구를 통째로 교체하지 않는다.
>
> 프로그램도 똑같이 만들어 뒀다. **AI를 바꿔도 나머지는 안 건드린다.**
> 이걸 어려운 말로 **프로바이더 추상화**라고 한다.

```
   프로그램 윗부분 (화면 · 안전장치 · 지휘 담당)
              │   ← 어떤 AI를 쓰는지 모른다
   ┌──────────┴──────────┐
   │   소켓 (공통 규격)   │
   └──────────┬──────────┘
        ┌─────┴─────┐
    Anthropic     Gemini      ← 설정 한 줄로 교체
```

**왜 이렇게 했나**: 값과 성능은 계속 변한다. 더 싸거나 빠른 게 나오면 **바로 갈아탈 수 있게** 하려고.

## M2-5. AI도 급이 있다 — 한 종류만 쓰지 않는다

💡 **쉬운 말로**: **모든 자리에 무빙을 걸지 않는 것**과 같다. 비싸고 좋은 걸 아무 데나 쓰지 않는다.

| 급 | 쓰는 곳 | 왜 |
|---|---|---|
| 크고 똑똑한 것 | 설계 · 어려운 문제 해결 · 검사 | 판단이 필요한 곳 |
| 중간 | 보통 작업 | 대부분 |
| 작고 빠른 것 | 단순 반복, **"다 됐나?" 판정** | 자주 부르니 싸고 빨라야 |

## M2-6. 돈 이야기 — 숨기지 않는다

- AI 사용료는 **진짜 나가는 돈**이고 무한하지 않다
- AI를 혼자 계속 돌게 두면(→ M5 루프) **방치하면 돈이 샌다.** 이 프로젝트는 **3번까지만 재시도**하도록 막아 뒀다
- **만들 때 드는 돈**과 **만든 프로그램이 쓰는 돈**은 별개다
- 공연장 인터넷이 불안정하면 못 쓴다 → 인터넷 없이도 되는 대비가 따로 필요하다

# M3 — 어떻게 만드나: 아이디어에서 실물까지 · 🟢 4h

💬 **한 줄로 말하면**
> 첫날 코드부터 짜지 않는다. **뭘 만들지 · 뭘 안 만들지 · 다 되면 어떻게 알지**를 먼저 글로 적는다.
> 그 다음 작게 쪼개서 하나씩 만든다.

🔑 **처음 나오는 말**: SPEC(계획 문서) · 비목표 · 인수 기준 · 테스트 · 회귀 테스트 · 커밋

---

## M3-1. 첫날 무엇을 했나

이 프로젝트의 **첫 기록에는 코드가 없다.** 계획 문서가 있다.

그리고 **첫 계획 문서의 제목이 "평가"였다.** 만들기가 아니라 **남이 만든 비슷한 프로그램을 써 보고 뭐가 부족한지 목록을 만드는 일**이 첫 작업이었다.

거기서 발견한 빈틈 — **그 제품은 영어만 됐다.** 그게 이 프로젝트가 존재할 이유가 됐다.

💡 **쉬운 말로**: 공연 준비할 때 **먼저 무대를 보러 가는 것**과 같다. 도면부터 그리지 않는다.

---

## M3-2. 계획서에 반드시 들어가는 3가지

| 항목 | 쉬운 말로 | 없으면 |
|---|---|---|
| **뭘 만드나** | 한 문장으로 | AI가 자꾸 딴 걸 만든다 |
| **뭘 안 만드나** | 일부러 뺄 것 *(=비목표)* | 매번 다시 싸운다 |
| **다 되면 어떻게 아나** | 완료 판정 기준 *(=인수 기준)* | "됐다"를 아무도 판정 못 한다 |

이 프로젝트가 실제로 적은 **"안 할 것" 3가지**:

1. **공연 중에는 AI가 스스로 실행하지 않는다** — 제안만 하고, **버튼은 사람이 누른다**
2. **예쁜지 아닌지는 사람이 정한다** — AI는 초안까지
3. **하드웨어 없이 실제 조명은 못 켠다** — 컴퓨터 안에서 연습까지만

---

## M3-3. 위험을 먼저 적는다

| 위험 | 어떻게 대비했나 |
|---|---|
| 콘솔 프로그램이 업데이트되면 명령어가 바뀔 수 있다 | 버전을 고정하고, 버전별 규칙집을 따로 둔다 |
| 공연장 인터넷이 불안정하다 | 미리 만들어 둔 걸 캐시, 끊기면 실행만 되게 강등 |
| **잘못된 명령으로 쇼파일이 망가진다** | 위험한 작업 전 **자동 백업** + 사람 승인 |
| AI 요금이 폭주한다 | **재시도 3번까지** + 한 번에 쓸 양 제한 |

---

## M3-4. 만드는 순서

```
   ① 계획    뭘 / 안 할 것 / 완료 기준을 글로
        ↓
   ② 검사   ★ 만든 사람 말고 다른 쪽이 계획의 구멍을 찾는다
        ↓
   ③ 만들기  작게 쪼개서 하나씩. 단계마다 확인
        ↓
   ④ 실제 확인  진짜 콘솔에서 진짜로 되는지
        ↓
   ⑤ 정리    문서 갱신 + 배운 것 기록 → 다음 번 규칙이 된다
```

💡 **②가 왜 따로 있나 — 쉬운 말로**
> **내가 포커싱한 걸 내가 검수하면 못 본다.** 사람은 자기가 만든 것의 구멍을 못 본다.
> 그래서 이 프로젝트는 계획마다 **다른 쪽에 검사를 맡겼고, 실제로 여러 건이 뒤집혔다.**

💡 **④가 왜 따로 있나**
> 컴퓨터 점검표를 다 통과해도 **진짜 콘솔에서는 다르게 동작한다.** (M4에서 실제 사례를 본다)
> "됐다"의 최종 기준은 항상 **실제 콘솔**이었다.

계획 문서 46건은 **처음부터 계획된 게 아니다.** 앞의 것을 만들다가 다음 게 필요해졌다.

| 07-29~31 | 사전 점검 · 이펙트 |
| 08-01~04 | 장면 구성 · 외부 연결 |

**원칙: 항상 돌아가는 상태를 유지하면서 하나씩 더한다.** 전부 뜯어놓고 며칠 걸리게 하지 않는다.

## M3-6. 점검표(테스트)를 왜 만드나

💡 **쉬운 말로**
> **프리셋을 하나 고쳤는데, 그 프리셋을 쓰던 큐 40개가 멀쩡한지 어떻게 아나?**
> 하나씩 다 눌러보는 것 — 그게 **테스트**다. 컴퓨터가 대신 눌러줄 뿐이다.

이 프로젝트에는 자동 점검표가 **251개** 있다. 코드를 고칠 때마다 전부 자동으로 돌려서, **고친 데 말고 다른 데가 깨졌는지**를 즉시 잡는다. (이걸 **회귀 테스트**라 한다)

> ⚠️ **단, 점검표가 전부는 아니다.**
> 부품 점검 980여 개가 다 통과했는데, **완성된 프로그램을 실제로 켜니** 부품끼리 연결이 안 돼 있던 적이 있다.
> **부품 검사와 완성품 검사는 다른 일이다.**

# M4 — 조명 콘솔과 어떻게 연동하나 · 🟢🔵 6h

💬 **한 줄로 말하면**
> AI는 조명 콘솔을 **직접 못 만진다.** 그래서 중간에 **네 겹의 번역기**를 놓는다.
> 사람 말 → AI가 고른 도구 → 안전 검사 → 네트워크로 보낸 명령 → **콘솔 안에 심어 둔 작은 프로그램**.
> 이 네 겹이 어떻게 이어지는지가 이 모듈의 전부다.

🔑 **처음 나오는 말**: OSC · UDP · Lua · 도구(tool) · 통행권 · 퍼센트 인코딩 · 플러그인

> M4는 조명 용어와 컴퓨터 용어가 동시에 나온다. **[`glossary.md`](./glossary.md)를 옆에 두고 본다.**

---

## M4-0. 전체 그림 — 말 한마디가 조명이 되기까지

```
  ①  사람    "무빙 앞줄을 파랗게"
              │
              ▼
  ②  AI 모델  어떤 도구를 쓸지 고른다  →  run_commands(["Group 3", "Color 5"])
              │                            ※ AI는 도구만 부를 수 있다. 아무 명령이나 못 쏜다
              ▼
  ③  안전 게이트  문법 검사 → 위험도 분류 → (위험하면) 사람 승인 → 백업 → 통행권 발급
              │                            ※ 통행권 없으면 한 글자도 못 나간다
              ▼
  ④  OSC 전송   네트워크로 명령 한 줄을 콘솔에 던진다   /copilot/cmd
              │
              ▼
  ⑤  콘솔 안의 Lua 응답기   명령을 실행하고, 결과를 JSON으로 되돌려 준다
              │                                        /copilot/feedback · /copilot/state
              ▼
  ⑥  다시 ③②로   결과를 확인하고, 필요하면 AI가 다음 수를 둔다
```

💡 **쉬운 말로**
> 외국인 손님(AI)이 주방(콘솔)에 주문하는 상황이다.
> 손님은 주방 말을 모르고, 주방에 직접 들어갈 수도 없다.
> 그래서 **메뉴판**(도구)에서 고르게 하고, **점원**(안전 게이트)이 확인하고, **전표**(OSC)로 전달하고, **주방 안의 사람**(Lua 응답기)이 실제로 만든다.

---

## M4-1. 왜 직접 연결이 안 되나

AI 모델은 글을 만드는 프로그램이다. **네트워크도 못 쓰고, 콘솔도 모른다.**

| 못 하는 것 | 그래서 필요한 것 |
|---|---|
| 콘솔이 어떤 명령어를 쓰는지 정확히 모른다 | **도구 목록**으로 고를 수 있는 것만 준다 (M4-2) |
| 위험한 명령을 만들어낼 수 있다 | **안전 게이트**가 막는다 (M4-3) |
| 네트워크로 뭘 보낼 수 없다 | **OSC 브리지**가 대신 보낸다 (M4-4) |
| 콘솔 안을 들여다볼 수 없다 | **콘솔 안의 Lua 응답기**가 읽어서 알려준다 (M4-5) |

> **이 네 개가 이 프로젝트의 전부다.** 나머지는 이 위에 쌓은 것이다.

---

## M4-2. 계층 1 — AI에게는 "메뉴판"만 준다

AI에게 "아무 명령이나 만들어 봐"라고 하지 않는다. **미리 정한 도구 20개** 중에서만 고르게 한다.

### 도구 20개의 구조

```
   바닥에 깔린 원시 도구 3개  ← 이것만이 실제로 콘솔을 건드린다
   ┌──────────────────────────────────────────────┐
   │ run_commands    명령을 실행한다               │
   │ query_state     콘솔 상태를 읽는다            │
   │ deploy_plugin   콘솔에 작은 프로그램을 심는다 │
   └──────────────────────────────────────────────┘
                        ▲
   그 위에 쌓은 전문 도구 16개
   ┌──────────────────────────────────────────────┐
   │ get_rig_context     지금 리그가 어떤지 요약   │
   │ find_looks · instantiate_look    룩 찾기·만들기│
   │ find_fx   · instantiate_fx       이펙트       │
   │ find_scene · compile_scene       장면         │
   │ prepare_busking · prepare_songcue 즉석·곡 큐  │
   │ precheck_patch · preshow_check   사전 점검    │
   │ build_patch_sheet · build_cue_sheet ·         │
   │ build_preset_list · build_handover_pack  서류 │
   │ plan_executor_layout             실행기 배치  │
   └──────────────────────────────────────────────┘
```

💡 **쉬운 말로 — 왜 이렇게 나누나**
> **원시 도구 3개는 "칼·불·도마"**다. 뭐든 할 수 있지만 위험하다.
> **전문 도구 16개는 "레시피"**다. 자주 하는 일을 미리 안전하게 묶어 둔 것이다.
>
> AI가 "룩을 만들어 줘"를 처리할 때, 명령어를 처음부터 지어내는 것보다
> **이미 검증된 레시피(`instantiate_look`)를 부르는 게 훨씬 안전하다.**

> 🔵 **심화** — 전문 도구도 결국 내부에서 `run_commands`를 부른다. 다만 **어떤 명령을 만들지가 사람이 검증해 둔 코드**라서, AI의 상상력이 끼어들 자리가 없다.

---

## M4-3. 계층 2 — 안전 게이트: "통행권" 모델

명령이 콘솔로 나가려면 **반드시 게이트를 통과해야 한다.** 이 프로젝트에서 가장 공들인 부분이다.

### 게이트가 하는 일 (순서 고정)

```
   ① 상태 점검      콘솔이 살아 있나
        ↓
   ② 문법 검증      이 명령이 문법에 맞나
        ↓
   ③ 위험도 분류    아래 5가지로 판정
        ↓            · 금지 목록에 걸리나 (삭제 계열 등)
        ↓            · 대상이 지정 안 된 명령인가 ("전부"에 걸리는 것)
        ↓            · 참조를 펼쳐 봐야 아는 것인가 (매크로 안에 뭐가 있나)
        ↓            · 플러그인 플래그가 붙어 있나
        ↓            · 이전에 결과를 확인 못 한 이력이 있나
        ↓
   ④ 공연 중 잠금 확인   지금 쇼가 돌고 있나
        ↓
   ⑤ 사람 승인      ★ 위험한 것만. 기본값은 "전부 거부"
        ↓
   ⑥ 잠금 재확인    승인받는 사이에 공연이 시작됐을 수도 있다
        ↓
   ⑦ 백업          위험한 작업 전에 저장
        ↓
   ⑧ 통행권 발급   ← 여기까지 와야 나갈 수 있다
```

### ★ 통행권이 왜 중요한가

게이트는 **"통행권(clearance)"을 발급**하고, 실제로 콘솔에 보내는 부분은 **통행권 하나당 딱 한 번만** 보낸다. 통행권이 없으면 **아무것도 안 나간다.**

💡 **쉬운 말로**
> 공연장 백스테이지 출입증과 같다.
> 출입구를 아무리 잘 알아도, **패스가 없으면 못 들어간다.**
> 그리고 패스는 **1회용**이다 — 한 번 쓰면 소모된다.
>
> 이렇게 만들면 **누가 실수로 전송 통로를 직접 붙잡아도 우회가 불가능하다.**
> 코드 어딘가에서 몰래 명령을 보내는 일이 원천적으로 안 된다.

**모든 전송은 1:1로 기록된다** — 나간 명령 하나에 감사 기록 하나.

### 안전의 방향은 한쪽으로만 기울어 있다

> **애매하면 막는다(HOLD).** 승인 기본값은 **전부 거부**다.
> "확실히 안전할 때만 통과"이지, "확실히 위험할 때만 차단"이 아니다.

이 차이가 결정적이다. 판단이 안 서는 명령은 **그냥 안 나간다.**

## M4-4. 계층 3 — OSC: 콘솔에 말 거는 방법

### OSC가 뭔가

💡 **쉬운 말로**
> **네트워크로 짧은 메시지를 주고받는 약속**이다. 원래 음악·조명 장비끼리 쓰라고 만든 규격이다.
> 편지로 치면 **봉투 규격**과 같다 — 주소를 어디 적고, 내용을 어떻게 담을지 정해 둔 것.

이 프로젝트는 **주소 세 개**만 쓴다.

| 주소 | 방향 | 담는 것 |
|---|---|---|
| `/copilot/cmd` | 컴퓨터 **→** 콘솔 | 실행할 명령 한 줄 |
| `/copilot/feedback` | 콘솔 **→** 컴퓨터 | 실행 결과 · 살아있음 응답 · 오류 |
| `/copilot/state` | 콘솔 **→** 컴퓨터 | 콘솔 내부 상태 스냅숏 |

### ★ 이 설계의 핵심 제약 — 입구가 하나뿐이다

여기가 M4에서 **가장 중요한 지점**이다.

> **콘솔은 `/cmd` 주소로 들어온 "명령 한 줄"만 실행한다.**
> 다른 주소를 만들어서 "이건 조회 요청이야"라고 알려줄 방법이 **없다.**
> 콘솔 쪽에 마음대로 주소를 추가하는 기능 자체가 없기 때문이다.

그래서 이렇게 우회한다:

```
   원하는 것:  "시퀀스 목록 좀 보여줘"  (조회)

   그런데 조회 전용 입구가 없다.
              ↓
   그래서:    조회 요청을 "명령"으로 위장해서 /cmd 로 보낸다

              Plugin "CopilotResponder" "state 42 DataPool/Sequences"
              └─────────────────────────────────────────────────┘
                이건 콘솔 입장에선 그냥 "플러그인 실행" 명령이다

              ↓ 콘솔이 그 플러그인을 실행한다
              ↓ 플러그인이 시퀀스 목록을 읽는다
              ↓ 플러그인이 /copilot/state 로 답장을 보낸다
```

💡 **쉬운 말로**
> 우체통이 **하나**뿐인 건물이다. "택배는 여기, 편지는 저기"가 없다.
> 그래서 **모든 걸 편지 봉투에 넣어** 그 하나뿐인 우체통에 넣는다.
> 안에 있는 사람이 열어보고 알아서 처리한다.
>
> **조회조차 "명령"의 모양을 하고 들어가는 것** — 이게 이 시스템 구조의 이유다.

### UDP라서 생기는 문제와 해결

OSC는 **UDP**라는 방식으로 오간다. UDP는 빠르지만 **불친절하다**:

- 보낸 게 **도착 안 할 수 있다** (사라져도 알려주지 않는다)
- 순서가 **뒤바뀔 수 있다**

그래서 두 가지 장치를 뒀다.

**① 요청 번호(request-id)를 붙여서 짝을 맞춘다**

```
   보낼 때:  state 42 DataPool/Sequences
                   ↑ 요청 번호

   답장:     { "v":1, "id":"42", "kind":"state", ... }
                              ↑ 그대로 되돌아온다
```
→ 답장 3개가 뒤섞여 와도 **어느 게 어느 요청의 답인지** 알 수 있다.

**② 도착한 것만 인정한다 — 정직 계약**

브리지는 **실제로 도착한 답장만 전달한다.** "안 왔으니 실패겠지" 같은 추측을 하지 않는다.
콘솔 쪽 응답기도 마찬가지다 — **타이머 없음 · 재시도 없음 · 상주 루프 없음.** 온 요청에만 답한다.

> 💡 이건 M4-8의 **"ok는 증거가 아니다"**와 같은 원칙이다.
> **모르는 건 모른다고 둔다.** 안다고 꾸미지 않는다.

## M4-5. 계층 4 — 콘솔 안의 Lua 응답기

### Lua가 왜 필요한가

콘솔은 **명령을 실행**해 준다. 그런데 **"안에 뭐가 들었는지 알려줘"**는 명령어로 안 된다.
그래서 **콘솔 안에서 도는 작은 프로그램**을 하나 심어 둔다. 그게 **Lua 응답기**다.

> **Lua**는 간단한 프로그래밍 언어다. grandMA3가 플러그인 언어로 채택하고 있어서, 콘솔 **안쪽**은 Lua로 쓴다.
> (컴퓨터 **바깥쪽**은 파이썬이다. 두 언어가 OSC로 만난다.)

이 프로젝트의 응답기는 **약 990줄짜리 Lua 파일** 하나다. 이름은 `CopilotResponder`.

### 응답기가 알아듣는 말 — 동사 5개

응답기에게 보내는 요청은 전부 이 모양이다:

```
   Plugin "CopilotResponder" "<동사> <요청번호> [나머지]"
```

| 동사 | 무엇을 하나 | 어디로 답하나 |
|---|---|---|
| `ping` | 살아 있니? | `/copilot/feedback` |
| `state` | 이 경로 안에 뭐가 있는지 보여줘 | `/copilot/state` |
| `prop` | 이 물건의 이 속성값 알려줘 | `/copilot/state` |
| `exec` | 이 명령 실행하고 결과 알려줘 | `/copilot/feedback` |
| `deploy` | 이 Lua 코드를 플러그인으로 심어 | `/copilot/feedback` |

**이 5개가 전부다.** 콘솔에 할 수 있는 모든 일이 이 다섯 동사 위에 올라간다.

### 답장은 어떻게 오나

응답기는 결과를 **JSON**(정해진 형식의 글)으로 만들어 되돌린다. 그런데 그냥 보내면 깨진다 —
따옴표·쉼표·공백이 명령줄 문법과 충돌하기 때문이다.

그래서 **퍼센트 인코딩**을 쓴다.

💡 **쉬운 말로 — 퍼센트 인코딩**
> 위험한 글자를 **안전한 글자로 바꿔 적는 것**이다.
> 공백을 `%20`처럼 바꾸면, 중간에 끊길 일이 없다. 받는 쪽에서 되돌린다.
> 인터넷 주소창에서 한글이 이상한 글자로 보이는 것과 같은 원리다.

답장에는 항상 **`"v": 1`**(규격 버전)이 붙는다. 규격이 바뀌면 이 숫자를 올리고 **양쪽을 동시에** 고친다.

### 현장에서 진짜 문제가 됐던 것들

> 🔵 **심화** — 이 세 가지는 실제로 며칠을 잡아먹었다. 학생 트랙은 "이런 게 걸린다" 정도만.

**① 답장을 어느 줄로 보내야 하는지** — 콘솔의 OSC 설정에는 여러 줄이 있고, **줄마다 역할이 다르다.**
이 현장에서는 **1번 줄이 수신 전용, 2번 줄이 송신 가능**이었다. 그래서 응답기 설정이 `osc_slot = 2`다.
→ 1번을 가리키면 답장이 **조용히 사라진다.**

**② 콘솔마다 답장 보내는 함수 모양이 다르다** — 그래서 응답기는 **네 가지 방식을 차례로 시도**한다.
그중 명령어로 보내는 방식은 **맨 마지막**에 둔다. 이유가 중요하다:

> 그 방식은 **실패해도 실패했다고 안 알려준다.** 콘솔이 거절해도 조용히 성공처럼 보인다.
> **실패를 알 수 있는 방법부터 먼저 시도**하고, 알 수 없는 방법은 최후에 쓴다.

**③ 따옴표를 못 쓴다** — 요청이 `"..."` 안에 담겨 들어가므로, 내용에 큰따옴표가 있으면 **거기서 잘린다.**
→ 이름을 붙일 땐 작은따옴표를 쓴다: `Store Cue 5 'name'`

## M4-6. 플러그인을 콘솔에 심는 두 가지 길

AI가 Lua 코드를 짜서 콘솔에 심으려면 **파일을 콘솔 안으로 넣어야** 한다. 길이 두 개 있었고, **하나가 이겼다.**

| | **길 A — OSC로 보내기** | **길 B — 파일 만들고 Import** ✅ |
|---|---|---|
| 방법 | 소스 코드를 명령 한 줄에 담아 전송 | 콘솔이 읽는 형식의 파일을 만들고 불러오기 |
| 문제 | **약 2KB에서 잘린다.** 그리고 이 방식으로 심은 건 콘솔에 **저장이 안 됐다** | 크기 제한 없음 |
| 한계 | — | 서버와 콘솔이 **같은 컴퓨터**에 있어야 한다 |
| 결과 | 실사용 포기 | **실제로 심은 플러그인은 전부 이 길로 나갔다** |

### 파일 형식에서 한 번 더 막혔다

같은 "파일 만들기"인데도 **두 가지 형태**가 있었다.

```
   ❌ 파일 이름만 적어 두는 형태
      <ComponentLua FileName="내코드.lua">
      → 불러오면 껍데기만 들어오고 내용이 없다. 실행해도 아무 일 없음

   ✅ 코드를 파일 안에 통째로 넣는 형태
      <UserPlugin><ComponentLua><FileContent>
          <Block Base64="……"/>   ← 코드를 조각내서 담는다
      → 이 형태만 실제로 동작했다
```

💡 **쉬운 말로**
> ❌는 **"내 코드는 저기 있어요"라고 쪽지만 넣은 것**이다. 콘솔이 그 쪽지를 안 따라간다.
> ✅는 **코드를 통째로 봉투에 넣은 것**이다.

### 심기 전에 세 관문을 통과한다

AI가 짠 코드라고 그냥 넣지 않는다.

```
   ① 컴파일 검사   문법이 맞나 (콘솔에 넣기 전에 미리 확인)
        ↓
   ② 스캔         위험한 코드가 들었나
        ↓
   ③ 사람 검토    ★ 사람이 읽고 승인해야 통과
        ↓
   ④ 콘솔에 심기
```

> **①과 ③이 둘 다 통과해야만** 심는다. 기본값은 **거부**다.

## M4-7. 실제 왕복 한 번 따라가기

"무빙 앞줄을 파랗게" 한마디가 실제로 어떻게 도는지, 처음부터 끝까지.

```
 1  사람        "무빙 앞줄을 파랗게 해줘"
 2  AI 모델     리그 정보를 먼저 확인해야겠다 → get_rig_context 호출
 3  서버        query_state 로 그룹 목록 조회 준비
 4  게이트      읽기 전용이라 안전 → 통행권 발급
 5  OSC 전송    /copilot/cmd  ←  Plugin "CopilotResponder" "state 17 DataPool/Groups"
 6  콘솔        플러그인 실행 → 그룹 목록을 읽음
 7  응답기      JSON으로 포장 → 퍼센트 인코딩 → /copilot/state 로 발송
 8  서버        요청번호 17로 짝 맞춤 → AI에게 전달
 9  AI 모델     "앞줄 무빙은 Group 3이구나" → run_commands(["Group 3", "Color 5"])
10  게이트      문법 OK · 위험 아님 · 공연 중 아님 → 통행권 발급
11  OSC 전송    /copilot/cmd  ←  Plugin "CopilotResponder" "exec 18 Group 3"
12  응답기      명령 실행 → 결과를 /copilot/feedback 으로
13  서버        결과 확인
14  ★ 재조회    query_state 로 진짜 바뀌었는지 다시 확인   ← 이게 증거다
15  사람        화면에서 파래진 걸 본다
```

> **14번이 없으면 12번의 "성공"은 주장일 뿐이다.** 왜 그런지는 바로 다음 절에서 본다.

## M4-8. 여기서 실제로 틀렸던 것들

원리를 알았으니, 이제 **그 원리가 어디서 배신했는지**를 본다. 전부 이 프로젝트에서 실제로 겪은 일이다.

**Case A — 화면 번호 ≠ 진짜 번호**
목록에서 읽은 번호로 명령을 보내니 대부분 거절당했다. 진짜 주소는 **읽은 번호 + 100**.
→ 무서운 건 **두 번호 다 오류가 안 난다**는 것. 하나는 경고 없이 **엉뚱한 조명을 켠다.**
→ **7번 거절당하는 것보다 1번 조용히 잘못 실행되는 게 나쁘다.**

**Case B — 같은 규칙이 상황 따라 정반대**
장비 등록 작업에서는 "작업 위치를 직접 지정하면" 실패한다. 조명 만드는 작업에서는 **반드시 필요**하다.
→ **"한 번 됐으니 저기서도 되겠지"가 조용히 틀린다.**

**Case C — "0개"가 "비었다"가 아니었다**
쓰고 있는 그룹을 `state`로 조회했더니 **0개**로 나왔다. 그룹은 멀쩡히 쓰이고 있었다 — **그 조회 경로가 그 정보를 안 담고 있었을 뿐**이다.
→ 못 읽으면 → 확인 못 하고 → 백업 못 하고 → **되돌릴 수 없다.** 그래서 그 자리 자동 생성은 **금지**로 못 박았다.

**Case D — 없는 명령이 "성공"이라고 답했다**
일부러 오타 낸 가짜 명령을 먼저 쏴 봤더니 **`ok`가 오고 큐까지 만들어졌다.** 콘솔은 모르는 옵션을 **조용히 무시**한다.
→ 가짜를 안 쏴봤으면 **아무 일도 안 하는 기능 위에 전부를 세웠을 것이다.**

### 그래서 확인 절차는 이렇게 된다

```
   ① 반드시 실패해야 하는 가짜 명령을 먼저 쏜다
        ├─ 실패한다 → 이 길은 믿을 수 있다 → ②로
        └─ 성공한다 → 이 길은 아무것도 구별 못 한다 → 다른 길을 찾는다
   ② 진짜 명령을 쏜다
   ③ 다시 조회해서 확인한다        ← M4-7의 14번
```

### 외울 문장 3개

| | 쉬운 말로 |
|---|---|
| **`ok`는 증거가 아니다** | 말은 말일 뿐. **다시 확인한 결과**가 증거다 |
| **읽을 수 있다 ≠ 시킬 수 있다** | 조회되는 번호로 조작이 된다는 보장은 없다 |
| **도구를 먼저 의심하라** | 실패해야 할 걸 먼저 시켜본다. 그게 실패해야 성공이 의미가 있다 |

💡 **조명으로 하면**
> 페이더를 올렸는데 안 밝다. 램프부터 보지 않는다 — **채널 → 밝기 → 패치** 순서로 본다.
> **당신은 이미 이 습관이 있다. AI에게도 쓰면 된다.**

## M4-9. 규칙집 — 검증된 명령만 쓰게 한다

AI는 콘솔 명령어를 **그럴듯하게 지어낼 수 있다.** 그래서 **실제로 콘솔에서 확인된 명령만** 모은 규칙집을 AI에게 항상 읽힌다.

들어가는 것: 확인된 명령 형식 · 상황별 예외(Case B) · 쓰면 안 되는 것 · **실패했던 방법과 그 이유**.

> **규칙집은 자란다.** 새 함정을 적어두면 그때부터 AI는 같은 실수를 안 한다.
> 이게 M5에서 배울 **하네스**의 조명 버전이다.

---

## M4-10. 실습 — 왕복 한 번 직접 해보기

1. 실습용 쇼파일 만들고 **백업**
2. 콘솔 OSC 설정에서 **송신 가능한 줄이 몇 번인지** 확인 (M4-5 ①)
3. `ping` 보내서 **살아있는지** 확인 — 여기서 막히면 통신 설정 문제
4. `state`로 그룹 목록 **조회**
5. **가짜 명령 먼저 쏴 보기** → 실패하는지 확인
6. `exec`로 진짜 명령 1건
7. **다시 `state`로 조회해서 확인** ← 이게 증거

> **5번을 건너뛰는 조가 반드시 나온다.** 그 조에게 Case D를 다시 읽힌다.

🎓 **학생 트랙 대안**: 강사 콘솔 하나로 조별 순서 진행. 단, **3번(ping)과 5번(가짜 명령)은 전원이 직접** 본다.

## M5-0. 왜 AI 한 대로는 안 되나

>

## M5-1. 오케스트레이션 — 일 나눠 시키기 · 1.5h

💬 **한 줄로 말하면**: **혼자 다 하지 않고, 나눠 주고, 모은다.**

### 조명으로 하면

| 조명 현장 | 여기서는 |
|---|---|
| 조명감독 | **지휘 담당 AI** — 방향 정하고, 일 나누고, 최종 판단 |
| 오퍼레이터 | 실제로 만드는 AI |
| 포커스 크루 | 특정 작업만 하는 AI |
| 외부 검수 | **검사만 하는 AI** |

**감독은 직접 다 하지 않는다.** 누구에게 뭘 시킬지 정하고, 올라온 결과를 판단한다.

### 나누는 방법 3가지

| 방법 | 언제 쓰나 | 예 |
|---|---|---|
| **차례로 넘기기** | 앞의 결과가 뒤의 재료일 때 | 계획 → 만들기 → 문서 |
| **동시에 시키기** | 서로 상관없을 때 | 안전·속도·읽기 쉬움을 **동시에** 검토 |
| **대량으로 돌리기** | 같은 작업이 수십~수백 개일 때 | 파일 200개 한꺼번에 점검 |

**실물**: 이 저장소는 지휘 담당이 **10종의 일꾼**에게 일을 나눈다. 그리고 **지휘 담당은 직접 만들지 않는다** — 규칙으로 못 박혀 있다.

## M5-2. 에이전트 — 역할 나누기 · 1.5h

💬 **한 줄로 말하면**: **역할과 할 수 있는 일이 정해진 AI 한 명.** 각자 자기 기억만 갖고, 끝나면 결과만 보고한다.

### 왜 나누나 — 세 가지

| 이유 | 쉬운 말로 |
|---|---|
| **기억이 안 섞인다** | 만드는 담당이 문서 담당 대화까지 기억할 필요가 없다. 섞이면 헷갈린다 |
| **권한을 줄이면 안전하다** | **조사만 하는 AI에게는 고칠 권한을 안 준다.** 실수해도 아무것도 안 망가진다 |
| **딴 사람이 검사한다** | 만든 쪽이 아닌 다른 쪽이 검사한다 |

### 실물 — 이 저장소의 11개 역할

계획 담당 · 만들기 담당 · 문서 담당 · 저장 담당 · **계획 검사** · **결과 검사** · 어려운 문제 자문 · 규칙 만들기 담당 · 완성품 검사 · 화면 설계 담당 · **여러 갈래 지휘 담당**.

### ★ 가장 중요한 규칙 — 검사는 만든 사람이 하지 않는다

두 개의 **검사 담당**은 통과시키는 게 일이 아니라 **결함을 찾는 게 일**이다.

💡 **조명으로 하면**: **내가 포커싱한 걸 내가 검수하면 못 본다.** 이미 아는 이야기다.

### 일꾼은 사용자에게 직접 못 묻는다

이 저장소의 규칙: **일꾼 AI는 사용자에게 직접 질문하지 못한다.** 정보가 없으면 **"이게 없어서 못 하겠다"**고 지휘 담당에게 보고하고, **지휘 담당이 사용자에게 묻는다.**

💡 **왜?** 사용자는 **한 명하고만 대화한다.** 11명이 각자 말 걸면 현장이 마비된다.

## M5-3. 하네스 — 규칙과 안전장치 · 2h

💬 **한 줄로 말하면**
> AI에게 **"우리 현장에선 이렇게 한다"를 가르쳐 두고**, AI가 깜빡해도 **기계가 대신 잡아주게** 하는 것.

💡 **이름의 뜻**
> **하네스(harness)**는 원래 **말에 씌우는 마구(고삐)**를 뜻한다.
> 말이 힘이 세다고 아무 데나 뛰게 두지 않는다. **원하는 방향으로 몰기 위해** 씌우는 장치다.
> AI도 똑같다.

### 조명으로 하면

| 조명 현장 | 여기서는 | 이 저장소 |
|---|---|---|
| 극장 하우스 룰 | **규칙 파일** — 반드시 지킬 것 | 71개 |
| 매뉴얼 선반 | **스킬** — 필요할 때 꺼내 읽는 자료 | 34개 |
| **리밋 스위치 · 인터록** | **훅** — 자동으로 켜지는 검사 | 43개 |
| 콘솔 설정 | 설정 파일 | — |

### 훅이 왜 결정적인가

💡 **쉬운 말로**
> **리밋 스위치**는 오퍼레이터가 깜빡해도 **무빙이 벽을 치지 않게** 한다.
> **훅**은 AI가 깜빡해도 **규칙을 어기지 못하게** 한다.
>
> 사람의 주의력에 안 맡기고 **기계에 맡기는 것**이다.

이 저장소에서 훅이 자동으로 켜지는 순간들:

```
   작업 시작할 때        →  프로젝트 상태 점검
   명령 실행하기 직전    →  위험한 명령인지 검사
   명령 실행한 직후      →  결과 기록
   일꾼이 시작·끝날 때   →  진행 상황 기록
   한 턴 끝날 때         →  점검표·문법 검사 통과했나
   한 턴 끝날 때         →  목표 달성했나 판정 (→ M5-4)
   기억이 꽉 찰 때       →  정리
```

### 하네스는 자란다

```
   실패한다 → 왜 실패했는지 적는다 → 규칙 파일에 추가한다
        ↑                                    │
        └────── 같은 실패가 다시 안 난다 ◀───┘
```

M4의 Case B(상황마다 규칙이 뒤집힘)를 겪은 뒤 그 내용이 규칙집에 들어갔고, **그 뒤로 같은 실수가 없다.**

> 💡 **핵심**: **규칙을 잘 깔면 같은 AI라도 결과가 좋아진다.**
> **도구를 바꾸기 전에 규칙을 먼저 고쳐라.**

## M5-4. 루프 — 될 때까지 반복시키기 · 1.5h

💬 **한 줄로 말하면**: **"이게 될 때까지 계속해"**라고 시켜두는 것. 단, **언제 그만둘지도 반드시 같이 정한다.**

### 세 종류

| 종류 | 언제 멈추나 | 예 |
|---|---|---|
| **조건 루프** | 정해둔 조건이 참이 되면 | "점검표 전부 통과할 때까지" |
| **목록 루프** | 문제 목록이 빌 때까지 | "잡힌 오류 다 없앨 때까지" |
| **시간 루프** | 사람이 끌 때까지 | "5분마다 상태 확인" |

**실물**: 이 저장소에는 **한 턴이 끝날 때마다 목표 달성 여부를 판정하는 훅**이 있다. 아직이면 AI는 멈추지 않고 다음 턴을 시작한다.

### ★ 반드시 그만둘 조건을 건다

```
   나쁜 조건 :  "완벽해질 때까지"        ← 판정 불가. 영원히 돈다

   좋은 조건 :  "점검표 통과 && 문법 검사 통과,
                 안 되면 20번 하고 중단"  ← 기계가 판정 가능 + 탈출구
```

**세 가지 한도를 반드시 건다**: 몇 번까지 반복할지 · 돈을 얼마까지 쓸지 · 같은 실패를 몇 번까지 (이 프로젝트는 **3번**).

💡 **조명으로 하면**
> **"될 때까지 반복"은 러닝 큐가 아니다.** 반드시 **빠져나갈 조건이 있는** 것이어야 한다.
> 탈출 조건 없는 루프는 **무대에 무한 체이스를 걸어두고 퇴근하는 것**과 같다.

### 조건은 기계가 판정할 수 있어야 한다

루프가 도는 동안 **사람은 안 보고 있다.** 그래서 조건은 **컴퓨터가 스스로 참/거짓을 낼 수 있어야** 한다.

| 좋은 조건 | 나쁜 조건 |
|---|---|
| 점검 명령이 **0을 반환하면** | "잘 작동하면" |
| 오류 개수가 **0이면** | "문제 없으면" |
| 파일이 **있으면** | "완성되면" |

> ⚠️ **틀린 판정 기준 위에서 도는 루프가 가장 비싸다.**
> 그래서 **M4의 검증 규율이 루프보다 먼저** 와야 한다.

## M5-5. 그래프 엔지니어링 — 순서와 기억 짜기 · 1.5h

💬 **한 줄로 말하면**: **뭘 동시에 하고 뭘 차례로 할지** 정하는 것 + **AI에게 뭘 언제 읽힐지** 정하는 것.

💡 **이름의 뜻**: **그래프**는 점과 선으로 그린 **관계도**를 말한다. 지하철 노선도를 생각하면 된다.

### (a) 순서 짜기

```
        ┌── 안전 검토 ──┐
   계획 ─┼── 속도 검토 ──┼─→ 종합 → 만들기 → 문서
        └── 읽기쉬움 검토 ┘
        (동시에 가능)      (차례로)
```

**판단 기준은 하나**: **앞의 결과가 뒤에 필요한가?**
- 필요하다 → 차례로
- 상관없다 → 동시에

💡 **쉬운 말로**
> **밥 짓기 → 상 차리기**는 차례로 해야 한다. 밥이 있어야 차린다.
> **세 사람이 각각 다른 방 청소**는 동시에 해도 된다. 서로 상관없으니까.

**이 저장소의 실제 규칙 2가지**
1. 서로 상관없는 일은 **한 번에 같이 보낸다**
2. **고칠 권한이 있는 AI 둘을 동시에 돌리지 않는다** — 같은 파일을 동시에 고치면 충돌한다

💡 **조명으로 하면**: **같은 실행기를 두 큐가 동시에 물면 안 되는 것**과 같은 제약이다.

### (b) 기억 관리

**AI가 기억할 수 있는 양은 정해져 있다.** 규칙 71개를 **전부 항상 읽히면 정작 일할 자리가 없다.**

💡 **쉬운 말로 — 시험 볼 때 책상**
> 시험 볼 때 책상에 **모든 교과서를 다 펴놓지 않는다.**
> 지금 푸는 과목만 놓고, 나머지는 가방에 둔다. 필요하면 꺼낸다.

```
   항상 읽힘     꼭 필요한 규칙 몇 개 (안전 · 말투 · 대화 방식)
       ↓
   때에 따라     그 작업일 때만 (콘솔 작업이면 콘솔 규칙집)
       ↓
   부를 때만     자료 34개 — 제목만 보이고 내용은 부를 때 가져온다
```

💡 **조명으로 하면**: **콘솔 화면에 모든 풀을 다 띄우지 않는다. 지금 쓸 것만 띄운다.**

### 기억이 꽉 차면 — 인수인계

긴 작업은 AI의 기억 한계를 넘는다. 그러면:

```
   기억이 거의 찼다 → 지금까지 한 걸 요약해서 파일로 저장
                          ↓
                   기억을 비우고 새로 시작
                          ↓
                   요약을 읽고 이어서 작업
```

💡 **조명으로 하면**: **교대할 때 넘기는 공연 노트.** 뭐가 끝났고, 뭐가 남았고, 뭘 조심해야 하는지.

## M5-6. 다섯 개가 어떻게 맞물리나 · 30분

```
   하네스(규칙 + 자동 검사) ─── 모든 것의 바닥 ────────────┐
                                                            │
   지휘 담당 ── 순서(그래프)대로 일을 나눠 준다 ──┐         │
        │                                          │         │
        │                            ┌─────────────┴───┐     │
        │                            │  일꾼 AI들       │     │
        │                            │  (역할 · 권한)   │     │
        │                            └─────────────┬───┘     │
        │                                          │         │
```

## M6-1. 실제 콘솔에서 되는 것

|---|---|
| 한국어 → 콘솔 명령 | 말로 시키면 콘솔이 움직인다 |
| 장비 등록 자동화 | 조명 기구를 한꺼번에 등록 (**실제 9대 성공**) |
| 콘솔용 프로그램 만들기 | AI가 코드를 짜서 콘솔에 심는다 |
| 룩 만들기 | "따뜻한 저녁 느낌" → 실제 설정으로 |
| 이펙트 다루기 | 반복 움직임을 말로 만든다 |
| 장면 구성 | 큐와 장면을 짠다 |
| 배치 인식 | 어느 조명이 어디 있는지 읽고 그에 맞게 연출 |
| 콘솔 상태 보기 | 지금 뭐가 어떻게 돼 있는지 화면으로 |
| 사전 점검 | 공연 전 이상 없나 확인 |
| 서류 자동화 | 인수인계 문서 만들기 |
| 안전장치 | 위험한 명령 막기 |
| 설치 가능한 프로그램 | 더블클릭으로 실행되는 앱 |

## M6-2. 반만 되는 것

- **그룹 자동 만들기** — 빈 자리만. 이미 쓰는 자리는 되돌릴 수 없어서 막아뒀다 (M4-5 Case C).
  만든 뒤 **안에 뭐가 들었는지는 기계로 못 읽어** 눈으로 확인해야 한다
- **추상적인 지시** — **낱개로는 된다.** "웅장하게"는 색(룩 라이브러리)으로도 조준(무드 표)으로도
  풀리고, 곡 설계 엔진은 구간마다 밝기·색·위치를 정한다. 아직인 것은 **셋을 한 번에 묶는 것** —
  지금은 색·조준·타이밍을 따로 불러서 각각 승인해야 한다
- **이펙트가 잘 도는지 확인** — 기계로는 못 본다. **사람이 눈으로 봐야 한다**

## M6-3. 일부러 안 하는 것

| 안 하는 것 | 왜 |
|---|---|
| 공연 중 AI가 스스로 실행 | **기술 문제가 아니라 선택.** 위험해서 설계에서 뺐다 |
| 예쁜지 판단 | AI는 초안까지. 확정은 사람 |
| 하드웨어 없이 실제 조명 켜기 | 콘솔 회사 정책 |
| 읽을 수 없는 걸 자동화 | 백업도 복구도 안 되면 막는다 |

> **상용 제품은 만 명을 위해 만든다. 당신의 도구는 당신 한 사람을 위해 만들면 된다.**

# M7 — 앞으로의 과제 · 🟢 2h

💬 **한 줄로 말하면**: 아직 못 한 게 많다. **그게 여러분이 할 몫이다.**

## M7-1. 남은 단계

| 단계 | 목표 | 상태 |
|---|---|---|
| 확인 | 남의 제품 평가, 범위 정하기 | ✅ 끝 |
| 최소 동작 | 통신 · 대답 · 채팅 화면 · 안전장치 | ✅ 대부분 끝 |
| **장비 배치 이해** | 도면·장비 파일을 읽어서 **"코러스에서 금색으로 웅장하게"** 수준의 지시를 실행 | 🟡 대부분 됨 |
| **음악 → 큐 자동 생성** | 곡 구조를 넣으면 **구간별 큐 초안**을 짜서 콘솔에 올린다 | ✅ 됨 |
| **공연 중 보조** | 다음 큐 제안, 즉석 운용 추천, 이상 알림 | ⬜ 미착수 |

> ⚠️ **2026-09-01 정정** — 위의 두 줄은 오랫동안 **「미착수」로 잘못 적혀 있었다.** 그 오기 때문에
> 이미 있는 기능을 다시 만들 뻔한 일이 실제로 있었다. **다시 만들지 마라 — 이미 있다.**
>
> - **장비 배치 이해** — 배치 판독·배치 쓰기·도면 연동(Vectorworks·MVR)·무드 조준이 전부 산다.
>   이 줄의 예시인 **"금색으로 웅장하게"**는 실제로 룩 라이브러리의 worked example
>   (`'a grand golden chorus'`)이고, "웅장"은 조준 무드 표의 정식 키워드다.
>   남은 것은 **색·조준·타이밍 세 축을 한 번의 지시로 묶는 것**뿐이다.
> - **음악 → 큐 자동 생성** — 곡 설계 엔진 전체(에너지 예산 · 연출 인터뷰 · L1~L14 린트)가
>   구간별 큐를 짜서 **승인 게이트를 거쳐 콘솔에 올린다.** 다만 **오디오 자체는 분석하지 않는다** —
>   구간·시각·BPM은 사람이 넣는다. 「3분 곡 → 10분」 목표치는 **아직 안 재봤다.**
> - **공연 중 보조** — 여기 적힌 세 가지는 정말로 없다(미착수 맞음). 다만 **버스킹 팔레트 준비**와
>   **큐 진행 모니터(읽기 전용)**는 이미 있으니 그 둘은 새로 만들지 마라.

## M7-2. 외부와 잇기

지금 하는 작업은 이 프로그램을 **다른 AI 프로그램이 불러 쓸 수 있게** 만드는 것이다.

- **1단계 (진행 중)** — **읽기만.** 콘솔을 바꾸는 기능은 하나도 안 열어준다
- **2단계 (나중)** — 쓰기 기능 열기

💡 **왜 읽기부터?**
> **읽기는 되돌릴 게 없다. 쓰기는 되돌릴 게 있다.**
> 되돌릴 수 없는 걸 나중에 붙이는 것 — M3·M4에서 배운 순서 그대로다.

## M7-3. 아직 못 푼 기술 문제

| 문제 | 쉬운 말로 |
|---|---|
| 그룹 안에 뭐가 들었는지 못 읽는다 | **이름은 읽힌다. 안에 든 장비 목록이 안 읽힌다.** 18대가 든 그룹도 「0」이라고 답하므로, 여기서 나온 0을 「비었다」로 읽으면 안 된다 — 자동 생성이 이것 때문에 막혀 있다 |
| 쇼파일을 되돌리는 길이 없다 | 백업은 되는데 복구가 안 된다. 여러 기능이 이것 때문에 막혀 있다 |
| 이펙트가 잘 도는지 기계로 못 본다 | 지금은 사람이 눈으로 보는 게 유일 |
| 콘솔 업데이트 대응 | 버전별 규칙집과 재검사 필요. 지금 규칙집은 **한 버전(2.4.2)뿐**이고 콘솔 버전을 읽어 고르는 길이 없다 |
| 인터넷 없을 때 | **읽기까지는 된다** — 인터넷·계정 없이 도는 로컬 모델이 이미 붙어 있다. 다만 대화가 두세 번 넘어가면 도구 호출을 놓쳐서 **쓰기는 못 맡긴다**(2026-08-20 실측). 「어디까지」의 답은 **판독·진단까지**다 |

## M7-4. 넓혀 갈 곳

- **도면 프로그램과 연결** — **한쪽 방향은 이미 됐다.** 도면 파일(Vectorworks 내보내기 6종·MVR)을
  읽어 콘솔 패치와 대조하고, 차이를 승인 게이트를 거친 패치 계획으로 만든다(도구 3종 등재).
  남은 것은 **반대 방향** — 콘솔에서 도면으로 되돌려 보내는 길은 아직 없다
- **다른 콘솔** — 지금은 grandMA3만. 다른 건 통신부터 다시
- **여러 명이 함께** — 지금은 1인용
- **인수인계 자동화** — **「시작」보다 많이 와 있다.** 한 번의 호출로 패치 시트·큐 시트·프리셋 목록·
  매직 시트 **4종과 자체 감사 색인**(무엇을 못 읽었는지 스스로 밝히는 표지)이 나온다.
  남은 것은 **읽기 한계 너머** — 못 읽은 값은 못 읽었다고 적힌 채로 넘어간다
