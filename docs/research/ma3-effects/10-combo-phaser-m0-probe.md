# 10. 콤보(컬러+디머) 페이저 프리셋 — M0 라이브 프로브 결과

`docs/handoff/2026-08-16-session-handoff.md` §2 함정②("컬러+디머 혼합은 All 풀(21~25)만
수용")를 검증 대상으로, `08-color-phaser-m0-probe.md`·`09-dimmer-phaser-m0-probe.md`가
이미 확립한 스텝·Form·Phase 문법은 재검증하지 않고, **혼합 프로그래머의 저장 풀 수용
여부**만 겨눈 프로브다. `verification-claim-integrity` 원칙에 따라 **관측된 그대로**만
적고, 추정은 GAP으로 명시한다.

- 실기: onPC 2.4.2, `console_probe.py` 직결(응답기 버전 별도 미확인 — GAP, ping 응답
  자체는 정상)
- 선택: `Group 11`
- 임시 슬롯: `21.50`·`21.51`·`21.52`(All 1 풀), `4.50`(Color 풀), `1.50`(Dimmer 풀)
  — **프로브 종료 후 5개 전부 삭제 완료, 3개 풀 childCount 전부 정확히 원복 확인**

## 0. 포트 전쟁 (기록)

`09-...`와 동일하게 `~/Documents/...` 데몬이 9005를 점유 중이었다. 이번엔 우리 앱
(pid 39804, cwd 확인상 orca 워크트리 — 다른 체크아웃 데몬이 아니라 우리 자신의 앱이었다)이
`SIGTERM`에 무반응이라 `kill -9`가 필요했다. Bash 권한이 거부되어 코디네이터에게
`ask`로 승인을 요청했고, 코디네이터가 `kill -9 39804` 실행 + 30분 베이비시터 루프(Documents
데몬 자동 사살)를 가동한 뒤 프로브를 진행했다. 종료 후 `/tmp/port_war.sh`로 재선점
성공(`WON pid=77634 attempt=1`, cwd 확인 완료).

## 1. All 풀 번호 실측

```
state DataPool/PresetPools →
  children 中 {"i": 21, "name": "All 1"}, {"i": 22, "name": "All 2"}, ...
             {"i": 25, "name": "All 5"}
```

**`All 1` = 풀 번호 `21`.** 핸드오프 문서의 "All 풀(21~25)" 표기가 실기로 확인됐다 —
추정이 아니라 `state:DataPool/PresetPools` 1회 쿼리로 5개 All 풀(21~25) 전부의 존재와
번호를 직접 읽었다. 하드코딩 시 이 번호를 근거로 삼을 것.

베이스라인 `childCount`: All 1(21)=16, Color(4)=37, Dimmer(1)=27 — 전부 프로브 종료 후
동일 값으로 원복 확인(§5).

## 2. 수용/거부 실측표

| # | 시도 | 대상 풀 | 명령 개수 | 결과 | 되읽기 `node.name` |
|---|------|---------|-----------|------|---------------------|
| 1 | 2스텝 혼합(Red+Dimmer100 → Red+Dimmer0) | All 1 (21.50) | 13 | **전부 `ok:true`** | `Preset 50` |
| 2 | 같은 종류의 혼합(Red+Dim100 → Blue+Dim0) | **Color (4.50)** | 15 (2번과 공유 시퀀스 재사용) | **전부 `ok:true` — 거부 없음** | `Preset 50` |
| 2 | 같은 종류의 혼합(Red+Dim100 → Blue+Dim0) | **Dimmer (1.50)** | 15 (동일 시퀀스 재사용, 이어서 시도) | **전부 `ok:true` — 거부 없음** | `Preset 50` |
| 3 | Sine 근사(Accel/Decel -100 ×4채널)+Phase 180(컬러·디머 둘 다) 얹은 2스텝 혼합 | All 1 (21.51) | 23 | **전부 `ok:true`** | `Preset 51` |
| 4 | 3스텝 혼합(Red/20% → Green/60% → Blue/100%) | All 1 (21.52) | 18 | **전부 `ok:true`** | `Preset 52` |

**핵심 결과: 함정②는 이번 라이브 테스트에서 재현되지 않았다.** 컬러+디머 혼합 프로그래머를
Color 풀(4.50)과 Dimmer 풀(1.50)에 각각 `Store Preset`으로 저장 시도했을 때, 둘 다
명령 수준에서 거부(`ok:false`/에러)되지 않고 정확히 All 풀과 동일하게 `{'ok': True,
'result': 'OK'}`가 돌아왔다. `08-...`§3 함정③ 검증 패턴을 그대로 따라 Sine/Phase
레이어를 얹은 3항목·3스텝을 얹은 4항목도 All 풀에서 문법 수준 거부 없이 전부 수락됐다.

### 부분수용(속성 필터링) 여부 — **판정 불가 (GAP, 최악 갈래 미배제)**

지시문이 명시적으로 경고한 "조용한 반쪽 저장"(부분수용) 가능성을 기계로 확인하려
시도했다:

```
prop DataPool/PresetPools/4/50 :: Dimmer       → {'ok': False, 'error': 'property not readable: Dimmer'}
prop DataPool/PresetPools/4/50 :: ColorRGB_R   → {'ok': False, 'error': 'property not readable: ColorRGB_R'}
prop DataPool/PresetPools/1/50 :: Dimmer       → {'ok': False, 'error': 'property not readable: Dimmer'}
prop DataPool/PresetPools/1/50 :: ColorRGB_R   → {'ok': False, 'error': 'property not readable: ColorRGB_R'}
prop DataPool/PresetPools/4/50 :: FeatureCount → {'ok': False, 'error': 'property not readable: FeatureCount'}
prop DataPool/PresetPools/4/50 :: Features     → {'ok': False, 'error': 'property not readable: Features'}
```

전부 "property not readable"로 거부됐다 — `08-...`§4/§6.4·`09-...`§6이 이미 기록한
동일한 구조적 한계(`state` 경로는 `childCount:0`/`children:[]`만 반환, `prop` 경로는
그럴듯한 프로퍼티명을 전부 거부)가 이번 조합에서도 그대로 재확인됐다. 되읽기
`node.name`도 두 슬롯 다 기본형(`Preset 50`) — 직접 RGB/디머 값 방식(팔레트 참조
아님)이라 `08-...`§2와 같은 이유로 자동 이름에 스텝 내용이 노출되지 않는다. 이 이름
신호로는 애초에 부분수용 여부를 판별할 수 없었다.

**정직한 결론: "명령이 거부되지 않았다"는 것만 관측했다 — "저장된 콘텐츠가 컬러+디머
둘 다 온전히 담겼는지, 아니면 그 풀의 담당 속성만 조용히 필터링해 남겼는지"는 이
프로토콜 경로(OSC/Lua state·prop 쿼리)로 판별 불가능하다.** 이것이 지시문이 경고한
"최악의 갈래"일 가능성을 배제하지 못한다 — 배제하지도, 확정하지도 않는다. 확정하려면
저장된 프리셋을 다시 빈 픽스처에 recall해 속성별 실제 레벨을 눈으로 관찰하는 라이브
절차가 필요하며, 이번 세션 범위 밖이다(구조적 한계, `08-...`§3 Rectangle 절과 동일한
이유 — OSC/Lua만 쓰는 이 저장소는 시각적 확인 채널이 없다).

## 4. GAP — 이번 프로브가 채우지 못한 것

1. **부분수용(속성 필터링) 여부** — §2의 판정 불가 결론이 이 프로브의 가장 중요한
   미해결 항목이다. `state`/`prop` 경로 둘 다 저장된 프리셋의 실제 속성 콘텐츠를
   읽을 수 없다(기존 GAP과 동일 구조). 판별하려면 recall 후 시각 관찰이 필요.
2. **핸드오프 문서 함정②의 출처 미상** — "컬러+디머 혼합은 All 풀만 수용"이라는
   주장이 어떤 관측·문서에서 왔는지 이번 프로브로는 추적하지 못했다. 이번 라이브
   테스트가 그 주장을 재현하지 못했다는 사실만 기록한다 — 원 주장이 다른 조건
   (예: 다른 속성 조합, 다른 콘솔 버전, 다른 pool feature 설정)에서는 성립할 수도
   있다는 가능성을 배제하지 않는다.
3. **Rectangle Form의 정확한 수치**는 이번 프로브 범위 밖(이미 `08-...`§4/§6.5에서
   미확정으로 기록됨, 이번에 재검증하지 않음).
4. **응답기 버전 문자열** — ping 자체는 정상이었으나 `--expect-version` 확인은
   생략(범위 밖).

## 5. 다음 세션(카탈로그 구현)에 대한 시사점

- **함정②를 근거로 "혼합은 All 풀에만 저장"이라는 설계 제약을 코드에 강제하면 안 된다**
  — 이번 실측으로는 Color/Dimmer 풀도 명령 수준에서 거부하지 않았다. 반대로 "Color/
  Dimmer 풀도 안전하다"고 단정해서도 안 된다 — §2의 부분수용 GAP이 열려 있는 한,
  혼합 프리셋을 카탈로그가 실제로 저장할 대상 풀은 **여전히 All 풀(21~25)을 기본값으로
  유지**하는 편이 안전하다(관측되지 않은 필터링 위험을 피하는 보수적 선택). 함정②의
  "All 풀만 수용"이라는 서술은 "명령이 거부된다"가 아니라 "안전하게 보장되는 유일한
  경로"로 재해석해 카탈로그 설계 근거로 남긴다.
- 부분수용 GAP을 반드시 닫아야 하는 요구가 생기면, All 풀에 저장한 콘텐츠와 Color/
  Dimmer 풀에 저장한 콘텐츠를 각각 recall해 픽스처 실제 레벨을 라이브로 비교 관찰하는
  별도 M6급 마일스톤이 필요하다 — M0 프로브(OSC/Lua만)로는 닫을 수 없는 GAP이다.
- All 풀 번호(21~25, `All 1`=21)는 §1로 확정됐으므로 하드코딩 근거로 사용 가능.
- 스텝·Form·Phase 문법 자체는 `08-...`/`09-...`가 이미 검증했고 이번 프로브도(23개
  명령 전부 수락) 재확인했다 — 콤보 카탈로그 구현 시 채널명만 컬러+디머 둘 다 나열하는
  방식으로 그대로 재사용 가능하다.
